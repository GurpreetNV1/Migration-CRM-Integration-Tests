# Backup & Restore Service — Test Catalog

This service manages scheduled and on-demand backups of the system's Sheets/Drive-backed data, filtered report exports, and admin-triggered restores, logging the outcome of every run through the Data Gateway; there are 46 tests below, split into 10 integration tests and 36 unit tests.

## Integration tests

### tests/integration/test_health.py

- **test_health** — Checks that the service's health endpoint responds successfully with a simple "everything is fine" status. This is the basic heartbeat check that monitoring tools and orchestration platforms use to confirm the Backup & Restore Service is up and reachable before anyone routes real backup or restore traffic to it, catching outright outages immediately.

### tests/integration/test_backup_flow.py

- **test_is_backed_up_false_before_any_backup_has_run** — Sets up a fresh service with no backup history and asks whether the Audit_Log data is backed up as of a given date. The answer comes back false, proving the system correctly reports "not protected yet" by default rather than optimistically assuming a backup exists, which matters because other services rely on this answer before deleting anything.
- **test_is_backed_up_true_after_a_successful_backup** — Triggers a real backup run, confirms it reports success, then asks the same "is this data backed up" question again for a date before the backup started. The answer is now true, demonstrating that a completed backup run is correctly recognized and recorded so downstream safety checks, such as the Cleanup Service's purge gate, can trust it.
- **test_trigger_backup_succeeds** — Kicks off a full system backup on demand for a given staff member and checks the response: HTTP 201 (created), a run ID that starts with the "BK-" prefix used to identify backup runs, a status of "succeeded," and the run type correctly labeled as a full backup. This proves the manual backup trigger works end to end.
- **test_trigger_backup_while_one_is_in_progress_returns_409** — Simulates a backup that is already mid-run by inserting an "in progress" run log dated in the future, then tries to start a second backup. The service refuses with HTTP 409 (conflict), proving it prevents two backups from running at the same time, which protects against corrupted or overlapping backup data.
- **test_trigger_filtered_export_succeeds** — Requests an export of just one report ("Cold Contacts") in CSV format rather than a full system backup. The service returns HTTP 201 with the run correctly tagged as a "filtered_export" that succeeded, proving staff can pull a narrow, on-demand data extract without having to trigger a full backup of the entire system.
- **test_trigger_filtered_export_with_an_unsupported_format_returns_422** — Attempts to export the "Cold Contacts" report in an "xlsx" file format the service doesn't support and expects a validation error, HTTP 422. This proves the service rejects unsupported export formats up front with a clear error rather than attempting the export and failing partway through or producing a broken file.
- **test_trigger_filtered_export_with_an_empty_report_name_returns_422** — Sends an export request with a blank report name and expects the service to reject it with a 422 validation error. This ensures staff can't accidentally trigger a meaningless export request with nothing to actually export, catching a data-entry mistake before it wastes processing time or clutters the backup logs.
- **test_initiate_restore_succeeds** — Asks the service to restore the "Contact" data scope back to a specific point in time. The response comes back HTTP 200 with a "partial" restore status and details that mention "Contact," proving the manual, admin-driven restore workflow runs and honestly reports that, in this current implementation, it restores partially rather than falsely claiming a full restore.
- **test_initiate_restore_with_missing_scope_returns_422** — Submits a restore request with an empty target scope, meaning no indication of what data to restore, and expects a 422 validation error. This confirms the service won't attempt a restore operation without knowing what it's restoring, preventing an ambiguous or accidental restore across the wrong data.

## Unit tests

### tests/unit/test_in_memory_account_clients.py

- **test_export_full_snapshot_records_the_call_and_returns_files** — Uses a fake, in-memory stand-in for the data-owner's storage account (used in tests instead of real Google Drive/Sheets) to request a full export snapshot. It checks that the request was recorded and that the returned snapshot lists at least one file, verifying the harness the rest of the backup tests depend on to simulate reading from a live account.
- **test_export_filtered_records_the_spec** — Requests a filtered export for a "Cold Contacts" report with a filter on rating, using the same in-memory test double. It confirms the exact filter specification was recorded and that the resulting snapshot is scoped to "Cold Contacts," proving the fake reader behaves like a real filtered export so higher-level export logic can be tested reliably against it.
- **test_write_backup_copy_records_the_snapshot_and_destination** — Writes a two-file snapshot to a fake backup destination folder using the in-memory writer and checks it recorded exactly which snapshot went to which folder, and that it returns file IDs for both files. This validates the test double used to stand in for the real backup storage account when copying files during a backup run.
- **test_write_formatted_export_records_and_returns_a_new_file_id** — Writes a formatted CSV export under the name "report.csv" into a fake destination folder and checks that the write was recorded with the correct filename and folder, and that exactly one new file ID came back. This confirms the in-memory test double correctly represents how a report export lands in backup storage.

### tests/unit/test_export_formatter.py

- **test_csv_formatter_renders_one_row_per_file** — Feeds a snapshot containing two files under the "Cold Contacts" scope into the CSV formatter and checks the resulting CSV text has one row per file, each showing the scope name alongside the file. This proves exported data gets turned into a readable, one-row-per-record CSV file rather than a jumbled or incomplete format.
- **test_factory_resolves_a_registered_formatter** — Registers a CSV formatter under the key "csv" in the export formatter factory and asks the factory for a "csv" formatter back. It confirms the factory returns the exact same formatter instance that was registered, proving the system can correctly look up the right export format handler by name when a user requests a specific file format.
- **test_factory_rejects_an_unregistered_format** — Asks the export formatter factory for a format ("xlsx") that was never registered, expecting it to raise an "unsupported format" error. This proves the system fails clearly and immediately when someone requests an export format that isn't supported, instead of silently producing a wrong or broken file.

### tests/unit/test_backup_executor.py

- **test_run_weekly_backup_succeeds_and_publishes_completed_event** — Runs the automated weekly full backup process using a fixed clock and fake storage accounts, then checks the run finishes as "succeeded" with the completion timestamp exactly matching the fixed clock's time, and that a single "backup.completed" event was published. This proves a normal, healthy backup both completes correctly and notifies the rest of the system.
- **test_run_weekly_backup_rejects_a_second_concurrent_run** — Pre-loads a backup run log marked as already "in progress," then tries to run the weekly backup again. The system raises a "backup already in progress" error rather than starting a second, overlapping backup. This is the core safety rule preventing two backups from writing to storage simultaneously and corrupting the backup set.
- **test_run_weekly_backup_marks_failed_when_the_source_account_is_unavailable** — Simulates the source data account, where live data is exported from, being unreachable during a backup attempt. The run is correctly logged as "failed" with the actual error message captured, and a "backup.completed" event still fires reporting the failure, rather than the whole process crashing silently, so operators are notified even on failure.
- **test_a_previously_failed_run_does_not_block_a_new_one** — After a prior backup run is recorded as "failed," a fresh backup attempt is started and succeeds normally. This proves the system doesn't get permanently stuck after one failure — only an actively in-progress run blocks new attempts, so a temporary outage doesn't require manual intervention to unblock future backups.

### tests/unit/test_restore_strategy.py

- **test_manual_admin_restore_returns_a_partial_outcome_with_details** — Runs the manual, admin-triggered restore strategy for restoring the "Contact" data scope to a specific past date, requested by a named staff member. It checks the outcome is reported as "partial" and that the details text mentions both the scope and the point-in-time requested, confirming the restore strategy honestly reports what it actually did rather than overstating a full recovery.

### tests/unit/test_weekly_backup_scheduler.py

- **test_run_forever_calls_the_backup_fn_repeatedly_until_stopped** — Starts the weekly backup scheduler on a very short interval in a background thread, lets it tick a few times, then tells it to stop. It confirms the backup function was called at least twice before stopping and that the background thread actually exits cleanly, proving the automated scheduling loop reliably fires repeated backups and can be shut down without hanging.
- **test_on_schedule_tick_swallows_an_exception_from_the_backup_fn** — Configures the scheduler's backup function to throw an error, simulating "a backup is already in progress," on each tick, then triggers one tick directly. No exception escapes, proving a single failed or blocked backup attempt doesn't crash the entire scheduler loop, so future scheduled backups keep running on schedule despite one bad tick.

### tests/unit/test_kafka_event_publisher.py

- **test_publish_wraps_event_into_the_full_audit_envelope_shape** — Publishes a "backup.completed" event with a run ID and status, then inspects what was actually sent to the messaging system. It checks the message carries a unique event ID, correctly identifies its source as the backup-restore service, labels the affected record as a "BackupRunLog" with the right ID, and stamps a timezone-aware timestamp, proving every published event is fully traceable for auditing.
- **test_envelope_is_json_serializable** — Publishes a "backup.restore_attempted" event and confirms the resulting audit envelope can be converted to plain text (JSON) without errors. This matters because the event gets sent over the wire to other services and downstream systems; if it weren't serializable this way, the whole audit trail would silently break at the point of publishing.

### tests/unit/test_filtered_export_executor.py

- **test_run_filtered_export_succeeds_and_writes_a_formatted_export** — Runs a filtered export for the "Cold Contacts" report using the default CSV format. It confirms the run is logged as "succeeded," exactly one formatted file named "Cold Contacts.csv" was written to backup storage, and a "backup.export_completed" event was published, proving the full filtered-export pipeline works end to end from request to stored file to notification.
- **test_run_filtered_export_rejects_an_empty_report_name** — Attempts to run a filtered export with no report name specified and expects an "invalid spec" error to be raised, with nothing written to storage. This proves the system validates export requests before doing any work, preventing wasted effort or a nonsensical, unnamed export file from ever being created.
- **test_run_filtered_export_rejects_an_unsupported_format_before_touching_the_source** — Requests an export in an unsupported "xlsx" format and confirms it's rejected with an "unsupported format" error before anything is written to storage. This proves format validation happens up front, so the system never wastes time reading data from the source account only to fail later when trying to write it out in a bad format.

### tests/unit/test_backup_run_log_repository.py

- **test_save_assigns_a_bk_prefixed_id_on_first_save** — Saves a brand-new backup run log with no ID yet and checks the repository assigns it a unique identifier starting with "BK-". This proves every backup run gets a consistent, recognizable ID the moment it starts, which is used throughout the system to track and reference that specific run later.
- **test_save_updates_the_same_row_on_a_second_save** — Saves a run log, marks it "succeeded" with a completion time, then saves it again. The second save updates the same record, same run ID, rather than creating a duplicate entry, proving the repository correctly tracks a run's full lifecycle, from start to finish, as one continuous record instead of scattering it across multiple rows.
- **test_get_latest_returns_none_when_no_runs_exist** — Asks the repository for the most recent full backup run when none have ever been saved, and confirms it returns nothing rather than erroring out. This proves the system handles a brand-new deployment gracefully, correctly reporting "no backup history yet" instead of crashing when there's nothing to find.
- **test_get_latest_returns_the_most_recently_started_run_of_that_type** — Saves three separate runs, two full backups on different dates and one filtered export, and asks for the latest full backup. It correctly returns the most recently started full backup, ignoring the filtered export entirely, proving the system can tell run types apart and always surfaces the truly newest run of the requested kind.
- **test_list_recent_returns_newest_first_up_to_the_limit** — Saves five backup runs on consecutive days and asks for the three most recent. Exactly three come back, ordered with the newest run first, proving the run history view used for monitoring and reporting always shows the latest activity first and correctly respects a requested page size limit.

### tests/unit/test_google_account_clients.py

- **test_export_full_snapshot_lists_untrashed_files** — Simulates calling the real Google Drive API to list files for a full export and checks the request explicitly excludes trashed files ("trashed = false"), returning only the two real files as a snapshot. This proves a full backup never accidentally scoops up deleted files sitting in the trash, keeping the backup clean and representative of live data.
- **test_export_filtered_adds_a_name_contains_clause** — Requests a filtered export where the filter criteria specifies files with "Cold" in the name, and checks the actual Google Drive API query includes a "name contains 'Cold'" clause. This proves filter criteria supplied by the caller are correctly translated into the real search query sent to the storage provider, not silently dropped or ignored.
- **test_export_full_snapshot_wraps_an_http_error** — Simulates the Google Drive API returning a 503 "service unavailable" error while trying to list files for a backup, and confirms this gets translated into the system's own "source account unavailable" error rather than an unhandled, generic Google API exception. This proves outages in the underlying cloud storage are recognized and handled predictably.
- **test_write_backup_copy_calls_copy_per_file** — Writes a two-file snapshot to backup storage and checks the system calls the Google Drive "copy" operation once per file, twice total, collecting both resulting copy IDs. This proves the backup-writing logic properly copies every single file in a snapshot into the backup destination, not just the first one it encounters.
- **test_write_formatted_export_uploads_the_rendered_content** — Uploads a formatted CSV export named "report.csv" into a specific backup folder and checks the real Google Drive "create file" call used the correct file name and correct destination folder. This proves formatted report exports actually land in the right place in cloud storage with the right file name, not a generic placeholder.

### tests/unit/test_restore_coordinator.py

- **test_restore_delegates_to_the_configured_strategy_and_logs_the_run** — Runs a restore request for the "Contact" scope through the restore coordinator, which is wired to a mock restore strategy that reports success. It confirms the coordinator called the strategy with the exact request, published a "backup.restore_attempted" event, and logged the restore as a "succeeded" run, proving every restore attempt is tracked and auditable regardless of which strategy performs it.
- **test_restore_rejects_a_missing_target_scope** — Attempts to initiate a restore with no target scope specified and expects an "invalid restore request" error, with the underlying restore strategy never even being called. This proves the coordinator validates a restore request before doing any real work, preventing an ambiguous restore of "nothing in particular" from ever being attempted.
- **test_restore_rejects_a_missing_point_in_time** — Attempts to initiate a restore for the "Contact" scope but with no point-in-time specified, and expects the same validation error with the restore strategy never invoked. This proves a restore always requires both what to restore and when to restore it back to, preventing an undefined or accidental full-history rollback.

### tests/unit/test_backup_coverage_checker.py

- **test_is_backed_up_false_when_no_runs_exist** — Asks the coverage checker whether "Audit_Log" data is backed up as of a given date when no backup runs exist at all in the system, and confirms it correctly answers false. This proves the safety check other services rely on, like Cleanup before deleting old records, defaults to "not safe" rather than assuming protection that doesn't exist.
- **test_is_backed_up_true_when_a_succeeded_run_completed_after_the_date** — Records a full backup that succeeded and completed the day after the date in question, then asks if data is backed up as of that earlier date. The answer is true, proving the checker correctly recognizes that a completed, successful backup run covers all data up to its completion time.
- **test_is_backed_up_false_when_the_only_run_completed_before_the_date** — Records a successful backup that completed a month before the date being checked, then asks whether data is backed up as of the later date. The answer is false, proving the checker won't treat an old, out-of-date backup as sufficient coverage for a more recent cutoff date, protecting against acting on stale backup evidence.
- **test_is_backed_up_false_when_the_run_failed** — Records a backup run that is marked "failed," even though it has a completion time after the date in question, and asks whether the data is backed up. The answer is false, proving a failed run is never mistaken for successful protection no matter when it finished — only genuinely successful backups count as real coverage.
