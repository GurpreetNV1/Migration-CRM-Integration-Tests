# User Service — Test Catalog

The User Service manages the full Contact lifecycle (enquiry through prospect to client), Staff records, Attendance, Leave Requests, Salary Calculations, and Appointments; this catalog covers all 86 tests for the service, split into 21 integration tests (across 3 files) and 65 unit tests (across 16 files).

## Integration tests

### tests/integration/test_contacts_flow.py

- **test_create_enquiry_defaults_to_cold_rating** — Submits a brand-new walk-in enquiry with just a source and a name, and confirms the API returns a 201 Created with a properly formatted contact ID (prefixed "CT-"), a rating that automatically defaults to "Cold," and a lifecycle state of "Enquiry." This proves a brand-new lead is captured and classified correctly with zero manual setup by staff.
- **test_create_enquiry_accepts_social_media_source** — Creates an enquiry tagging its source as "Social Media" instead of walk-in, and checks the API accepts it (201) and echoes that exact source back. This demonstrates the intake channel is genuinely configurable, so marketing can trust that leads from different channels (ads, referrals, social) are tracked accurately for reporting.
- **test_get_contact_returns_what_was_created** — Creates a contact named "Another Person," then immediately fetches it back by its generated ID and checks the returned name matches what was submitted. This is the basic round-trip guarantee that data saved through the intake form is exactly what staff will see later when pulling up that record during a follow-up call, case review, or handover to another consultant.
- **test_get_unknown_contact_returns_404** — Requests a contact ID that was never created ("CT-999999") and confirms the service responds with a clean 404 Not Found rather than crashing or returning empty/garbage data. This matters because front-end screens and other services need a reliable, predictable signal when a record simply doesn't exist, so they can show a proper "not found" message instead of breaking.
- **test_lifecycle_transition_enquiry_to_prospect** — Creates a fresh enquiry, then moves it forward one stage to "Prospect" via the lifecycle-transition endpoint, checking for a 200 response and the updated state. This proves the core sales-pipeline progression works as staff advance a lead through the stages that ultimately lead to becoming a paying client, which is the backbone of case tracking.
- **test_list_contacts_filters_by_rating** — Creates two contacts, marks one "Hot" and leaves the other at its default, then queries the contact list filtered by rating=Hot and checks exactly one record (the correct one) comes back. This proves staff can reliably shortlist their hottest leads to prioritize follow-up instead of scrolling through every single record in the system by hand.
- **test_skipping_a_lifecycle_stage_returns_409** — Attempts to jump a brand-new Enquiry straight to "Client," skipping the required "Prospect" stage, and confirms the API rejects it with a 409 Conflict. This enforces that every deal must pass through the proper sales stages in order, preventing staff from accidentally mis-recording a client's true progression history in the official case file.
- **test_assign_rating_outside_the_active_ladder_returns_422** — Tries to assign a rating value ("Nonexistent") that isn't part of the currently configured rating ladder, and checks the API refuses it with a 422 validation error. This guarantees ratings always stay within the business-approved scale (e.g. Lost/Cold/Warm/Hot), so reports and dashboards can't be corrupted by typo or stray values.
- **test_assign_rating_within_the_active_ladder_succeeds** — Assigns the valid rating "Hot" to a freshly created contact and confirms a 200 response with the rating correctly updated. This is the positive-path counterpart proving that legitimate rating changes staff make while qualifying a lead are actually saved and reflected immediately on the contact record for the whole team to see.
- **test_set_enquiry_category_with_a_valid_category** — Tags a contact's enquiry with a configured category ("Student Visa") and confirms the update succeeds (200) with the category stored. This shows the system correctly records what type of service a prospective client is interested in, which downstream drives case routing, reporting, and matching each lead to the right specialist consultant on staff.
- **test_set_enquiry_category_with_an_invalid_category_returns_422** — Attempts to tag an enquiry with a made-up category ("Not Real") and confirms the API rejects it with a 422 error rather than silently accepting bad data. This keeps the category list clean and trustworthy so filtering and reporting by service type stay accurate and trustworthy across the whole business.
- **test_link_sponsor_between_two_contacts** — Creates two separate contacts and links one as the "Sponsor" of the other, confirming the response correctly reflects the linked contact's ID. This proves the system can model real-world relationships between people (such as a sponsoring family member), which is essential for accurately documenting migration case files and family-based eligibility for staff to review.
- **test_link_sponsor_to_self_returns_409** — Attempts to link a contact as its own sponsor and confirms the API blocks this nonsensical relationship with a 409 Conflict. This is a data-integrity safeguard preventing an obviously invalid record (a person sponsoring themselves) from ever being saved and confusing later case handling, staff reporting, or official client documentation and audits.
- **test_appointment_intake_and_conversion_to_contact** — Books a new appointment from a phone enquiry (with a contact number and message), confirms it gets an "APT-" prefixed ID, then converts that appointment into a full contact record and checks the resulting contact carries over the same phone number with a proper "CT-" ID. This proves the front-desk booking flow smoothly upgrades a raw enquiry call into a tracked contact without losing any details.
