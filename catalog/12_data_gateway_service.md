# Data Gateway Service — Test Catalog

The Data Gateway Service is the single writer/reader gateway that every other business microservice must go through instead of touching Google Sheets or Drive directly — it enforces per-tab write ownership, routes records and documents to the correct backend, allocates block-based IDs, and maintains an in-memory row index for fast lookups; this catalog documents 92 tests total (19 integration, 73 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — Checks that hitting the gateway's health endpoint returns a 200 response reporting status "ok" and confirms the in-memory row-index (the per-tab lookup table the gateway uses for fast lookups) has finished building and is ready. This matters because if the index isn't ready yet, every other service's reads and writes through the gateway could silently fail or return incomplete data.

### tests/integration/test_records_flow.py

- **test_create_record_allocates_a_gateway_id** — Creates a new Task record with only a status field, sent by the task-service (the tab's rightful owner), and confirms the gateway assigns it a system-generated ID starting with the "TK-" prefix rather than leaving ID assignment to the caller. This proves the gateway centrally manages unique record identifiers so no two services can ever collide on IDs.
- **test_get_record_returns_what_was_created** — After creating a Task record, fetches it back by its newly assigned ID and confirms the returned record matches what was created. This proves basic round-trip read-after-write consistency: a record retrieved from the gateway is exactly the record that was just stored, with nothing lost or altered in between.
- **test_get_unknown_record_returns_404** — Requests a Task record using an ID that was never created and confirms the gateway responds with a 404 Not Found rather than crashing or returning an empty success response. This proves the gateway correctly signals "this record doesn't exist" so calling services can handle missing data gracefully instead of guessing.
- **test_get_record_is_not_restricted_to_the_owning_caller** — Creates a Task record (owned by task-service) then reads it back while identifying as a completely different caller, application-service, and confirms the read still succeeds with a 200. This proves the ownership rule only restricts who may write to a tab; every service remains free to read any tab's data.
- **test_create_with_wrong_caller_returns_403** — Attempts to create a Task record while identifying as application-service, a service that does not own the Task tab, and confirms the gateway blocks the write with a 403 Forbidden. This proves the core per-tab ownership rule: only the one service designated as the owner may write into a given tab.
- **test_unregistered_tab_returns_404** — Sends a create request for a tab name that was never registered with the gateway at all ("NotARealTab") and confirms it returns 404 rather than crashing or silently creating unknown data. This proves the gateway only ever accepts writes into tabs it explicitly knows about and has configuration for.
- **test_update_record_overwrites_fields** — Creates a Task with status "open," then updates it by sending status "done" through the same owning caller, and confirms the returned record now shows "done." This proves the update endpoint correctly applies field changes end-to-end through the full API, not just at the repository layer underneath it.
- **test_batch_get_preserves_requested_order** — Creates two Task records, then requests both by ID in a specific order (second one first) through the batch-get endpoint, and confirms the response returns them in that same requested order rather than creation order. This matters because callers building UI lists or reports depend on predictable, caller-controlled ordering.
- **test_query_records_with_no_filters_returns_everything_in_the_tab** — Creates two Task records with different statuses, then runs a query with no filter criteria at all, and confirms at least both records come back. This proves an empty filter means "give me everything in this tab" rather than nothing, matching the default browsing behavior every consuming service expects.
- **test_query_records_filters_by_field** — Creates a generic Task plus one with a distinctive status value, then queries filtering specifically for that status, and confirms exactly one matching record comes back with the right ID. This proves the query endpoint can narrow results by field value instead of forcing every caller to fetch everything and filter it themselves.
- **test_query_records_is_not_restricted_to_the_owning_caller** — Runs a query against the Task tab while identifying as application-service, which does not own that tab, and confirms it still returns 200. This reinforces, specifically at the query endpoint, that ownership only ever restricts writes; shared configuration tabs and business data alike remain fully readable by every service.
- **test_delete_record_soft_deletes_by_default** — Creates a Contact record as its owning service, deletes it without requesting a hard delete, and confirms the delete succeeds while a follow-up read still finds the record but now flagged is_deleted as true. This proves the default delete behavior preserves data for audit and recovery instead of permanently erasing it outright.
- **test_delete_record_hard_deletes_when_requested** — Creates a Task record then deletes it with the hard=true flag explicitly set, and confirms a subsequent attempt to read that record now returns 404 instead of a soft-deleted stub. This proves callers can opt into genuinely permanent deletion when that is truly the intended behavior, distinct from the safer default.

## Unit tests

### tests/unit/test_row_index.py

- **test_build_maps_ids_to_one_indexed_rows** — Builds an in-memory row index for the Task tab from a list of three record IDs and confirms looking up the first and third IDs returns row numbers 1 and 3 respectively. This proves the gateway's internal lookup table correctly translates a record's ID into the physical spreadsheet row it lives on, which every read and update depends on.
- **test_get_row_before_build_raises_index_not_ready** — Attempts to look up a row number on a freshly created index that has never been loaded with actual sheet data, and confirms this raises an explicit "index not ready" error instead of silently returning a wrong answer. This protects against the gateway serving bad lookups before startup has finished loading data.
- **test_get_row_unknown_id_raises_record_not_found** — Builds an index containing one known ID, then looks up a completely different ID that was never in the sheet, and confirms it raises a clear "record not found" error. This ensures a typo'd or deleted record ID fails loudly and specifically rather than crashing unpredictably or returning the wrong row.
- **test_build_skips_blank_id_cells** — Builds an index from a list that includes an empty string between two real IDs, mimicking a blank row in the underlying spreadsheet, and confirms the two real records still map to their correct row numbers. This proves stray blank rows in the sheet don't corrupt the lookup table or shift other records' positions.
- **test_put_adds_or_overwrites_a_row_mapping** — Builds an empty index, then manually inserts a single ID-to-row mapping, and confirms it can immediately be looked up. This proves the index supports adding a brand-new record's location incrementally right after a create, without needing to rebuild the entire lookup table from scratch every time a row is added.
- **test_remove_fixes_up_row_numbers_below_the_deleted_row** — Builds an index of three records, removes the middle one, and confirms the first record keeps row 1 while the third record's row number shifts down from 3 to 2, matching how a real spreadsheet reflows after a row is deleted. This keeps every remaining record's row pointer accurate after any deletion.
- **test_remove_unknown_id_is_a_no_op** — Removes an ID from the index that was never present in it, and confirms this does not raise an error and leaves the existing record's row mapping untouched. This proves the index tolerates a redundant or already-processed delete request without corrupting its state or throwing an unnecessary failure.
- **test_registry_get_index_returns_the_same_instance_per_tab** — Asks the row-index registry for the Task tab's index twice and confirms it hands back the exact same object both times rather than two separate copies. This proves each tab has exactly one shared, consistent lookup table in memory, so every part of the service always sees the same up-to-date row positions.
- **test_registry_build_all_marks_every_tab_ready** — Builds indexes for two tabs at once using a supplied data-fetching function, and confirms the registry reports itself fully ready afterward and that the Task tab's index correctly resolves its one known record. This proves the startup routine that primes every tab's lookup table in one pass works correctly.
- **test_registry_not_ready_until_built** — Checks a freshly created, empty row-index registry and confirms it reports itself as not ready before any tab data has been loaded into it. This is the guard behind the health-check endpoint's "index_ready" flag, ensuring the service never claims to be healthy before it can actually serve accurate lookups.

### tests/unit/test_retry.py

- **test_succeeds_on_the_first_try_with_no_retries** — Runs a mocked Google API request that succeeds immediately, and confirms the retry helper returns the successful result while calling the underlying request exactly once. This establishes the baseline: when Google Sheets or Drive responds normally, the retry wrapper adds no extra calls, delay, or overhead to the happy path.
- **test_retries_a_transient_503_and_then_succeeds** — Simulates a Google API call that fails once with a 503 Service Unavailable error and then succeeds on the second attempt, and confirms the retry helper automatically tries again and returns the eventual successful result. This proves the gateway can ride out brief Google outages without the failure ever reaching the calling service.
- **test_every_documented_retryable_status_is_retried (429)** — Simulates Google's own "Too Many Requests" rate-limit response failing once before succeeding, and confirms the retry helper treats it as transient and retries through to success. This is the exact status a real quota-exhaustion hit returns, so this case matters more than the others here.
- **test_every_documented_retryable_status_is_retried (500)** — Simulates a generic Google-side Internal Server Error failing once before succeeding, and confirms it's retried the same as every other documented transient code. This covers Google's own infrastructure having a momentary problem unrelated to anything this service did wrong.
- **test_every_documented_retryable_status_is_retried (502)** — Simulates a Bad Gateway response failing once before succeeding, and confirms it's retried rather than surfaced immediately as a hard failure. This is the kind of error a flaky intermediate proxy/load balancer on Google's side can produce transiently.
- **test_every_documented_retryable_status_is_retried (503)** — Simulates Google's Service Unavailable response failing once before succeeding, and confirms it's retried. This is the same status this service's own callers see when ITS quota is exhausted, so proving it's retried here is proving the documented convention end to end.
- **test_every_documented_retryable_status_is_retried (504)** — Simulates a Gateway Timeout failing once before succeeding, and confirms it's retried the same as the other four codes. Together, these five cases prove the full documented set of temporary Google errors is actually covered, not just one example code.
- **test_a_non_retryable_status_is_raised_immediately_without_retrying** — Simulates a Google API call failing with a 404 Not Found, a permanent error rather than a transient one, and confirms the retry helper raises it immediately after exactly one attempt instead of wasting time retrying something that will never succeed. This keeps genuine, non-recoverable errors from being masked or delayed.
- **test_exhausting_all_attempts_raises_data_store_unavailable** — Simulates a Google API call that keeps failing with 503 errors on every attempt, and confirms that after the configured maximum of three attempts, the retry helper gives up and raises a clear "data store unavailable" error rather than retrying forever or hanging indefinitely. This surfaces genuine, sustained Google outages honestly to the caller.
- **test_a_raw_transport_error_is_retried_like_a_transient_5xx (SSL error)** — Simulates the underlying network connection itself failing with an SSL error ("wrong version number") rather than Google returning a structured HTTP error response, and confirms the retry helper treats it exactly like a transient 503 and retries until it succeeds. This was confirmed live: a shared connection getting corrupted by concurrent requests surfaced this way, not as an HttpError, and had to be retried rather than crashing the request outright.
- **test_a_raw_transport_error_is_retried_like_a_transient_5xx (timeout)** — Simulates a raw socket/read timeout instead of an HTTP error response coming back from Google, and confirms the retry helper still recognizes it as a transient, retryable failure and succeeds on the next attempt. This protects against a slow or momentarily unreachable network dropping a request entirely instead of quietly recovering.
- **test_a_raw_transport_error_is_retried_like_a_transient_5xx (connection reset)** — Simulates the connection being abruptly reset mid-request, and confirms this raw transport-level failure is retried the same way a transient 503 would be, rather than being leaked out to the caller as an unhandled error. This covers a real-world network hiccup that has nothing to do with Google's API logic but must not take down a request.
- **test_a_raw_transport_error_is_retried_like_a_transient_5xx (socket timeout)** — Simulates a low-level socket timeout distinct from the read-timeout case above, and confirms it too is retried automatically and succeeds on the following attempt. Together with the other three transport-error cases, this proves the retry helper treats every kind of raw network failure it might realistically encounter as transient, not just clean HTTP error responses from Google itself.
- **test_exhausting_all_attempts_on_a_transport_error_raises_data_store_unavailable** — Simulates a raw SSL transport error that keeps happening on every single attempt, and confirms that once the maximum attempt count is exhausted, the retry helper gives up and raises the same "data store unavailable" error it would for a persistent HTTP 503, rather than leaking the raw low-level network exception out to the caller. This ensures sustained network-level failures are reported through the same clear, consistent error as sustained Google API failures.
- **test_backoff_delays_grow_and_are_only_called_between_attempts** — Simulates a request that always fails, allowing three attempts, and captures the delay values passed to the sleep function, confirming they double each time (1 second, then 2 seconds) and that a sleep only happens between attempts, never after the last one. This proves the backoff strategy avoids hammering an already-struggling Google API.

### tests/unit/test_id_allocation_service.py

- **test_first_id_for_a_new_prefix_starts_at_one** — Asks the ID allocator for the very first ID under a brand-new "TK" (Task) prefix and confirms it returns "TK-000001." This proves new record types start their numbering cleanly at one, with the zero-padded six-digit format every downstream service expects when parsing or displaying record IDs.
- **test_ids_increment_sequentially_within_a_block** — Configures the ID allocator with a 100-ID block size, then requests three consecutive IDs under the same "TK" prefix and confirms they come back in strict sequential order: TK-000001, TK-000002, TK-000003. This proves the allocator hands out gap-free, correctly-ordered IDs for a single prefix within one reserved block, which every service relies on for predictable, non-colliding record numbering.
- **test_reserving_a_block_writes_the_counters_row_once** — Requests five IDs in a row under the same prefix with a block size of 100, then checks the underlying counters record, confirming its stored "next available ID" value has been written as 101. This proves the allocator reserves a whole block of IDs in a single write rather than performing one costly write per ID handed out.
- **test_common_path_makes_no_repository_call_once_a_block_is_reserved** — After the first ID reserves a fresh block, disables the counters repository's read and update methods entirely and requests a second ID, confirming it still succeeds. This proves that once a block of IDs is reserved in memory, handing out subsequent IDs from that block needs zero further calls to the underlying data store, keeping allocation fast.
- **test_exhausting_a_block_reserves_a_fresh_one** — Configures a small block size of 2, then requests three IDs in a row, and confirms the third request transparently triggers reservation of a new block (the counters value jumps to 5) while still returning the correctly sequential TK-000003. This proves the allocator seamlessly refills its supply of IDs once a block runs out, with no gaps or duplicates.
- **test_different_prefixes_get_independent_blocks** — Requests IDs under two different prefixes, "TK" and "AP," interleaved with each other, and confirms each prefix maintains its own independent sequential counter (TK-000001, AP-000001, TK-000002) rather than sharing one global counter. This proves different record types, like Tasks and Applications, never collide or skip numbers because of each other's activity.
- **test_failed_block_reservation_raises_data_store_unavailable** — Forces the underlying counters repository to fail every write, then requests an ID, and confirms the allocator raises a clear "data store unavailable" error instead of silently handing out a duplicate or invalid ID. This ensures that if Google Sheets can't be reached to reserve a new ID block, the failure is obvious rather than corrupting data.
