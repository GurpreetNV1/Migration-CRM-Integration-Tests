# Audit Service — Test Catalog

The Audit Service consumes change-events, delivered via Kafka in production or a synchronous HTTP stand-in endpoint in tests, from every other publishing service, buffers them in memory, flushes them in batches to durable storage, and exposes a query API to fetch an entity's full audit trail by target type and target ID; this catalog documents 40 tests total (7 integration, 33 unit).

## Integration tests

*These also live at `../tests/service_integration/audit/`, dual-mode (real Data Gateway/real Sheets by default, `--gateway-mode=memory` for the fast in-memory behavior described below) — run via `python run_local_integration_tests.py --service audit`. Same definitions apply to both; see `../README.md`/`../TESTING_GUIDE.md` section 8.5.*

### tests/integration/test_health.py

- **test_health** — Checks that hitting the audit service's health endpoint returns a 200 response with a simple status of "ok." This is the most basic smoke test confirming the service is up and responding at all, which matters because every other publishing service depends on reliably being able to send audit events here.

### tests/integration/test_audit_flow.py

- **test_ingest_event_returns_202** — Submits a single audit event, a Contact-created action performed by a staff member, to the ingestion endpoint and confirms it's accepted with a 202 Accepted response. This proves the service acknowledges incoming events immediately without making the publishing service wait for the event to actually be written to permanent storage.
- **test_ingested_event_appears_in_the_audit_trail_after_force_flush** — Submits an event, then forces the internal buffer to flush immediately rather than waiting for its normal batching schedule, and confirms querying that contact's audit trail now returns exactly one entry with the correct action. This proves the full path from ingestion through buffering to durable storage and back out through the query API actually works end to end.
- **test_audit_trail_missing_target_type_returns_400** — Queries the audit trail endpoint supplying only a target ID but omitting the required target type parameter, and confirms this returns a 400 Bad Request rather than an empty or incorrect result. This ensures callers get clear, immediate feedback when they forget a required parameter instead of silently getting back wrong or empty data.
- **test_audit_trail_missing_target_id_returns_400** — Queries the audit trail endpoint supplying only a target type but omitting the required target ID, and confirms this also returns 400 Bad Request. This proves both halves of the required "which entity's history do you want" identifier are independently validated and enforced, not just one of the two.
- **test_malformed_ingested_event_is_dead_lettered_and_never_flushed** — Submits an audit event with its required actor_id field deleted entirely, and confirms the request is rejected outright with a 422 Unprocessable Entity error at the API's schema validation layer, before it ever reaches the internal event-processing pipeline. This proves malformed events are caught and blocked at the earliest possible point, rather than being accepted and silently dropped or corrupted later.
- **test_multiple_events_batch_and_flush_together** — Submits three separate audit events for the same contact in quick succession, then force-flushes the buffer once, and confirms all three show up together in that contact's audit trail. This proves the batching mechanism correctly accumulates multiple distinct events before writing them out as one combined batch, rather than only ever handling events one at a time.

## Unit tests

### tests/unit/test_audit_event_envelope.py

- **test_valid_envelope_is_valid** — Builds a fully well-formed audit event, event ID, source service, actor, action, target, and a proper UTC timestamp, and confirms the envelope's own self-validation check reports it as valid. This establishes the baseline "good data passes" case that every other validation test in this file compares itself against.
- **test_missing_actor_id_is_invalid** — Builds an otherwise well-formed audit event but with an empty actor_id, the field identifying who performed the action, and confirms the envelope reports itself as invalid. This ensures every audit entry can always be traced back to a specific responsible person or system, since an audit trail with unknown actors would be useless for accountability.
- **test_missing_target_id_is_invalid** — Builds an otherwise well-formed audit event but with an empty target_id, the field identifying which record the action happened to, and confirms it's flagged invalid. This ensures every audit entry can always be tied back to a specific entity, since a log entry with no identifiable subject would be meaningless when someone later tries to look up a record's history.
- **test_naive_timestamp_is_invalid** — Builds an audit event using a timestamp created without any timezone information attached at all, a so-called naive datetime, and confirms the envelope flags it as invalid. This guards against ambiguous timestamps entering the audit trail, since a time with no timezone reference could be misinterpreted and misplace an event in the historical record.
- **test_non_utc_timezone_is_invalid** — Builds an audit event using a timestamp in a non-UTC timezone (UTC+5:30), and confirms the envelope flags it as invalid even though the timestamp does carry timezone information. This enforces that every event's time is recorded in one single, consistent standard timezone, so audit trails can always be compared and sorted correctly regardless of which service or region an event originated from.

### tests/unit/test_flush_policy.py

- **test_does_not_flush_an_empty_buffer** — Checks the flush policy with zero pending events and a large elapsed time, and confirms it says not to flush. This proves the service never wastes effort triggering a flush cycle when there's genuinely nothing buffered to write out, avoiding pointless, empty writes to permanent storage.
- **test_flushes_once_batch_size_reached** — Checks the flush policy at exactly 50 pending events (the configured batch size) versus 49, and confirms it recommends flushing right at 50 but not one short of it. This proves the size-based trigger that keeps audit batches from growing unboundedly in memory fires at precisely the configured threshold, not before or after.
- **test_flushes_once_interval_elapsed** — Checks the flush policy with just one pending event but different elapsed times, confirming it recommends flushing once the configured 2-second interval has passed but not at 1.9 seconds. This proves the time-based trigger ensures even a single lonely audit event doesn't sit unflushed indefinitely just because the batch never fills up.

### tests/unit/test_audit_event_consumer.py

- **test_valid_dict_message_is_forwarded_to_the_buffer** — Passes a well-formed audit event, already as a plain dictionary, into the consumer and confirms it gets forwarded to the buffer exactly once with nothing sent to the dead-letter sink. This proves normal, healthy events flow straight through to buffering without being needlessly rejected or delayed.
- **test_valid_json_string_message_is_forwarded_to_the_buffer** — Passes the same well-formed event, but this time serialized as a raw JSON string rather than a Python dictionary (mimicking how a real Kafka message would actually arrive), and confirms it's still correctly parsed and forwarded to the buffer. This proves the consumer handles both the in-memory test format and the real wire format Kafka delivers in production.
- **test_malformed_message_is_dead_lettered_not_raised** — Passes a string that isn't valid JSON at all into the consumer, and confirms the buffer never receives it while the dead-letter sink records exactly one rejected message, with no exception escaping to crash the consumer. This proves one garbled message from a misbehaving publisher can never bring down audit ingestion for every other service.
- **test_message_missing_a_required_field_is_dead_lettered** — Passes a well-formed JSON payload with its actor_id field removed into the consumer, and confirms it's rejected into the dead-letter sink rather than being buffered. This proves incomplete events are caught by the same validation logic used elsewhere and safely quarantined instead of being silently accepted with missing accountability information.
- **test_message_with_a_non_utc_timestamp_is_dead_lettered** — Passes an otherwise valid event whose timestamp is in a non-UTC timezone (+5:30) into the consumer, and confirms it's dead-lettered with the recorded reason "validation failed" rather than being buffered. This proves the same timezone-consistency rule enforced on the envelope itself is actually applied at the point where real incoming messages get processed.

### tests/unit/test_audit_query_service.py

- **test_get_audit_trail_queries_by_target_type_and_id** — Asks the query service for a Contact's audit trail by its target type and ID, and confirms it calls the underlying repository's query method with exactly those two values as a filter. This proves fetching "everything that ever happened to this specific record" is implemented as a simple, direct filter rather than some more complex or error-prone lookup path.

### tests/unit/test_audit_event_buffer.py

- **test_add_does_not_flush_below_threshold** — Adds a single event to a buffer configured with a batch size of 50 and a very long time interval, and confirms the writer's flush method is never called while the buffer correctly reports one pending event. This proves the buffer patiently accumulates events without prematurely writing tiny batches to storage one at a time.
- **test_add_flushes_and_clears_once_batch_size_reached** — Adds two events to a buffer configured with a batch size of exactly 2, and confirms the writer's flush method fires exactly once and the buffer's pending count drops back to zero immediately afterward. This proves reaching the configured batch size automatically triggers a write and then correctly resets the buffer for the next batch.
- **test_failed_flush_keeps_pending_events_for_the_next_trigger** — Configures the writer to raise a flush-failure error, adds one event that triggers an immediate flush attempt, and confirms the event remains counted as pending afterward rather than being lost. This proves that if the storage layer fails during a flush, the buffered events aren't discarded and get another chance to be written on a later trigger.
- **test_force_flush_ignores_the_policy** — Configures a buffer with a batch size and interval both huge enough that a normal flush would never trigger, adds one event, then explicitly calls force_flush, and confirms it writes immediately and clears the pending count regardless of the policy thresholds. This is exactly what powers the integration tests' ability to deterministically flush without waiting on real time or accumulating huge batches.
- **test_buffer_stops_accepting_new_events_once_the_cap_is_reached** — Configures a buffer with a hard cap of 2 pending events, adds three events in a row, and confirms only 2 ever end up counted as pending. This proves the buffer has a built-in safety limit protecting the service's memory from growing without bound if storage becomes unavailable and events pile up faster than they can be flushed.

### tests/unit/test_data_gateway_audit_log_repository.py

- **test_append_batch_generates_ids_when_not_supplied** — Appends a single audit log entry with no log_id supplied, through the repository that writes audit data via the Data Gateway service, then queries it back and confirms it was assigned an ID starting with the "AUD-" prefix. This proves the repository, not the caller, is responsible for generating unique identifiers for every stored audit log entry.
- **test_query_filters_by_target** — Appends two audit log entries for two different contacts, then queries specifically for one of those contacts, and confirms only that one matching entry comes back rather than both. This proves the audit trail lookup correctly isolates one specific entity's history instead of returning unrelated entries mixed in alongside it.
- **test_query_returns_newest_first** — Appends two audit log entries for the same contact with different timestamps, an older one and a newer one, and queries that contact's trail, confirming the newer entry comes back first in the results. This proves audit history is presented in a natural, most-recent-first reading order, matching how someone reviewing "what happened to this record recently" would expect to see it.

### tests/unit/test_audit_log_writer.py

- **test_flush_maps_envelopes_and_persists_via_the_repository** — Flushes a single audit event envelope through the writer with a supplied ID generator, and confirms the repository's append_batch method is called with a properly converted audit log record carrying the generated ID and the correct target ID. This proves the writer's core job of translating raw incoming events into permanent, storable audit log records works correctly.
- **test_small_detail_json_is_not_truncated** — Flushes an event carrying a small amount of extra detail data (a single short field), and confirms that detail data is stored completely intact and unmodified in the resulting audit log record. This establishes the baseline case that ordinary, reasonably-sized event details pass through the writer without being altered or shortened in any way.
- **test_oversized_detail_json_is_truncated_with_a_marker** — Flushes an event carrying a deliberately huge chunk of detail data (20,000 characters), and confirms the stored version is cut short, ends with a "...truncated" marker, and stays within a 10,000-byte size limit. This protects the underlying storage from being overwhelmed by unexpectedly massive event payloads while still leaving a clear signal that data was trimmed.
- **test_flush_retries_on_failure_and_succeeds_within_the_attempt_budget** — Configures the repository to fail once with a transient error and then succeed on a second attempt, flushes an event, and confirms the writer retried and the batch was ultimately written successfully after exactly two attempts. This proves a brief, temporary storage hiccup doesn't cause audit data to be lost, mirroring the same resilience the gateway itself provides for Google API calls.
- **test_flush_raises_after_exhausting_all_attempts** — Configures the repository to fail on every single attempt, flushes an event, and confirms the writer gives up after exactly three tries and raises a clear "audit flush failed" error rather than retrying forever or silently swallowing the failure. This ensures a genuinely broken storage backend produces a loud, actionable failure instead of quietly losing audit data.

### tests/unit/test_kafka_consumer_runner.py

- **test_run_forever_subscribes_by_pattern_not_a_single_topic** — Starts the real Kafka-backed consumer runner against a mocked Kafka client and confirms it subscribes using a topic pattern rather than one hardcoded topic name, with specific consumer settings like manual offset commits and reading from the earliest available offset. This matters because each publishing service uses its own topic name, so the audit service must catch all of them by pattern, not just one hardcoded topic.
- **test_run_forever_passes_each_message_value_to_the_consumer_and_commits** — Feeds the runner one fake Kafka message and confirms its value is handed off to the event consumer's on_message method and that the Kafka offset is then explicitly committed afterward. This proves the runner only acknowledges a message as processed after it's actually been handled, reducing the risk of silently losing events on a crash.
- **test_run_forever_closes_the_client_when_done** — Runs the Audit Service's Kafka consumer loop against a fake client with no messages waiting, then confirms that once the loop exits, the underlying connection to the message broker is explicitly closed rather than left dangling. This ensures the service cleans up its network resources correctly on shutdown or restart, rather than silently leaking open broker connections that could eventually exhaust available connections.
- **test_stop_sets_running_false** — Manually flips the runner's internal running flag to true, calls stop(), and confirms the flag is now false. This is the basic mechanism the service uses to gracefully shut down the Kafka consumption loop on demand, for example during a controlled service restart or deployment.

### tests/unit/test_periodic_flusher.py

- **test_run_forever_calls_flush_fn_repeatedly_until_stopped** — Starts a periodic flusher configured to run every 0.05 seconds on a background thread, lets it run for roughly 0.23 seconds, then stops it, and confirms the flush function was called at least three times and the background thread actually terminates cleanly. This proves the time-based flush trigger reliably fires on its own schedule without manual intervention and shuts down properly when asked.
- **test_stop_before_the_first_interval_prevents_any_flush_call** — Starts a periodic flusher configured with a long 10-second interval, immediately calls stop() before that interval could ever elapse, and confirms the flush function was never called even once and the background thread exits promptly. This proves a fast shutdown request is honored immediately rather than the flusher waiting around for its next scheduled tick.
