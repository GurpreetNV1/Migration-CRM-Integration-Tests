# Notes Service — Test Catalog

The Notes Service lets staff log free-text notes against a Contact or an Application, keeps those notes staff-only and author-locked, validates note categories against live configuration, and supports an additive admin review layer, all backed by a Data Gateway; this catalog covers 47 tests in total (14 integration, 33 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — This test proves the Notes Service is alive and reachable by calling the standard /health endpoint that monitoring and load-balancing tools rely on before routing real traffic. It checks that the response comes back with a success status and a simple confirmation message, giving operators an early, reliable signal that the service is ready to serve requests.

### tests/integration/test_notes_flow.py

- **test_create_note_against_a_contact** — Demonstrates the core scenario of a staff member logging a note against a Contact record. It posts a valid note with target type Contact, an author, and the "general" note type, and confirms the service returns success, generates a proper NT-prefixed note ID, and automatically marks the note as staff-only visibility rather than client-visible.
- **test_create_note_against_an_application** — Shows the same note-creation flow works equally well when the note is attached to an Application instead of a Contact, proving the polymorphic target design genuinely supports both record types. It submits a "follow_up" note against an Application and confirms the response is successful and correctly echoes back Application as the stored target type.
- **test_create_note_with_an_illegal_target_type_returns_422** — Confirms the service enforces a fixed whitelist of record types notes can be attached to. It attempts to create a note against a made-up target type ("Ticket") that isn't Contact or Application, and verifies the request is rejected with a client error rather than silently accepted, protecting data integrity against invalid or unsupported target references.
- **test_create_note_with_an_unconfigured_note_type_returns_422** — Verifies that note categories are governed by live configuration, not free text. It submits a note using a made-up note_type ("not_a_real_type") that has not been registered in the system's configured list, and confirms the service rejects it with a client error, preventing staff from inventing arbitrary categories outside the approved taxonomy.
- **test_get_note_returns_what_was_created** — Confirms that once a note is saved, it can be retrieved again with its data intact. It creates a note, then fetches it back by its generated ID, and checks the returned note ID matches exactly what was created, proving the read path correctly returns the same record that was just persisted.
- **test_get_unknown_note_returns_404** — Checks that looking up a note ID that was never created returns a proper "not found" response instead of an error or an empty success. It requests a clearly nonexistent note ID and confirms the service answers with a 404 status, so client applications can distinguish genuinely missing notes from other kinds of failures.
- **test_list_notes_filters_by_author_id** — Proves that notes can be searched by the staff member who wrote them. It creates a note under a distinct author ID, then queries the notes list filtered to that same author, and confirms the created note appears in the results, supporting everyday staff workflows like "show me all notes I've written."
- **test_author_can_update_their_own_note** — Confirms that a staff member who wrote a note is allowed to edit its content later, for example to correct or add detail. It creates a note as one author, submits an update as that same author, and checks the update succeeds and the note's content field reflects the new text supplied.
- **test_a_different_staff_member_cannot_update_someone_elses_note** — Enforces that notes are private to their author for editing purposes: one staff member cannot rewrite another's note. It creates a note under one staff ID, then attempts to update it while posing as a different staff member, and confirms the service blocks the attempt with a 403 forbidden response.
- **test_an_admin_identity_still_cannot_update_someone_elses_note** — Proves there is no admin override for editing someone else's note content, not even for an identity representing an Admin or Director role. It creates a note under one author, then tries to update it as "STF-ADMIN," and confirms the request is still rejected with a 403, matching the rule that authorship protection has no exceptions.
- **test_author_can_delete_their_own_note** — Confirms a staff member can remove a note they personally authored, when it's no longer needed. It creates a note under a given author, then sends a delete request identifying that same staff member as the requester, and checks the service responds with a 204 success status confirming the note was fully removed as expected.
- **test_a_different_staff_member_cannot_delete_someone_elses_note** — Confirms deletion rights are as tightly restricted as editing rights: only the original author can delete their own note. It creates a note under one staff member, then attempts to delete it while identifying as a different staff member, and verifies the service refuses with a 403 forbidden response, keeping notes safe from unauthorized removal.
- **test_attach_review_does_not_change_content_or_author** — Demonstrates that the admin review layer is purely additive metadata layered on top of a note, never a rewrite of the note itself. It creates a note, then attaches an admin review marking it "reviewed" with a comment, and confirms the review status and reviewer are recorded while the original content and author remain completely unchanged.

## Unit tests

### tests/unit/test_note_ownership_guard.py

- **test_assert_is_author_allows_the_actual_author** — Confirms the ownership check that protects notes from unauthorized edits correctly lets the real author through. It builds a note authored by one staff ID and verifies that checking that same staff ID against the note raises no error, proving legitimate authors are never mistakenly blocked from touching their own notes.
- **test_assert_is_author_rejects_a_different_staff_member** — Confirms the ownership guard blocks anyone other than the note's original author. It builds a note under one staff ID, then checks a different staff ID against it, and verifies the guard raises a "not the author" error, forming the foundation of the rule that only authors can change their own notes.
- **test_assert_is_author_rejects_an_admin_role_identity_with_no_override** — Proves at the lowest level that there is no special-case bypass for admin identities in the ownership check, because the guard has no concept of roles at all. It checks a staff ID representing an admin against someone else's note and confirms the same authorship error is raised as it would be for any other non-author.

### tests/unit/test_note_target_validator.py

- **test_validate_accepts_contact** — Confirms that "Contact" is recognized as a legitimate, supported target type for a note in this polymorphic system. It runs the validator against the string "Contact" and checks it correctly resolves to the internal Contact target type, proving the target system correctly recognizes contacts as a valid destination for staff-written notes.
- **test_validate_accepts_application** — Confirms that "Application" is also recognized as a legitimate target type for a note, alongside Contact, in this two-target design. It runs the validator against the string "Application" and checks it resolves to the internal Application target type, proving both supported record kinds are correctly accepted by the exact same validation logic.
- **test_validate_rejects_an_unregistered_target_type** — Confirms the target validator actively rejects target types outside the supported set rather than accepting anything handed to it. It runs the validator against "Ticket," a type that isn't Contact or Application, and checks it raises an invalid-target-type error, the underlying rule that produces the 422 response seen in the integration tests.

### tests/unit/test_note_type_validator.py

- **test_validate_accepts_a_currently_configured_type** — Confirms note types are validated against whatever list is currently configured, not a hardcoded list buried in the code somewhere. It sets up a validator backed by a mock configuration returning "general" and "follow_up" as allowed, then checks that validating "general" succeeds without error, proving properly configured categories are accepted correctly.
- **test_validate_rejects_a_type_not_in_the_configured_set** — Confirms the note type validator actively rejects any category not present in the currently configured allowed list. Using a mock configuration allowing only "general" and "follow_up," it validates "escalation" and checks the validator raises an invalid-note-type error, enforcing that staff can only tag notes with approved, configured categories, and nothing else.

### tests/unit/test_gateway_note_config_provider.py

- **test_get_allowed_note_types_reads_from_system_config** — Confirms the list of allowed note types is sourced from the shared System_Config data rather than being fixed in the service's own code. It seeds a config record listing "general" and "follow_up," then checks the config provider reads and returns exactly that list, proving note categories are centrally, dynamically configurable.
- **test_get_allowed_note_types_caches_within_the_ttl** — Confirms the allowed-note-types lookup is cached for performance rather than hitting the data store on every single request. It reads the configured types once, then changes the underlying config value, and confirms a second read within the cache window still returns the original, cached list instead of the freshly changed one.
- **test_get_allowed_note_types_raises_when_config_missing** — Confirms the service fails safely and loudly if the note-type configuration record is missing entirely, rather than silently allowing any note type through. It queries an empty configuration store and checks the provider raises a "configuration unavailable" error, preventing notes from ever being created with no governing rules in place.

### tests/unit/test_kafka_event_publisher.py

- **test_publish_wraps_event_into_the_full_audit_envelope_shape** — Confirms that every event this service emits for audit purposes carries a complete, consistent envelope of metadata. It publishes a "note.created" event and checks the resulting message includes a unique event ID, the source service name, an actor, the correct action and target identifiers, the original event details, and a timezone-aware timestamp.
- **test_envelope_is_json_serializable** — Confirms the audit event envelope this service builds can actually be serialized to JSON without errors, which matters because Kafka consumers and downstream audit systems expect valid JSON messages. It publishes a "note.deleted" event and checks the resulting envelope converts cleanly to a JSON string with no encoding failures whatsoever.

### tests/unit/test_note_review_service.py

- **test_attach_review_sets_review_fields_without_touching_content_or_author** — Confirms, at the service layer, that attaching an admin review to a note only adds review metadata and leaves the note's substance untouched. It attaches a "reviewed" status with a comment from an admin staff ID and checks the review status, reviewer, and comment are set while the original content and author stay exactly as they were.
- **test_attach_review_confirms_the_note_exists_first** — Confirms the review workflow always looks up the target note before attaching a review to it, rather than blindly writing review data against a note ID that might not exist. It attaches a review and checks the repository's find-by-ID lookup was called exactly once with the correct note ID beforehand.
- **test_attach_review_publishes_a_reviewed_event** — Confirms that attaching an admin review to a note triggers an audit trail event, so review actions are traceable just like note creation or deletion already are. It attaches a review and checks that exactly one event was published, carrying the "note.reviewed" topic name, keeping the audit log complete and consistent.

### tests/unit/test_note_service.py

- **test_create_note_saves_and_publishes_created_event** — Confirms the core note-creation service correctly saves a new note through the repository and announces its creation to the rest of the system. It creates a note with valid data and checks the returned note carries a generated ID, that the repository's save method was actually invoked, and that a "note.created" event was published.
- **test_create_note_sets_created_at** — Confirms every newly created note is automatically timestamped, so there is always a record of when it was written even if no one supplies that value themselves. It creates a note and inspects the object handed to the repository for saving, checking that its created_at field has been populated rather than left blank or empty.
- **test_create_note_rejects_an_illegal_target_type** — Confirms the note-creation service itself, not just the API layer, enforces the valid target type rule. It attempts to create a note against the unsupported "Ticket" target type and checks an invalid-target-type error is raised and, critically, that the repository's save method is never called, so no bad data reaches storage.
- **test_create_note_rejects_an_unconfigured_note_type** — Confirms the note-creation service rejects a note type outside the currently configured allowed set, using a setup where only "general" is permitted. It attempts to create a note tagged "escalation" and checks an invalid-note-type error is raised and that the repository's save method is never invoked, so unapproved categories never reach storage.
- **test_update_note_by_the_author_succeeds** — Confirms the note-update service lets the original author change their note's content when they need to. It sets up an existing note authored by one staff member, requests an update from that same staff member, and checks the returned note reflects the new content and that a "note.updated" event was published to record the change.
- **test_update_note_by_a_non_author_is_rejected** — Confirms the note-update service blocks edits from anyone but the original author, at the business-logic layer rather than just the API. It attempts to update a note as a different staff member than its author, and checks the service raises a not-the-author error, the repository's update method is never called, and no event is published.
- **test_delete_note_by_the_author_succeeds** — Confirms the note-deletion service allows the original author to remove their own note when appropriate. It sets up an existing note and requests its deletion from the same staff member who authored it, then checks the repository's delete method was called with the correct note ID and that a "note.deleted" event was published.
- **test_delete_note_by_a_non_author_is_rejected_even_for_an_admin_identity** — Confirms deletion is blocked for any non-author, explicitly including an identity representing an admin role, at the service layer itself. It attempts to delete a note as "STF-ADMIN" when the note belongs to a different staff member, and checks a not-the-author error is raised, the repository's delete is never called, and no event fires.
- **test_list_notes_delegates_to_repository_find_by_filter** — Confirms the note-listing service correctly passes search criteria through to the storage layer rather than doing its own ad-hoc filtering. It requests a list of notes filtered by a specific target ID and checks the repository's find-by-filter method was called exactly once with that same filter, proving the search request is handled faithfully end to end.

### tests/unit/test_gateway_note_repository.py

- **test_save_assigns_an_nt_prefixed_id** — Confirms that saving a brand-new note through the storage layer automatically generates a properly formatted identifier. It saves a note with no ID supplied and checks that the saved record comes back with a note ID that is not empty and begins with the "NT-" prefix used consistently throughout the system for notes.
- **test_find_by_id_returns_what_was_saved** — Confirms the storage layer's lookup-by-ID faithfully returns the same data that was written to it. It saves a note with specific content and a Contact target type, then fetches it back by its assigned ID, and checks the retrieved note's content and target type exactly match what was originally saved a moment earlier.
- **test_save_and_find_round_trips_created_at** — Confirms that the created_at timestamp on a note survives being written to and read back from storage without being altered or silently dropped. It saves a note with a specific creation timestamp, then retrieves it, and checks both the just-saved copy and the freshly fetched copy report that exact same timestamp value.
- **test_find_by_id_raises_for_an_unknown_note** — Confirms the storage layer correctly signals a missing record rather than returning empty or incorrect data when asked for something that doesn't exist. It looks up a clearly nonexistent note ID directly against the repository and checks that a record-not-found error is raised, the underlying condition the API turns into a 404 for clients.
- **test_find_by_filter_matches_on_author_id** — Confirms the storage layer can search notes by author, matching only records that belong to the requested staff member and no one else. It saves two notes under two different author IDs, then filters by one specific author, and checks exactly one note is returned and it belongs to the correct author.
- **test_update_persists_content_changes** — Confirms edits made to a note's content are actually written through to permanent storage rather than only existing briefly in memory. It saves a note, changes its content through the note object's own edit method, writes that change back through the repository's update call, then re-fetches the note and checks the new content actually stuck.
- **test_update_review_fields_writes_only_the_four_review_columns** — Confirms the review-attachment write path in storage is a narrow, additive update that touches only the four review-related fields, status, reviewer, timestamp, and comment, without disturbing the note's own content or authorship. It writes a review update, then re-fetches the note and checks the review fields changed while content and author_id remain untouched.
- **test_delete_soft_deletes_rather_than_hard_deleting** — Confirms that deleting a note doesn't actually erase it from the underlying data store, preserving it for audit and recovery purposes rather than losing it forever. It saves a note, deletes it through the repository, then inspects the raw stored record directly and checks it still exists but is now flagged with is_deleted set to true.
