# Application Service — Test Catalog

The Application Service manages a visa application's entire lifecycle — the 4-stage pipeline, client registration gate (signatures, invoices, coupons), case officer assignment, ART tribunal reviews, RFI and notification tracking, compliance checklists, and inbound-document matching — and this catalog covers all 49 tests (29 integration + 20 unit).

## Integration tests

### tests/integration/test_application_flow.py

- **test_create_application_with_valid_dynamic_fields** — Seeds a visa-type schema that allows a "course_name" field, then submits a new Student visa application with that field filled in. Confirms the system accepts it, generates an application ID starting with "AP-", starts the application at stage 1 of the pipeline, and stores the submitted field exactly as entered — proving new applications can be created correctly.
- **test_create_application_rejects_unknown_visa_type** — Attempts to create an application for a visa type that has never been registered in the system's schema catalog. The API is expected to refuse the request with a validation error rather than accept it, demonstrating that only known, configured visa types can be used to open new applications, preventing typos or unsupported categories.
- **test_create_application_rejects_unknown_dynamic_field** — Registers a visa-type schema that does not include a field called "bogus_field", then tries to submit an application carrying that unlisted field. The request is rejected with a validation error, confirming the service enforces each visa type's own approved field list and blocks unexpected or unsupported data from being saved onto an application record.
- **test_get_application_returns_what_was_created** — Creates an application, then immediately fetches it back by its ID. Checks that the record returned by the lookup matches the one just created, proving the service can reliably store an application and hand back the exact same record on request — a basic but essential guarantee for staff pulling up client cases.
- **test_get_unknown_application_returns_404** — Looks up an application ID that was never created ("AP-999999") and confirms the system responds with a clean "not found" error instead of crashing or returning misleading data. This protects staff from acting on a nonexistent case and confirms the lookup endpoint behaves predictably when given a bad or mistyped application reference.
- **test_update_dynamic_fields_merges_into_existing** — Creates an application with a "course_name" already filled in, then adds a new "campus" field afterward. Confirms both fields end up saved together rather than the new one overwriting the old, proving that updating an application's extra details is additive — so staff can fill in information gradually across multiple steps without losing earlier answers.
- **test_record_trn** — Records a Transaction Reference Number (TRN), the government-issued reference tying an application to its formal visa lodgement, against a freshly created application. Confirms the value is accepted and stored exactly as submitted, verifying the service correctly captures this key identifier that later drives stage progression and document-matching logic elsewhere in the pipeline.
- **test_record_outcome** — Submits a final decision outcome of "Grant" against an application and confirms the API stores and returns it correctly. This proves the service can record the ultimate result of a visa application — approved, refused, or otherwise — which is the piece of information case officers and clients care about most at the end of the process.
- **test_compliance_status_reflects_active_checklist_items** — Sets up an active compliance checklist item requiring "Form 956" to be uploaded, then asks a fresh application for its compliance status. Confirms that item shows up as required but not yet completed, proving the service can tell staff at a glance which mandatory documents or steps are still outstanding on a given case.
- **test_assign_case_officer** — Assigns a named case officer, "Pat Smith", to an application along with the date the case was received. Confirms the system creates a new assignment record with an ID starting "CO-" and stores the officer's name correctly, proving the service supports tracking which staff member is responsible for handling a given visa application.
- **test_advance_stage_beyond_client_registration_gate_is_rejected** — Calls the internal pipeline service directly to try advancing a brand-new application straight from stage 1 to stage 2, bypassing the normal gate checks. The system blocks this with an invalid-transition error, proving stage progression can only happen through the proper client-registration gate (signatures and invoice payment) and never by a shortcut, protecting process integrity.

### tests/integration/test_art_review_flow.py

- **test_initiate_and_decide_art_review** — Opens an Administrative Review Tribunal (ART) review on an application with a named decision maker, confirming it starts with no decision recorded yet. Then records a "Refused" decision with an appeal flagged as initiated, and confirms the outcome, appeal flag, and a decision timestamp are all saved — modeling the full lifecycle of a tribunal review.
- **test_list_reviews_for_application** — Initiates one ART review against an application, then requests the full list of reviews tied to that same application. Confirms exactly one review comes back, proving the service correctly tracks and retrieves the review history per application — important for case officers who need to see every tribunal review an application has gone through at a glance.
- **test_initiate_review_on_missing_application_returns_404** — Tries to start an ART review against an application ID that doesn't exist. Confirms the system responds with a "not found" error rather than silently creating an orphaned review record, proving the service validates that an application genuinely exists before letting anyone attach a tribunal review to it, protecting data integrity.

### tests/integration/test_client_registration_gate_flow.py

- **test_full_gate_flow_advances_application_to_stage_two** — Walks through the entire client-registration gate end to end: requesting an e-signature, receiving webhook confirmations for both the Form 956 and Client Agreement documents, checking the gate isn't satisfied until payment happens, creating an invoice, then confirming a payment webhook. Verifies the application only advances to stage 2, and its invoice flag is set, once every requirement is met.
- **test_redelivered_signature_webhook_is_idempotent** — Sends the exact same e-signature completion webhook twice in a row for the Form 956 document. Confirms both calls succeed but only a single document record is stored, proving the service safely tolerates duplicate webhook deliveries — a real-world necessity since external signature and payment providers commonly retry notifications, and duplicates must never create duplicate paperwork.
- **test_redelivered_payment_webhook_is_idempotent** — Creates an invoice, then sends the same payment-confirmation webhook for it twice. Confirms both requests return success without error, proving the payment side of the registration gate is also safe against duplicate notifications from the payment provider — preventing an application from being double-charged or double-processed if a webhook happens to be delivered more than once.
- **test_invalid_coupon_code_is_rejected** — Attempts to create a registration invoice using a coupon code ("NOPE") that does not exist in the system. Confirms the request is rejected with a "bad request" error rather than silently ignoring the invalid code or applying no discount, proving the billing logic actively checks coupon validity before letting it affect an invoice amount.
- **test_valid_coupon_applies_discount_and_gets_redeemed** — Seeds an active "SAVE10" coupon worth a 10% discount, then creates a $500 invoice using that code. Confirms the invoice correctly shows a $50 discount and a $450 final amount, and that the coupon's status flips to "redeemed" afterward — proving discounts are calculated correctly and coupons can't be reused once spent.

### tests/integration/test_health.py

- **test_health** — Calls the service's health-check endpoint and confirms it responds with a 200 success and a simple "status: ok" body. This is the most basic possible check that the Application Service is up and running, which matters because monitoring tools and load balancers rely on this exact response to know the service is alive.

### tests/integration/test_inbound_document_flow.py

- **test_process_matches_by_trn_and_creates_rfi_request** — Configures an RFI type tied to an incoming document type, creates an application with a known TRN, then feeds in an inbound document carrying that same TRN and a submission deadline. Confirms the document is automatically matched to the right application and an RFI request is auto-created from it, proving inbound document processing can self-file paperwork correctly.
- **test_process_with_no_trn_match_lands_in_manual_review_queue** — Feeds in an inbound document whose TRN doesn't match any known application. Confirms it's marked "unmatched" and shows up in the manual-review queue for staff to handle by hand, proving the system gracefully handles documents it can't auto-file instead of losing them or attaching them to the wrong client's case.
- **test_resolve_manually_marks_log_matched** — Takes a document that failed automatic TRN matching, then has a staff member manually resolve it by pointing it at the correct application. Confirms the log flips to "matched," records which application it now belongs to, and notes which staff member performed the fix, proving the manual-review safety net actually works end to end.
- **test_resolve_manually_on_missing_log_returns_404** — Attempts to manually resolve an inbound-document log using an ID that doesn't exist. Confirms the system responds with a "not found" error instead of crashing or silently succeeding, proving staff get clear, honest feedback when they try to act on a document log that isn't actually in the queue anymore.

### tests/integration/test_rfi_and_notification_flow.py

- **test_create_rfi_computes_reminder_date_from_lead_days** — Creates an RFI (Request for Information) request dated September 1st, 2026, with a submission deadline of September 15th. Confirms the system automatically flags a reminder as required and calculates the reminder date as September 12th, three days before the deadline, proving the service automatically schedules follow-up reminders so staff don't miss information deadlines.
- **test_create_rfi_with_unknown_type_returns_422** — Tries to create an RFI request using a type key that was never configured in the system. Confirms the request is rejected with a validation error, proving that RFI types — like Section 56 requests — must be explicitly set up in advance before they can be used, preventing staff from creating requests with made-up or misspelled categories.
- **test_mark_rfi_handled_excludes_it_from_open_list** — Creates an RFI request, then marks it as handled once the required information has been received. Confirms the "handled" flag is set to true and that the request disappears from the list of open RFIs for that application, proving staff have a reliable way to clear resolved information requests off their active to-do list.
- **test_create_notification_with_unknown_type_returns_422** — Attempts to create an application notification using a notification type, such as "bridging visa," that hasn't been registered in the system's configuration. Confirms the request is rejected with a validation error, proving notification categories must be predefined before use — keeping the set of notification types controlled and consistent rather than allowing arbitrary, unmanaged labels.
- **test_create_and_mark_notification_handled** — Creates a "bridging visa" notification on an application with extra details (an arrival time), confirming those details are saved as submitted. Then marks the notification as handled and confirms that flag updates, and checks the notification still appears in the application's full notification list — proving notifications can be created, resolved, and audited without disappearing from history.

## Unit tests

### tests/unit/test_application_pipeline_service.py

- **test_advance_stage_rejects_skipping_a_stage** — Directly tests the pipeline logic by trying to jump an application from stage 1 straight to stage 3, skipping stage 2 entirely. Confirms the service raises an invalid-transition error, proving the 4-stage pipeline enforces strict, sequential progression and can never let a case skip ahead, which keeps every application's paper trail consistent and auditable.
- **test_advance_stage_rejects_leaving_stage_one_without_the_gate_satisfied** — Sets up an application still sitting in stage 1 with no invoice created yet, then tries to advance it to stage 2. Confirms the service blocks the move with an invalid-transition error, proving stage 1 can only be exited once the client-registration gate — the signatures and invoice payment — has genuinely been completed, not just assumed.
- **test_advance_stage_allows_leaving_stage_one_once_gate_satisfied** — Sets up an application in stage 1 with the Form 956 signed, the client agreement signed, and the invoice created — every registration-gate requirement met. Confirms the service allows advancement to stage 2 and publishes a "stage_changed" event recording the move from stage 1 to 2, proving the pipeline both enforces and correctly signals legitimate stage progress.
- **test_advance_stage_rejects_leaving_stage_two_without_a_trn** — Sets up an application sitting in stage 2 with no Transaction Reference Number recorded, then tries to advance it to stage 3. Confirms the service raises an invalid-transition error, proving that a case can't move into the later, tribunal/decision-facing stages of the pipeline until its official government TRN has actually been logged against it.
- **test_advance_stage_allows_leaving_stage_two_with_a_trn** — Sets up an application in stage 2 that already has a TRN recorded, then advances it to stage 3. Confirms the move succeeds and the application's stage updates accordingly, proving that once the government reference number is on file, a case is free to progress into the next phase of its visa pipeline without further blockers.
- **test_advance_stage_rejects_reversing_a_stage** — Sets up an application already sitting in stage 3, then tries to move it backward to stage 2. Confirms the service raises an invalid-transition error, proving the pipeline is strictly one-directional — once a case has progressed, it can never be pushed back to an earlier stage, protecting the integrity and history of every application's progress record.

### tests/unit/test_document_match_strategy.py

- **test_match_returns_matched_for_a_single_trn_hit** — Feeds a TRN into the default document-matching strategy when exactly one application in the system carries that TRN. Confirms the match result comes back as "matched" and correctly identifies that specific application, proving the core matching logic used to auto-file inbound documents correctly links a document to its one true owning application.
- **test_match_returns_unmatched_for_no_hits** — Feeds a TRN into the matching strategy when no application in the system carries that reference number. Confirms the result comes back as "unmatched," proving the matching logic correctly recognizes when a document can't be tied to any known case, so it gets routed to manual review instead of being wrongly attached to the wrong file.
- **test_match_returns_unmatched_when_no_trn_in_payload** — Feeds an empty payload with no TRN at all into the matching strategy. Confirms the result is "unmatched" and, importantly, that the system never even bothers searching application records when there's no reference number to search by, proving the service avoids wasted or nonsensical lookups when incoming documents lack the one piece of data matching depends on.
- **test_match_returns_ambiguous_for_multiple_hits** — Feeds a TRN into the matching strategy when two separate applications both happen to carry that same reference number. Confirms the result comes back as "ambiguous" rather than guessing which one is correct, proving the service deliberately refuses to auto-file a document when there's a genuine conflict, forcing a human to resolve it instead of risking a wrong match.
- **test_factory_falls_back_to_default_strategy** — Asks the document-match strategy factory for a strategy tied to a document type it has no special handling registered for. Confirms the factory hands back the generic default matching strategy rather than failing, proving the system always has a sensible fallback for matching any document type, even ones nobody has configured special handling for yet.
- **test_factory_returns_registered_strategy_for_its_key** — Registers a special matching strategy under the key "SPECIAL_DOC" in the factory, alongside a generic default. Confirms asking for "SPECIAL_DOC" returns that specific strategy, while asking for any other document type still returns the default, proving the factory correctly routes each document type to its own custom matching logic when one has been defined.

### tests/unit/test_esignature_provider_client.py

- **test_verify_webhook_signature_accepts_a_correctly_signed_payload** — Builds a webhook signature header using the correct shared secret and the current timestamp, matching exactly how the real e-signature provider would sign an incoming request. Confirms the verification method accepts it as valid, proving legitimate webhook deliveries from the signature provider are correctly recognized and allowed to update application records like Form 956 uploads.
- **test_verify_webhook_signature_rejects_a_wrong_secret** — Signs a webhook payload using the wrong shared secret instead of the one the client actually trusts. Confirms signature verification fails, proving the service can detect and reject webhook calls that weren't genuinely produced by the real e-signature provider — a critical security control that stops attackers from forging signing-completion events to fraudulently unlock an application's registration gate.
- **test_verify_webhook_signature_rejects_a_tampered_payload** — Signs one payload correctly, then swaps in a different, tampered payload while reusing that original signature. Confirms verification fails, proving the signature check actually covers the content of the message and not just its header — so nobody can intercept a legitimate webhook and quietly alter its contents, such as which document type was actually signed.
- **test_verify_webhook_signature_rejects_a_stale_timestamp** — Signs a payload correctly but stamps it with a timestamp well past the allowed tolerance window, simulating an old, delayed, or replayed webhook. Confirms verification fails despite the signature itself being technically valid, proving the service also guards against replay attacks — an old, correctly-signed webhook can't be resent later to trigger actions it shouldn't still be allowed to trigger.
- **test_verify_webhook_signature_rejects_a_malformed_header** — Sends a signature header that isn't in the expected format at all ("not-a-valid-header") alongside an arbitrary payload. Confirms verification fails cleanly rather than crashing or throwing an unhandled exception, proving the service handles garbled or unexpected webhook input safely, which matters because externally-facing webhook endpoints must never be crashable by malformed or malicious input.

### tests/unit/test_schema_validator.py

- **test_validate_passes_for_allowed_fields** — Configures a visa type's schema to allow "course_name" and "campus" as dynamic fields, then validates a submission containing only "course_name". Confirms validation completes without raising any error, proving the schema validator correctly lets through data that's genuinely on the approved list for a given visa type rather than rejecting legitimate, well-formed submissions.
- **test_validate_rejects_unknown_field** — Configures a visa type's schema to only allow "course_name," then validates a submission that includes a field called "bogus" instead. Confirms the validator raises an unknown-dynamic-field error, proving the core validation rule at the heart of the application-creation process — that every dynamic field must be pre-approved for its visa type — works correctly at the unit level.
- **test_validate_rejects_unknown_visa_type** — Simulates looking up a schema for a visa type that returns nothing at all (no schema exists), then attempts to validate a submission against it. Confirms the validator raises an unknown-visa-type error rather than an unknown-field error, proving the two failure modes — bad visa type versus bad field — are distinguished correctly at the lowest level.
