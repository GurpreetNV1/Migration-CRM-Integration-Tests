# Application Service — Test Catalog

This service manages visa applications end to end — the 4-stage pipeline, ART tribunal reviews, RFI and notification tracking, case officer assignment, invoices/coupons, compliance checklists, and inbound-document matching — and this catalog covers 65 tests total (31 integration, 34 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — Confirms the service's basic health-check endpoint responds successfully. A plain GET request to /health returns HTTP 200 with a simple `{"status": "ok"}` body. This is the same kind of check load balancers and monitoring dashboards rely on to know the Application Service is alive and reachable before real traffic gets routed to it, so a demo audience can trust the service is genuinely running.

### tests/integration/test_art_review_flow.py

- **test_initiate_and_decide_art_review** — Seeds an application, then starts an ART (tribunal) review naming the decision-maker role, confirming the review is created with no decision recorded yet. It then records the tribunal's outcome as "Refused" with an appeal initiated, and checks the decision, the appeal flag, and a decided-at timestamp all come back correctly, proving the full review-to-decision lifecycle works end to end.
- **test_list_reviews_for_application** — After creating an application and initiating one ART review against it, this test fetches the list of reviews tied to that application and confirms exactly one comes back. It proves staff can reliably pull up the tribunal review history for a specific case, which matters when someone needs to check appeal status quickly during a client conversation or demo.
- **test_initiate_review_on_missing_application_returns_404** — Attempts to start an ART review against an application ID that was never created. The system correctly responds with a 404 Not Found rather than crashing or silently creating orphaned data, demonstrating that the service protects against staff accidentally logging a tribunal review under a case number that doesn't exist.

### tests/integration/test_client_registration_gate_flow.py

- **test_full_gate_flow_advances_application_to_stage_two** — Walks through the entire client-registration "gate" a new application must clear before progressing: requesting an e-signature, receiving webhook confirmations that both Form 956 and the Client Agreement were signed, checking the gate isn't yet satisfied because payment is outstanding, raising an invoice, confirming payment via webhook, and finally verifying the application automatically advances to stage 2 with the gate marked satisfied. It also checks that opening the application promotes the contact from Enquiry to Prospect immediately, and that both documents being signed further promotes the contact to Client, ahead of the full gate being satisfied.
- **test_signature_request_and_invoice_creation_each_schedule_a_followup_reminder** — Requests an e-signature on a fresh application and confirms a "reminder.schedule_requested" event fires for that application with an email delivery channel and a real future fire-at timestamp, then raises an invoice against the same application and confirms a second such reminder event fires. This proves both key registration-gate actions automatically queue a follow-up nudge through the Reminder Service, so outstanding signatures or unpaid invoices don't quietly go stale without anyone being prompted to chase them.
- **test_redelivered_signature_webhook_is_idempotent** — Sends the exact same signature-completion webhook twice in a row, simulating a provider retry or duplicate delivery. Both calls return success, but the underlying document record is only created once, proving the service won't double-file the same signed document if an external e-signature provider redelivers a webhook it already sent, which happens often in real integrations.
- **test_handle_signature_completed_resumes_after_a_partial_failure** — Simulates a real partial-failure scenario where a signed document was saved but the Application's "form_956_uploaded" flag update never completed, since the two are separate writes rather than one atomic transaction. Replaying the same signature-completion event resumes and finishes the interrupted work, restoring the flag without creating a second copy of the document. This proves a naive "already processed" check can't leave the registration gate permanently stuck if a prior attempt only got halfway.
- **test_redelivered_payment_webhook_is_idempotent** — Creates an invoice, then sends the identical payment-confirmation webhook to the service twice in a row. Both requests succeed without error, showing that a duplicate payment notification — a common real-world occurrence with payment providers — cannot accidentally double-process or double-count a single client payment against the same invoice.
- **test_invalid_coupon_code_is_rejected** — Tries to raise an invoice using a coupon code that doesn't exist anywhere in the system. The request is rejected with a 400 error instead of silently applying no discount or crashing, proving staff and clients can't accidentally, or deliberately, apply a bogus discount code to shrink an invoice amount.
- **test_valid_coupon_applies_discount_and_gets_redeemed** — Seeds an active 10%-off coupon, then raises a $500 invoice using that code. The response shows a correct $50 discount bringing the total to $450, and afterward the coupon's status flips to "redeemed" in storage, proving the discount math is accurate and a coupon can't quietly be reused once it's already been spent.

### tests/integration/test_application_flow.py

- **test_create_application_with_valid_dynamic_fields** — Seeds a visa-type schema allowing a "course_name" field, then creates a new application supplying that field. The response confirms the new application gets an "AP-" prefixed ID, starts at stage 1, and stores the dynamic field exactly as submitted, proving the intake process correctly creates and tracks a brand-new visa application from the very first step.
- **test_create_application_rejects_unknown_visa_type** — Attempts to create an application for a visa type that was never configured in the system. The request is rejected with a 422 validation error, proving staff cannot accidentally open a case under a visa category the business hasn't set up, which would otherwise leave a case with undefined rules and unclear requirements.
- **test_create_application_rejects_unknown_dynamic_field** — Seeds a schema for a visa type but then tries to submit a dynamic field name that isn't on that schema's allowed list. The service returns a 422 error, proving each visa type enforces its own specific set of intake fields and rejects extraneous or mistyped data rather than silently storing whatever is sent.
- **test_get_application_returns_what_was_created** — Creates an application and then immediately fetches it back by ID, confirming the returned record's application ID matches what was just created. This is a basic but essential proof that data written during intake is durably retrievable afterward for case lookups, status checks, and reporting later on.
- **test_get_unknown_application_returns_404** — Requests an application record using an ID that was never created. The service correctly responds 404 Not Found instead of returning empty or malformed data, proving staff get a clear, honest signal when they look up a case number that doesn't exist rather than a confusing blank or broken result.
- **test_update_dynamic_fields_merges_into_existing** — Creates an application with a "course_name" value already set, then submits an update adding a new "campus" field. The final record contains both the original and the new field together, proving that updating dynamic fields merges new information into a case rather than overwriting or discarding previously captured details.
- **test_record_trn** — Creates an application and records a Transaction Reference Number (TRN) against it, then confirms the TRN is saved and returned exactly as submitted. This proves the service can attach the official government-issued reference number to a case, a required step before an application can progress past the early stages of the pipeline.
- **test_record_outcome** — Records a final outcome of "Grant" against an existing application and confirms it comes back stored correctly. This proves the service can capture the ultimate result of a visa application — arguably the single most important piece of information for both the client and the firm's own case reporting and statistics.
- **test_compliance_status_reflects_active_checklist_items** — Seeds an active compliance checklist item ("Form 956") and creates a fresh application, then checks its compliance status. The response shows that checklist item present and marked as not yet completed, proving the system automatically surfaces outstanding document requirements for a case instead of requiring staff to track them manually on a spreadsheet.
- **test_assign_case_officer** — Assigns a named case officer ("Pat Smith") with a received date to an application, and confirms the response includes a "CO-" prefixed assignment ID along with the officer's name. This proves the service can formally record which staff member owns a case, supporting accountability and workload tracking across the immigration team.
- **test_advance_stage_beyond_client_registration_gate_is_rejected** — Directly calls the internal pipeline service to try advancing a brand-new application straight to stage 2 before its registration gate (signed forms, paid invoice) has been satisfied. The call raises an InvalidStageTransitionError, proving stage progression can't be forced or bypassed through internal logic even when no public API endpoint exposes such a shortcut.

### tests/integration/test_inbound_document_flow.py

- **test_process_matches_by_trn_and_creates_rfi_request** — Configures an "S56" RFI document type, creates an application carrying a specific TRN, then feeds in an inbound document that carries that same TRN plus a submission deadline. The processor automatically matches it to the correct application and creates a corresponding RFI request, proving incoming tribunal correspondence can be auto-linked to the right case and turned into an actionable task without manual triage.
- **test_process_with_no_trn_match_lands_in_manual_review_queue** — Feeds in an inbound document referencing a TRN that matches no application anywhere in the system. Rather than failing or being discarded, the document is logged as "unmatched" and shows up in the manual-review queue, proving unrecognized incoming paperwork is never silently lost and instead gets flagged for a human staff member to sort out by hand.
- **test_resolve_manually_marks_log_matched** — Takes a document that landed in the unmatched queue and has a staff member manually resolve it by linking it to the correct application. The log updates to "matched" status, records the correct application ID, and records which staff member performed the resolution, proving the manual fallback process works cleanly when automatic TRN matching fails to find a case.
- **test_resolve_manually_on_missing_log_returns_404** — Tries to manually resolve an inbound-document log entry using an ID that doesn't exist. The service returns 404 Not Found instead of crashing or creating a phantom record, proving staff get a clear, honest error if they reference the wrong log entry while triaging the unmatched-documents queue during their daily workflow.

### tests/integration/test_rfi_and_notification_flow.py

- **test_create_rfi_computes_reminder_date_from_lead_days** — Creates an RFI (request for information) with a submission deadline of September 15, 2026, and checks the system automatically computes a reminder date of September 12 — three days earlier, the default lead time — flagging the reminder as required. This proves staff get proactively reminded ahead of an information-request deadline instead of having to track due dates manually by memory.
- **test_create_rfi_with_unknown_type_returns_422** — Attempts to create an RFI request using a request type that was never configured in the system. The service rejects it with a 422 validation error, proving that only recognized, business-approved categories of information requests, like a Section 56 notice, can be logged against a case rather than arbitrary free-text types.
- **test_mark_rfi_handled_excludes_it_from_open_list** — Creates an RFI request, then marks it as handled and confirms the "handled" flag comes back true in the response. It then checks the list of open RFI requests for that application and confirms the handled one no longer appears there, proving completed information requests correctly drop off staff's active to-do list once resolved.
- **test_create_notification_with_unknown_type_returns_422** — Tries to create an application notification using a notification type that isn't configured, unlike a recognized type such as "bridging visa." The service rejects the request with a 422 error, proving notifications are restricted to a controlled, pre-approved set of categories rather than accepting free-form or accidental entries from any source.
- **test_create_and_mark_notification_handled** — Creates a "bridging visa"-type notification with arrival-time details attached to an application, confirms those details are stored exactly as submitted, then marks the notification handled and confirms that flag flips to true. Finally it checks the notification still appears in the application's notification list, proving history is preserved even after a notification is resolved.

## Unit tests

### tests/unit/test_application_pipeline_service.py

- **test_advance_stage_rejects_skipping_a_stage** — Sets up an application sitting at stage 1 and attempts to jump it straight to stage 3, skipping stage 2 entirely. The service raises an InvalidStageTransitionError, proving the pipeline enforces that every application must pass through each stage in strict order and can never leapfrog a step, no matter how the internal request is made.
- **test_advance_stage_rejects_leaving_stage_one_without_the_gate_satisfied** — Sets up a stage-1 application where no invoice has been created yet, then attempts to advance it to stage 2. The service raises an InvalidStageTransitionError, proving an application can't leave the initial client-registration stage until the required registration gate — signed forms and payment — is actually completed, protecting the firm from working unpaid cases.
- **test_advance_stage_allows_leaving_stage_one_once_gate_satisfied** — Sets up a stage-1 application with Form 956, the client agreement, and an invoice all marked complete, then advances it to stage 2. The move succeeds, and the test confirms an "application.stage_changed" event was published for the Audit Service to record, proving both the business rule and the audit trail work correctly once every gate requirement is genuinely met.
- **test_advance_stage_rejects_leaving_stage_two_without_a_trn** — Sets up a stage-2 application that has no Transaction Reference Number recorded, then tries to advance it to stage 3. The service blocks the move with an InvalidStageTransitionError, proving the pipeline requires the official government TRN to be captured before a case can progress into its next phase of processing.
- **test_advance_stage_allows_leaving_stage_two_with_a_trn** — Sets up a stage-2 application that already has a TRN recorded, then advances it to stage 3. The transition succeeds and the returned application reflects the new stage, proving that once the TRN prerequisite is genuinely met, the pipeline correctly lets a case move forward without throwing up any additional blockers.
- **test_advance_stage_rejects_reversing_a_stage** — Sets up an application already sitting at stage 3 and attempts to move it backward to stage 2. The service raises an InvalidStageTransitionError, proving the pipeline is strictly one-directional and a case can never be accidentally, or deliberately, rolled back to an earlier stage once it has already progressed forward.
- **test_create_application_promotes_the_contact_to_prospect** — Creates a new application for a contact and confirms the service calls through to the User Service to transition that contact's lifecycle stage to "Prospect." This proves opening a real case automatically upgrades a person's status in the CRM from a mere enquiry to an active prospect, without staff needing to remember to do it themselves.
- **test_create_application_survives_a_lifecycle_transition_failure** — Simulates the User Service call that promotes a contact to Prospect throwing a runtime error, then confirms application creation still succeeds and returns the saved application. This proves a transient failure or hiccup in a downstream service can't block a case from being opened, since the Application record itself is the more critical piece of data to get saved reliably.

### tests/unit/test_boldsign_webhook_adapter.py

- **test_process_event_downloads_and_records_both_documents_on_completed** — Feeds a "Completed" BoldSign webhook event referencing a document ID tied to a seeded application, and confirms the adapter downloads the signed ZIP, recognizes both the Form 956 and Client Agreement PDFs inside it, and calls the registration-gate service twice — once per document — with the correct application ID, provider reference, and a real Drive file ID for each. This proves the core webhook-to-gate-update pathway correctly turns one signing-completion notification into both expected document records.
- **test_process_event_accepts_uppercase_event_type** — Sends the same completed-signature webhook but with the event type spelled "COMPLETED" in all caps instead of BoldSign's usual casing, and confirms it's still recognized and processed exactly as before. This protects against the integration silently breaking if the external provider's casing conventions vary between requests or change over time.
- **test_process_event_accepts_document_key_instead_of_data** — Sends a webhook payload using a "document" key instead of the expected "data" key to carry the document ID, and confirms the adapter still finds it and processes the event normally. This proves the adapter tolerates a known real-world variation in BoldSign's payload shape rather than being brittle to a single exact format.
- **test_process_event_ignores_a_non_completed_event** — Feeds the adapter a "Sent" event instead of "Completed," representing a document that has merely been dispatched for signing but not yet finished. Confirms no call is made to record a completed signature, proving the service only reacts to genuine completion notifications and ignores the other lifecycle events BoldSign also sends.
- **test_process_event_logs_and_stops_when_document_id_missing** — Sends a "Completed" event with an empty data payload carrying no document ID at all, and confirms the adapter simply stops without calling the gate service or raising an exception. This ensures a malformed webhook can't crash the endpoint or trigger a bogus signature-completion call with missing information.
- **test_process_event_logs_and_stops_when_no_application_matches_the_reference** — Sends a completed-signature webhook referencing a document ID that doesn't correspond to any application's pending signature reference, and confirms the adapter safely stops without recording anything. This guards against stray or unrecognized webhook traffic ever being attached to the wrong case, or crashing the service.
- **test_process_event_logs_and_stops_when_no_recognizable_pdf_is_in_the_zip** — Makes the signed-document download return a ZIP containing only an unrelated file name that doesn't match either expected document type, and confirms the adapter records nothing rather than guessing which document it might be. This prevents a corrupted or unexpected file from ever being filed under the wrong document type.
- **test_process_event_still_records_whichever_pdf_it_does_recognize** — Makes the signed-document download return a ZIP containing only the Form 956 PDF instead of both expected files, and confirms the adapter still records that one document rather than failing the whole operation because the Client Agreement was missing. This proves the service processes what it can identify instead of being all-or-nothing when a signing session comes back incomplete.
- **test_process_event_does_not_raise_when_the_download_itself_fails** — Makes the signed-document download itself raise a RuntimeError, simulating BoldSign being unreachable, and confirms the adapter absorbs the failure without recording anything and without crashing the webhook handler. This keeps a downstream outage from taking down the Application Service's own webhook processing.

### tests/unit/test_document_match_strategy.py

- **test_match_returns_matched_for_a_single_trn_hit** — Mocks the application repository to return exactly one application when searched by TRN, then runs the default matching strategy against a document payload containing that TRN. The result is a "matched" status pointing to the correct application ID, proving the core auto-matching logic correctly links an incoming document when there's exactly one candidate case in the system.
- **test_match_returns_unmatched_for_no_hits** — Mocks the repository to return zero applications for a given TRN search, then runs the matching strategy against that TRN. The result comes back as "unmatched," proving that when an inbound document's reference number doesn't correspond to any known case, the system correctly flags it as unmatched instead of guessing or throwing an error.
- **test_match_returns_unmatched_when_no_trn_in_payload** — Runs the matching strategy against a completely empty document payload with no TRN field at all. The result is "unmatched," and critically the repository's search method is never even called, proving the system safely skips a doomed lookup rather than wasting a database query when there is clearly nothing to match against.
- **test_match_returns_ambiguous_for_multiple_hits** — Mocks the repository to return two different applications for the same TRN search, then runs the matching strategy. The result comes back as "ambiguous" rather than arbitrarily picking one, proving the system recognizes when a reference number isn't unique enough to safely auto-match and defers the decision to a human instead of guessing wrong.
- **test_factory_falls_back_to_default_strategy** — Builds a document-match strategy factory with no registered document-type-specific strategies at all, then asks it for a strategy to handle an arbitrary document type. It returns the configured default strategy, proving the factory always has a sensible fallback so no incoming document type is ever left with no matching logic whatsoever.
- **test_factory_returns_registered_strategy_for_its_key** — Registers a special-case matching strategy under the key "SPECIAL_DOC" in the factory alongside a default strategy. Asking the factory for "SPECIAL_DOC" returns that specific strategy, while asking for any other key returns the default, proving it correctly routes each document type to its own custom matching logic whenever one has been defined for it.

### tests/unit/test_esignature_provider_client.py

- **test_verify_webhook_signature_accepts_a_correctly_signed_payload** — Builds a webhook payload and signs it with the correct shared secret and a current timestamp, exactly as the real e-signature provider would when notifying the system that a document was signed. The verification function returns true, proving the service correctly accepts genuine, unaltered webhook notifications from the trusted signing provider.
- **test_verify_webhook_signature_rejects_a_wrong_secret** — Signs a webhook payload using an incorrect secret instead of the one actually shared with the e-signature provider. Verification returns false, proving the service would reject a forged webhook sent by an attacker who doesn't know the real secret, protecting against fake "document signed" notifications being trusted.
- **test_verify_webhook_signature_rejects_a_tampered_payload** — Signs one payload correctly but then submits a different, altered payload alongside that original signature. Verification returns false, proving that if someone intercepts and modifies a webhook in transit, the signature mismatch is detected and the tampered request is rejected instead of silently trusted as legitimate.
- **test_verify_webhook_signature_rejects_a_stale_timestamp** — Signs a payload correctly but stamps it with a timestamp well past the allowed tolerance window, more than a minute beyond the limit. Verification returns false, proving the service rejects old webhook requests, which prevents a captured, genuinely valid signature from being replayed later by an attacker.
- **test_verify_webhook_signature_rejects_a_malformed_header** — Submits a webhook signature header ("not-a-valid-header") that doesn't follow the expected HMAC format at all, and confirms verification simply returns false rather than throwing an unhandled exception. This proves the service fails safely and predictably when it receives garbled or unexpected webhook input, instead of crashing the endpoint outright and potentially exposing an internal error to an outside caller.

- **test_upsert_creates_a_row_when_none_exists** — Upserts a compliance-checklist status (Form 956 uploaded, marked complete) for an application that has no existing compliance rows at all, and confirms it's saved as completed and that exactly one row now exists for that application. This proves the update-in-place behavior above is scoped correctly to each specific checklist item, not the whole application, so a case's compliance checklist can track several requirements independently.
