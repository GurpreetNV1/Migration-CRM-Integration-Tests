# Reminder Service — Test Catalog

The Reminder Service lets staff schedule manual reminders or lets other services request automated ones against a Contact, Application, or Task, then periodically sweeps for due reminders and fires them out through a delivery channel like email, and this catalog covers 65 tests in total (10 integration, 55 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — Confirms the service exposes a working health-check endpoint that returns HTTP 200 with a simple `{"status": "ok"}` body. This is the basic signal that the service is alive and reachable, which every monitoring tool, load balancer, and deployment pipeline relies on before routing real traffic to it.

### tests/integration/test_reminders_flow.py

- **test_create_manual_reminder_against_a_contact** — Creates a reminder against a Contact with a future fire time and an email delivery channel through the real HTTP API, confirming a 201 response where the reminder ID is prefixed "RM-", the source is recorded as "manual," and the status starts as "pending." This proves staff can successfully schedule a personal reminder tied to a specific person in the CRM.
- **test_list_reminders_filters_by_target** — Creates two separate reminders against two different Application targets, then queries the reminder list filtered to just one specific target type and ID, confirming exactly one reminder comes back and it's the matching one. This proves staff or another screen in the CRM can pull up only the reminders relevant to one particular Contact, Application, or Task instead of wading through every reminder in the system.
- **test_create_manual_reminder_against_a_task_is_rejected** — Attempts to manually create a reminder targeting a Task and confirms the API rejects it with a 422 validation error. This enforces the business rule that reminders against Tasks can only be generated automatically by the system, never created directly by staff, preventing a category of reminder that's meant to be system-driven from being created by hand.
- **test_create_manual_reminder_with_a_past_fire_at_is_rejected** — Attempts to schedule a manual reminder with a fire time set in the past (the year 2020) and confirms the API responds with 422. This stops staff from accidentally (or pointlessly) scheduling a reminder that would already be overdue the moment it's created, which would never make sense for a manually-set reminder.
- **test_get_reminder_returns_what_was_created** — Creates a reminder through the API and then retrieves it by its ID, confirming the fetched reminder's ID matches what was originally created. This proves reminders can be reliably looked up after creation, which underpins any reminder detail view or confirmation screen in the CRM.
- **test_get_unknown_reminder_returns_404** — Requests a reminder ID ("RM-999999") that was never created through the real HTTP API and confirms the response comes back as 404 rather than a 500 error or an empty success. This ensures a clean, predictable "not found" signal reaches staff or another integrating system whenever they look up a reminder that genuinely doesn't exist.
- **test_cancel_reminder_returns_204_and_removes_it** — Creates a reminder, then cancels it with a stated reason through the delete endpoint, confirming the API returns 204 and that the reminder can no longer be fetched afterward (returns 404). This proves staff can call off a reminder that's no longer needed and that it's genuinely removed from the active pending list, not just marked in a way that still shows up.
- **test_cancelling_an_unknown_reminder_is_a_no_op_not_an_error** — Attempts to cancel a reminder ID that doesn't exist and confirms the API still returns a success response (204) rather than an error. This makes the cancel operation safe to call repeatedly or defensively without needing to first check whether the reminder still exists, simplifying integration for other services.
- **test_firing_sweep_fires_a_due_reminder_end_to_end** — Creates a reminder due one second in the future, then directly triggers the periodic sweep as of two seconds later, confirming at least one reminder was fired and that the reminder is no longer retrievable afterward (having moved out of the pending list). This proves the full real-world scenario: a scheduled reminder actually gets delivered and cleared once its time arrives, which is the entire point of the service.

## Unit tests

### tests/unit/test_reminder_creation_service.py

- **test_create_from_manual_request_succeeds_and_publishes_created_event** — Creates a manual reminder against a valid Contact target with a future fire time, confirming the reminder is saved, correctly attributed to the requesting staff member, and that a "reminder.created" event is published. This proves the central logic for a normal, successful manual reminder request works correctly end to end at the business-logic level.
- **test_create_from_manual_request_rejects_a_task_target** — Confirms that requesting a manual reminder against a Task target raises an "invalid target" error at the business-logic layer, before anything is ever saved to storage. This is the underlying rule enforcement behind the API's 422 rejection at the HTTP layer, guaranteeing Task-targeted reminders can only ever be produced through the automated event path, never typed in directly by staff.
- **test_create_from_manual_request_rejects_a_past_fire_at** — Confirms that requesting a manual reminder with a fire time set in the past raises an "invalid fire-at" error at the business-logic layer and that nothing gets persisted to storage as a result. This guarantees every staff-created reminder always represents a genuinely future event, never something that would already be overdue the instant it's created, which would make no practical sense.
- **test_create_from_manual_request_rejects_a_naive_fire_at** — Confirms that a fire time provided without timezone information (a "naive" timestamp) is rejected with an "invalid fire-at" error rather than being silently accepted and possibly misinterpreted. This prevents subtle bugs where a reminder could fire hours early or late due to ambiguous timezone handling, which matters greatly for something time-sensitive like a reminder.
- **test_create_from_manual_request_rejects_an_unparseable_fire_at** — Confirms that a completely invalid, non-date string passed as the fire time is rejected with an explicit "invalid fire-at" error rather than causing an unhandled crash deep inside date-parsing logic. This ensures malformed input arriving from a client is caught early and reported clearly, rather than producing a confusing internal server error with no useful explanation.
- **test_create_from_automated_event_allows_a_task_target_with_no_future_check** — Confirms that reminders created via the automated event pathway can target a Task and can even have a fire time in the past, without being rejected, and that no staff ID is attached since no human requested it. This proves the automated and manual creation paths intentionally follow different rules, since system-generated reminders (e.g. "this task is now overdue") legitimately need to reference already-past moments.
- **test_cancel_delegates_to_repository_and_publishes_cancelled_event** — Cancels a reminder with a stated reason and confirms the repository's cancellation method is called with the right reminder ID, and that a "reminder.cancelled" event is published carrying both the reminder ID and the cancellation reason. This proves cancellations are properly persisted and broadcast for auditing, not just silently accepted.

### tests/unit/test_reminder_event_consumer.py

- **test_on_message_schedules_a_reminder_for_a_registered_event_type** — Feeds a "reminder.schedule_requested" event to the consumer and confirms it correctly triggers automated reminder creation with the right target type, target ID, and delivery channel extracted from the event. This proves other services in the CRM can request a reminder be scheduled on their behalf simply by publishing an event, without needing direct API access.
- **test_on_message_accepts_a_json_string_payload** — Feeds the consumer a "reminder.schedule_requested" event serialized as a raw JSON string, exactly as it would arrive over a real message queue, rather than a pre-parsed Python dictionary, and confirms it still correctly triggers automated reminder creation. This proves the consumer's message handling matches how events actually arrive from real production messaging infrastructure, not just how they look in a unit test.
- **test_on_message_defaults_delivery_channel_when_absent** — Sends a scheduling event with the delivery-channel field entirely removed from its payload, then confirms the consumer defaults the resulting reminder to "email" rather than failing outright or leaving the channel blank. This ensures every automatically-created reminder always has a sensible, working delivery method even when the triggering upstream event didn't explicitly specify one.
- **test_on_message_ignores_an_unregistered_event_type** — Sends the consumer an event type with no matching scheduling rule configured ("contact.created" instead of "reminder.schedule_requested") and confirms neither is a reminder created nor is any event published in response. This proves the consumer safely and quietly ignores irrelevant traffic on the shared message bus instead of reacting to every single event that happens to flow past it.
- **test_on_message_routes_a_cancel_event_to_cancel** — Sends a "reminder.cancel_requested" event carrying a reminder ID and reason, and confirms the consumer correctly routes it to the cancellation logic with those exact values. This proves other services can cancel a previously-scheduled reminder (e.g. because the underlying task was completed early) purely through the event system.
- **test_on_message_skips_a_cancel_event_missing_reminder_id** — Sends a "reminder.cancel_requested" event that's missing the reminder ID it's supposed to identify, and confirms the consumer does not attempt any cancellation, instead publishing a "reminder.auto_creation_skipped" warning event to record the incident. This protects against a malformed cancel request either silently doing nothing with no trace, or crashing the service outright on bad upstream data.
- **test_on_message_skips_and_publishes_a_warning_for_an_invalid_target** — Simulates the underlying reminder creation failing because the target type is invalid, and confirms the consumer catches this and publishes a "reminder.auto_creation_skipped" warning rather than letting the error propagate. This keeps the service resilient to bad or unexpected upstream event data while preserving an audit trail of what was skipped and why.
- **test_on_message_skips_a_malformed_event_missing_a_required_field** — Removes the required fire-at field from an otherwise valid, qualifying scheduling event and confirms the consumer skips reminder creation entirely, publishing a "reminder.auto_creation_skipped" warning event instead of proceeding with incomplete data. This prevents partial or corrupted upstream event data from ever resulting in a broken or incorrectly-timed reminder.
- **test_on_message_schedules_a_reminder_from_a_real_kafka_envelope** — Feeds the consumer a fully-wrapped Kafka audit envelope, the same shape the Application Service's real event publisher actually sends (topic under "action," business fields nested inside "detail_json"), rather than the flatter shape used elsewhere in this file, and confirms it still correctly triggers automated reminder creation with the right target type, ID, and fire time. This proves the consumer works against the real on-the-wire message format produced by upstream services, not just a simplified stand-in shape.
- **test_on_message_handles_an_undeserializable_payload_without_raising** — Feeds the consumer a plain string ("not valid json") that fails to parse as JSON at all, and confirms it doesn't crash but instead publishes a "reminder.auto_creation_skipped" warning event whose reason explicitly notes the deserialization failure. This proves the service can survive completely garbled input arriving from the message queue without going down or losing visibility into what happened.

### tests/unit/test_periodic_sweep_runner.py

- **test_run_forever_calls_sweep_fn_repeatedly_until_stopped** — Starts the periodic sweep runner on a very short interval (0.01 seconds) in a background thread, lets it run briefly, then stops it, confirming the sweep function was called multiple times and the thread cleanly exits. This proves the mechanism that repeatedly checks for due reminders on a schedule actually loops correctly and can be shut down cleanly, which is the heartbeat driving all automated reminder delivery.
- **test_stop_before_any_interval_elapses_prevents_any_call** — Starts the sweep runner with a long 60-second interval, then immediately stops it before that interval could ever elapse, confirming the sweep function was never called even once. This proves the runner responds promptly to a stop signal rather than being stuck waiting out its first interval, which matters for fast, clean shutdowns.

### tests/unit/test_notification_channel.py

This validates the basic email delivery mechanism actually used to notify staff or clients whenever a scheduled reminder comes due.
- **test_in_app_channel_send_succeeds_and_records_it** — Sends a reminder through the in-app notification channel (as opposed to email) and confirms the outcome reports success while the channel's internal sent-items list grows to exactly one entry. This proves the alternate, non-email delivery path also works correctly on its own, giving the system real flexibility in how a reminder actually reaches its recipient.
- **test_factory_resolves_a_registered_channel** — Registers a specific email-channel instance with the notification channel factory, then asks the factory for the "email" channel and confirms it hands back that exact same instance rather than a new or different one. This proves the routing mechanism correctly connects a reminder's chosen delivery method string to the one right underlying sending implementation.
- **test_factory_rejects_an_unregistered_channel** — Sets up a factory with no channels registered at all, then asks it for an "sms" channel and confirms it raises a clear "unsupported channel" error rather than silently failing, returning nothing, or sending through some unrelated channel by mistake. This prevents reminders from ever being lost or misdelivered because of a typo or a delivery method that was never actually configured.

### tests/unit/test_reminder_target_validator.py

- **test_validate_manual_target_accepts_contact** — Confirms that passing "Contact" to the manual-target validator succeeds and returns the corresponding Contact target-type value rather than raising any error. This is one half of the core rule defining exactly which kinds of records staff are allowed to set a personal, manually-created reminder against in the first place.
- **test_validate_manual_target_accepts_application** — Confirms that passing "Application" to the manual-target validator succeeds and returns the corresponding Application target-type value without raising an error, exactly as "Contact" does. This extends the same manual-reminder capability to visa/immigration applications, not just contacts, matching how staff actually work day-to-day across both kinds of CRM records.
- **test_validate_manual_target_rejects_task** — Confirms that passing "Task" to the manual-target validator explicitly raises an "invalid target" error rather than being accepted. This enforces the documented business rule that Task-linked reminders must always be system-generated from an automated event, never created directly by a staff member typing into a form, keeping that entire category fully automated.
- **test_validate_manual_target_rejects_an_unknown_type** — Confirms that a completely unrecognized target type ("Ticket," which this service doesn't own or know about) passed to the manual-target validator is also rejected with an "invalid target" error. This ensures the validator fails safely and predictably on any target type it doesn't explicitly recognize, rather than accidentally letting something unsupported slip through.
- **test_validate_automated_target_accepts_task** — Confirms that on the automated (event-driven) reminder path, "Task" is accepted as a valid target type. This is the counterpart rule to the manual-path rejection above, showing that Tasks can only get reminders through the automated route, which this test confirms is open to them.
- **test_validate_automated_target_rejects_an_unknown_type** — Confirms that passing an unrecognized target type ("Ticket") to the automated-path validator also raises an "invalid target" error, just as it does on the manual path. This ensures automated reminder requests arriving from other services via events are held to the same "known target types only" discipline as manual ones, even though the automated path's allowed list of target types is different.

### tests/unit/test_reminder_firing_sweep.py

- **test_run_sweep_only_fires_reminders_that_are_actually_due** — Sets up one reminder due now and another due months in the future, runs the sweep, and confirms only the due one is actually fired while the future one is left untouched and removed from the pending list. This is the central correctness guarantee of the whole service: the sweep must never fire a reminder early, only exactly when its scheduled time has arrived.
- **test_run_sweep_appends_history_for_every_evaluated_reminder** — Runs the sweep against a single due reminder and confirms a history record is written recording its final status as "sent." This proves every reminder the sweep processes leaves a permanent record of what happened to it, which matters for auditing and for staff to confirm a reminder actually went out.
- **test_run_sweep_marks_a_failed_delivery_as_failed_without_removing_it** — Simulates the delivery channel reporting a failure when trying to send a due reminder, and confirms the sweep records it as failed rather than sent, and critically does not remove it from the pending list. This ensures a reminder that failed to deliver (e.g. an email provider outage) isn't silently lost, but stays available to potentially retry or be investigated.
- **test_run_sweep_continues_after_a_channel_exception** — Sets up two due reminders where the delivery channel throws an unexpected error on the second one, and confirms the sweep still successfully evaluates both, firing the first and marking the second as failed, rather than the whole sweep crashing. This proves one bad or broken delivery attempt can't take down the entire batch of reminders due at that moment, which is critical for reliability at scale.
- **test_run_sweep_publishes_one_batched_event_for_the_whole_sweep** — Runs the sweep over a single due reminder and confirms exactly one "reminder.fired_batch" event is published for the entire run rather than separate events per reminder. This shows the sweep reports its results as one consolidated batch event, which is more efficient for downstream systems consuming sweep activity.
- **test_run_sweep_publishes_nothing_when_no_reminder_is_due** — Runs the sweep when the only reminder present isn't due yet, confirming zero reminders are evaluated, no history is written, and no event is published at all. This proves the sweep is quiet and inert when there's genuinely nothing to do, avoiding noisy or misleading empty events on every scheduled run.

This proves every event this service emits carries complete audit information that downstream systems like the Audit Service require to function correctly.
- **test_publish_falls_back_to_event_type_when_no_reminder_id_exists** — Publishes a "reminder.auto_creation_skipped" event, which never has a reminder ID since no reminder was actually created, and confirms the envelope substitutes the original event type as the target ID instead of leaving it empty. This prevents the Audit Service from silently discarding these important skip/warning events, which it does whenever a target ID is blank.
- **test_fired_batch_explodes_into_one_envelope_per_reminder** — Publishes a single "reminder.fired_batch" event containing two reminders, and confirms it results in two separate, correctly-attributed messages being sent (one per reminder ID), rather than one message with no clear target ID. This ensures the audit trail can track each individual reminder's outcome even though the sweep reports them together internally as one batch.
- **test_fired_batch_with_no_reminders_sends_nothing** — Publishes a "reminder.fired_batch" event whose payload contains a completely empty list of reminders, and confirms absolutely nothing is sent out to the underlying message broker as a result. This prevents pointless, empty audit events from being generated purely because a scheduled sweep run happened to find zero reminders actually due to fire.
- **test_envelope_is_json_serializable** — Publishes a "reminder.created" event through the Kafka publisher and confirms the complete envelope it hands off, including its event ID, source service, target, and timestamp, can be converted to JSON without raising any error. This is a basic sanity guarantee that messages this service produces won't silently break the downstream Kafka-based event pipeline due to a non-serializable field slipping in.

### tests/unit/test_reminder_repository.py

- **test_add_pending_assigns_ids** — Saves a brand-new reminder through the repository's add-to-pending method and confirms exactly one reminder comes back with a non-empty generated ID (the real Data Gateway Service allocates an "RM-000001"-style ID; this in-memory test double only guarantees an ID is assigned, not that specific format). This proves every reminder gets a real identifier the moment it's created and added to the pending queue, which every later lookup or status update depends on.
- **test_get_by_id_returns_what_was_saved** — Saves a new reminder through the repository, then retrieves it back by its generated ID, confirming the fetched record's target contact ID exactly matches what was originally saved. This validates the basic read/write reliability of reminder storage on its own, independent of anything happening at the HTTP or sweep layers above it.
- **test_get_by_id_raises_for_an_unknown_reminder** — Confirms that looking up a reminder ID ("RM-999999") that was never actually saved raises a clear "record not found" error rather than returning nothing or crashing unexpectedly. This is the underlying storage-layer mechanism that ultimately produces the clean 404 response seen when the API is asked for a reminder that doesn't exist.
- **test_add_pending_explicitly_sets_is_deleted_false_on_create** — Directly checks the exact data sent to the storage layer when creating a reminder, confirming the "is_deleted" flag is explicitly set to false rather than left blank. The test notes this fixes a real production bug: a blank flag (rather than an explicit false) meant the sweep's due-reminder lookup, which filters strictly on "is_deleted equals false," never matched newly created reminders, so the firing sweep silently found nothing to do, ever, in the live Sheets-backed storage.
- **test_get_due_pending_returns_only_status_pending_rows** — Creates one reminder that stays pending and marks a second one as failed, then confirms that a lookup for due-and-pending reminders returns only the still-pending one. This ensures the sweep never tries to re-fire a reminder that's already been marked failed or otherwise resolved, only genuinely outstanding ones.
- **test_update_status_batch_sets_status_on_each_reminder** — Saves two reminders, marks both as failed in a single batch update call, then confirms each one individually shows the failed status when looked up. This proves the sweep's batch status updates apply correctly and completely across every reminder in the batch, not just the first or a subset.
- **test_remove_from_pending_soft_deletes_each_reminder** — Saves a reminder, then removes it from the pending list via the repository's batch removal method, and confirms the underlying storage row now has "is_deleted" set to true rather than the row being physically erased. This proves fired reminders are archived through a soft delete, preserving a historical trace rather than destroying data outright the moment it's no longer active.
- **test_append_history_batch_writes_to_the_history_tab** — Writes a completed reminder history entry (with a final status of "sent") to the history storage and confirms it can be retrieved from there with the correct final status. This proves the permanent historical record of fired reminders is correctly written to separate, durable storage distinct from the active pending list.
- **test_mark_cancelled_soft_deletes_a_pending_reminder** — Saves a pending reminder, cancels it through the repository's mark-cancelled method, and confirms the underlying pending-storage row now shows "is_deleted" as true rather than the reminder simply vanishing. This proves the cancellation feature actually and reliably removes a reminder from the active queue, so it can never be mistakenly picked up and fired by a later sweep.
- **test_mark_cancelled_is_a_no_op_for_an_already_fired_reminder** — Marks a reminder as failed (simulating it already being processed) and then attempts to cancel it, confirming no error is raised and the reminder's status remains unchanged. This ensures cancellation requests arriving after a reminder has already been resolved don't cause errors or corrupt its final recorded outcome.
- **test_mark_cancelled_is_a_no_op_for_an_unknown_reminder** — Attempts to cancel a reminder ID that was never created and confirms no error is raised. This makes the cancellation operation safe to call defensively without first checking existence, which matters for the API's "cancelling an unknown reminder is a no-op" behavior seen at the integration level.
