# Cleanup Service — Test Catalog

This service enforces retention and purge policies across the system's data, such as deleting old Audit_Log and Reminders_History rows, only after confirming with the Backup & Restore Service that the data is safely backed up, using the Data Gateway for all storage access; there are 36 tests below, split into 4 integration tests and 32 unit tests.

## Integration tests

### tests/integration/test_health.py

- **test_health** — Checks that the Cleanup Service's health endpoint responds with HTTP 200 and a simple "status ok" message. This is the standard heartbeat check confirming the service process is running and reachable, which matters for monitoring even though this service has no other public-facing API for staff to call directly, since it runs entirely on its own schedule.

### tests/integration/test_cleanup_flow.py

This service has no REST endpoints for the cleanup process itself (it runs only on an internal schedule with no outside callers), so "integration" here means driving the fully-wired cleanup orchestrator directly against a real in-memory data store, exercising retention policy, backup safety check, and deletion together as one pipeline.

- **test_full_cycle_purges_old_rows_once_backup_is_confirmed** — Seeds one old Audit_Log entry and one old Reminder History entry, both dated in 2020, sets the backup-check to always approve, and runs a full cleanup cycle. Both old rows are actually deleted from storage and reported as purged. This proves the end-to-end retention pipeline, checking age, confirming backup safety, then permanently deleting, genuinely removes stale records once it's safe to do so.
- **test_full_cycle_skips_old_rows_when_backup_is_not_confirmed** — Seeds an old Audit_Log row but configures the backup-check to deny, simulating that this data hasn't been backed up yet, then runs a cleanup cycle. The row is reported as "skipped" rather than purged, and it's confirmed to still exist in storage afterward. This proves the service refuses to delete data it can't first confirm is safely backed up, a critical safeguard against permanent data loss.
- **test_full_cycle_leaves_recent_rows_alone** — Seeds an Audit_Log row timestamped as of right now, not old at all, and runs a cleanup cycle with backup approval granted. The recent row is left untouched in storage, proving the retention policy correctly distinguishes data old enough to purge from current, still-relevant data, so cleanup never deletes anything before its retention window has actually expired.

## Unit tests

### tests/unit/test_retention_policy.py

- **test_audit_log_policy_computes_a_365_day_cutoff_by_default** — Checks that the Audit Log retention policy, using its default settings, computes a cutoff date exactly 365 days before a given "now," for example from September 2, 2026 it computes September 2, 2025. This proves the standard business rule of "keep one year of audit history" is correctly encoded and calculated by the policy.
- **test_audit_log_policy_cutoff_is_configurable** — Creates an Audit Log retention policy with a custom 30-day retention window instead of the default year, and confirms the cutoff date computed is exactly 30 days earlier than "now." This proves retention windows aren't hard-coded and can be tuned per deployment or policy change without modifying the underlying code.
- **test_reminder_history_policy_computes_a_180_day_cutoff_by_default** — Checks that the Reminder History retention policy defaults to a 180-day, roughly six-month, retention window, correctly computing a cutoff date half a year before the given "now" date. This confirms reminder history, a different type of record than audit logs, follows its own, shorter, appropriate retention rule.
- **test_entity_names_match_the_gateway_tabs_they_act_on** — Confirms the Audit Log policy is wired to operate on the "Audit_Log" data table and the Reminder History policy targets "Reminders_History." This is a simple but important check that each retention policy purges from the correct underlying data table, preventing a policy from accidentally being pointed at the wrong dataset.

### tests/unit/test_backup_check_client.py

- **test_in_memory_client_approves_by_default_and_records_calls** — Uses the in-memory test stand-in for the backup-check client to ask whether "Audit_Log" is backed up as of a date, and confirms it approves by default while also recording exactly what was asked. This validates the test double used throughout the rest of the suite to simulate a healthy, backed-up state without needing the real Backup & Restore Service running.
- **test_in_memory_client_can_be_configured_to_deny** — Configures the in-memory backup-check stand-in to always deny backup confirmation, then confirms asking it returns false. This proves the test harness can also simulate an "unsafe to delete" state, which is used elsewhere to verify the cleanup process correctly holds off purging when backups aren't confirmed.
- **test_http_client_returns_true_when_the_service_confirms** — Simulates calling the real Backup & Restore Service over the network with the correct entity name and date parameters, and has it respond that the data is backed up. The client correctly reports true, proving the real integration between Cleanup and Backup & Restore correctly reads a positive confirmation and passes along the right request details.
- **test_http_client_returns_false_when_the_service_denies** — Simulates the Backup & Restore Service responding that data is not backed up, and confirms the client correctly reports false rather than defaulting to an optimistic "yes." This proves a genuine "not backed up" answer from the real service is faithfully passed through to the cleanup logic rather than being lost or misinterpreted along the way.
- **test_http_client_fails_closed_on_a_non_2xx_response** — Simulates the Backup & Restore Service returning an error response, HTTP 503 service unavailable, when asked to confirm a backup, and checks the client reports false rather than throwing an error or assuming success. This proves that if the backup service is having problems, Cleanup defaults to the safe assumption that data is not backed up, rather than risking permanent data loss.
- **test_http_client_fails_closed_on_a_transport_error** — Simulates a complete network failure, a refused connection, when trying to reach the Backup & Restore Service, and confirms the client still returns false instead of crashing. This proves that even total unreachability of the backup service is treated as "cannot confirm backup, so don't delete anything," the same fail-safe behavior as an explicit denial from the service.

### tests/unit/test_backup_confirmation_gate.py

- **test_check_approves_when_the_client_confirms** — Runs the backup confirmation gate against a backup-check client configured to always approve, and confirms the gate's decision is "approved" with the reason "backup confirmed." This proves the gate correctly passes through a genuine backup confirmation as permission to proceed with deleting old data during the cleanup cycle.
- **test_check_denies_when_the_client_says_not_backed_up** — Runs the gate against a backup-check client configured to deny, and confirms the resulting decision is "not approved" with the reason "not yet backed up." This proves the gate blocks deletion with a clear, human-readable reason whenever the underlying data hasn't been confirmed as backed up yet, avoiding a silent or unexplained refusal.
- **test_check_fails_closed_when_the_client_raises** — Simulates the backup-check client throwing an unexpected error, representing the backup service being down, and confirms the gate still returns a denied decision, with a reason mentioning the backup check being unavailable. This proves any failure in checking backup status is treated as "don't delete," the fail-safe default that protects data whenever the safety check itself can't be completed.

### tests/unit/test_purge_executor.py

- **test_execute_deletes_all_candidate_row_ids_and_reports_the_count** — Gives the purge executor two Audit_Log row candidates flagged for deletion and confirms it deletes both by ID in a single batch call, then reports back exactly 2 rows purged and 0 skipped. This proves the actual deletion step correctly removes every approved candidate row in one go and accurately counts what it did.
- **test_execute_publishes_a_purge_summary_event** — Purges one Audit_Log candidate row and checks that a "cleanup.purged" event is published containing the entity name and the exact purged and skipped counts. This proves every purge action is announced to the rest of the system for auditing and monitoring, so there's a traceable record of what was deleted and when it happened.

### tests/unit/test_cleanup_scheduler.py

- **test_run_forever_calls_the_cleanup_fn_repeatedly_until_stopped** — Starts the cleanup scheduler on a very short interval in a background thread, lets it tick multiple times, then stops it. It confirms the cleanup function ran at least twice and the background thread shuts down cleanly, proving the automated scheduling loop reliably triggers repeated cleanup cycles and can be stopped without hanging indefinitely.
- **test_trigger_cleanup_run_swallows_an_exception_from_the_cleanup_fn** — Configures the scheduler's cleanup function to throw an error simulating a failed cleanup cycle, then triggers one run directly. No exception escapes the scheduler, proving a single failed cleanup attempt doesn't crash the whole scheduling loop, so future scheduled cleanup cycles continue running on their normal interval despite one failure.

### tests/unit/test_kafka_event_publisher.py

- **test_publish_wraps_event_into_the_full_audit_envelope_shape** — Publishes a "cleanup.purged" event describing 5 purged Audit_Log rows and inspects what actually gets sent. It confirms the message includes a unique event ID, correctly labels its source as the cleanup service, identifies the affected entity as "Audit_Log," and carries a timezone-aware timestamp, proving every cleanup action is fully traceable for later auditing.
- **test_envelope_is_json_serializable** — Publishes a "cleanup.purged" event for Reminders_History with zero purged and three skipped rows, and confirms the resulting audit envelope converts cleanly to plain text (JSON). This matters because the event has to travel over the network to other systems; if it couldn't serialize this way, the audit trail for that cleanup run would silently fail to reach anyone downstream.

### tests/unit/test_retention_policy_registry.py

- **test_get_all_returns_policies_given_at_construction** — Creates a retention policy registry pre-loaded at construction time with a single Audit Log retention policy, then confirms asking the registry for all its policies returns a list containing exactly that one policy object, unchanged. This proves the registry correctly holds onto and returns whatever full set of retention rules the service was configured with when it originally started up.
- **test_register_adds_a_policy_without_replacing_existing_ones** — Starts a registry with an Audit Log policy already in it, then registers a second policy, Reminder History, afterward, and confirms both now appear in the full list in the order they were added. This proves new retention rules can be added on top of existing ones without accidentally wiping out previously configured policies.
- **test_get_all_returns_a_copy_not_the_internal_list** — Retrieves the full list of policies from the registry, clears that returned list, then checks the registry still internally holds its one original policy. This proves external code can't accidentally corrupt the registry's real policy list just by modifying whatever list they were handed back, protecting the integrity of the configured retention rules.

### tests/unit/test_cleanup_orchestrator.py

- **test_run_cleanup_cycle_purges_approved_candidates** — Runs a full cleanup cycle with one aged Audit_Log candidate row and backup approval granted, and confirms the cycle's start time matches the fixed clock, exactly one outcome is recorded showing 1 purged and 0 skipped, and the delete operation was called with the right row ID. This proves the orchestrator correctly drives the whole purge process end to end when everything is in order.
- **test_run_cleanup_cycle_skips_candidates_when_backup_not_confirmed** — Runs a cleanup cycle with one aged candidate row but with backup confirmation denied, and confirms the outcome reports 0 purged and 1 skipped, with the delete operation never actually called. This proves the orchestrator correctly holds back deletion, without even attempting it, whenever the backup safety gate isn't satisfied, keeping the data intact and safe.
- **test_run_cleanup_cycle_records_a_zero_outcome_when_no_candidates_exist** — Runs a cleanup cycle where the repository finds zero rows old enough to purge, and confirms the outcome reports 0 purged and 0 skipped, and crucially that the backup-check client is never even consulted. This proves the system doesn't waste effort checking backup status when there's genuinely nothing to clean up, an efficiency and correctness detail.
- **test_run_cleanup_cycle_skips_a_policy_whose_lookup_fails_and_continues** — Simulates the underlying data store being completely unavailable when the orchestrator tries to look up aged rows for two different policies, Audit_Log and Reminders_History. Both lookups fail, but the overall cleanup cycle itself does not crash; it simply records no outcomes for that run. This proves one broken policy or a storage outage doesn't bring down the entire cleanup process.
- **test_run_cleanup_cycle_records_zero_purged_when_delete_fails** — Runs a cleanup cycle where one candidate row is found and approved for deletion, but the actual delete operation fails because the underlying data store becomes unavailable mid-cycle. The outcome is recorded as 0 purged and 1 skipped rather than silently reporting success. This proves a failure during the deletion step itself is honestly reflected in the results, not hidden from operators.

### tests/unit/test_purge_repository.py

- **test_get_aged_rows_returns_only_rows_on_or_before_the_cutoff** — Seeds one Audit_Log row from January 2025 and one from August 2026, then asks the repository for rows aged as of a September 2025 cutoff. Only the older January 2025 row comes back as a purge candidate, proving the age-based filtering correctly separates genuinely old records from recent ones that must be left alone during a cleanup run.
- **test_get_aged_rows_excludes_rows_already_hard_deleted_by_a_prior_purge** — Seeds one old Audit_Log row, hard-deletes it to simulate it already being purged in a previous cleanup cycle, then asks for aged rows again. No candidates come back, proving the repository doesn't try to re-process or re-report a row that's already been permanently removed, avoiding duplicate work or errors on a later cleanup pass.
- **test_get_aged_rows_queries_without_an_is_deleted_filter** — A regression test confirming the repository's query to the data store does not filter on an "is_deleted" field, since neither Audit_Log nor Reminders_History actually has that column in the real system. This guards against a past bug where filtering on a non-existent column silently matched nothing at all, meaning cleanup would never have found anything to purge in production despite tests appearing to pass.
- **test_get_aged_rows_uses_the_right_date_field_for_reminders_history** — Seeds an old Reminder History row and confirms the repository correctly finds it as an aged candidate using the "fired_at" date field specific to that table, rather than an Audit_Log-style timestamp field. This proves the repository knows each data table has its own relevant date column and reads the correct one per entity type being cleaned up.
- **test_delete_rows_hard_deletes_each_row_and_returns_the_count** — Seeds two Audit_Log rows, deletes both by ID through the repository, and confirms it reports deleting 2 rows while both are actually gone from storage afterward, not just soft-hidden. This proves the purge step performs a genuine, permanent deletion and accurately counts how many records were actually removed.
