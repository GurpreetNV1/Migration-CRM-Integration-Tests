# Graphics Service — Test Catalog

The Graphics Service manages content requests (posters, videos, reels, carousels, stories, thumbnails, banners) end-to-end — creation, AI-assisted generation, file uploads, client approval, comments, social publishing, and KPI reporting — and this catalog covers all 42 tests (30 integration, 12 unit) that verify it.

## Integration tests

*These also live at `../tests/service_integration/graphics/`, dual-mode (real Data Gateway/real Sheets and Drive by default, `--gateway-mode=memory` for the fast in-memory behavior described below) — run via `python run_local_integration_tests.py --service graphics`. Same definitions apply to both; see `../README.md`/`../TESTING_GUIDE.md` section 8.5.*

### tests/integration/test_ai_generation_flow.py

- **test_poster_without_pii_masking_is_rejected_but_still_created** — Someone tries to create a poster request with raw text for AI summarization but without confirming that personally identifiable information has been masked first. The API blocks it with a validation error, but the request row is still saved as "pending" in the list. This proves the compliance guardrail (no ungoverned text reaches AI) works without silently losing the work item.
- **test_poster_with_pii_masking_triggers_generation_and_completes_on_callback** — A poster request is created with PII masking confirmed, and the system immediately queues it for AI text summarization. The test then simulates the AI vendor stand-in finishing the job and confirms the request updates to "generated" status with the summarized text and the correct generation method recorded. This proves the poster AI pipeline fires automatically and reflects vendor completion correctly.
- **test_video_generation_triggers_on_raw_upload_not_at_creation** — This is the regression test for a real bug: video AI subtitle generation must only start once raw footage is actually uploaded, not the moment the request is created. It creates a video request (confirms generation status is "not applicable" with no file yet), accepts it, uploads a raw video file, and only then checks generation moves to "pending" and later "generated" after the vendor stand-in completes — proving the timing bug is fixed.
- **test_non_ai_request_type_never_enters_generation_pipeline** — A banner request (a type that has no AI component) is created, and the test confirms its AI generation status stays "not applicable" forever. This proves the system correctly distinguishes AI-eligible content types (posters, videos) from plain design work so banners never get stuck waiting on a generation step that will never happen.

### tests/integration/test_comment_flow.py

- **test_add_and_list_comments** — A story request is created, a staff member posts a clarification comment on it, and the test confirms the comment is saved with the right type and immediately shows up when comments for that request are listed. This proves the back-and-forth communication trail between designers and requesters actually persists and is retrievable, which matters for accountability during revisions.
- **test_comment_on_unknown_request_returns_404** — Someone tries to post a comment against a content request ID (GRX-999999) that does not exist anywhere in the system. The API correctly refuses with a clean "not found" response instead of silently creating an orphaned comment attached to nothing. This proves the system validates the parent request before accepting feedback, keeping the comment audit trail meaningful and trustworthy for designers and clients reviewing history later.

### tests/integration/test_content_request_flow.py

- **test_create_request_defaults_to_pending** — A brand-new content request is created and the test checks it gets a properly formatted ID (starting with "GRX-"), starts in "pending" status, and has no designer assigned yet. This proves every new request enters the system in a clean, predictable starting state before any work begins, so the intake queue always looks the same regardless of content type.
- **test_get_request_returns_what_was_created** — After creating a request, the test fetches it back by its ID and confirms the exact same request, with the matching request ID, comes back from the lookup endpoint. This is the basic guarantee that what you save is what you get when you look it up again later — foundational trust in the data layer that every other workflow step depends on.
- **test_get_unknown_request_returns_404** — Looking up a content request ID (GRX-999999) that was never created correctly returns a clean "not found" response rather than a server error or a misleading empty success. This proves the lookup endpoint distinguishes "this genuinely does not exist" from other failure conditions, which matters for clean, predictable error handling in whatever dashboard or app calls this API.
- **test_list_requests_filters_by_status** — A new request is created, and the test confirms that filtering the overall request list down to just "pending" status correctly includes that newly created request in the results. This proves the dashboard or queue view that staff use to triage incoming work can reliably filter by lifecycle stage, instead of forcing everyone to scroll through every request regardless of state.
- **test_accept_request_assigns_designer_and_moves_to_in_progress** — A designer accepts a pending request, and the test confirms both that the request status flips from "pending" to "in_progress" and that the designer's staff ID is now permanently attached to it. This proves the exact moment a designer picks up a piece of work is tracked precisely, which becomes the starting clock for turnaround-time measurement in KPI reporting later.
- **test_update_request_applies_partial_fields** — A request's title and priority are updated through a partial edit that only sends those two fields, and the test confirms both changed correctly while the untouched description field stayed exactly as it originally was. This proves editing a request is a safe, surgical operation that updates only what was intentionally changed and can't accidentally wipe out unrelated fields on the record.
- **test_update_request_after_cancellation_is_rejected** — Once a request has been cancelled, a follow-up attempt to edit its title is blocked with a 409 conflict error rather than silently succeeding. This proves cancelled work is frozen in place and can't be quietly reopened, renamed, or altered after the fact, which protects the integrity of closed-out records and keeps reporting on cancelled work accurate.
- **test_cancel_request_twice_is_rejected** — A request is cancelled successfully the first time, and then a second attempt to cancel that same already-cancelled request is rejected with a 409 conflict error instead of quietly succeeding again. This proves cancellation is a one-way, one-time action, so the system never produces confusing duplicate history entries or lets someone re-cancel a request that is already closed.

### tests/integration/test_file_upload_flow.py

- **test_upload_raw_files_updates_stats_and_timestamp** — A raw video file is uploaded to a reel request, and the test confirms the upload succeeds, the file is tagged with the "raw" role, and the request's raw file count and raw-uploaded timestamp update accordingly. This proves file intake is properly tracked, which is the data KPI reporting later relies on for turnaround timing.
- **test_deliverables_upload_rejected_before_designer_accepts** — Someone tries to upload a finished deliverable to a request that is still sitting untouched in "pending" status, with no designer having formally accepted it yet, and the system blocks the upload with a 409 conflict error. This proves the workflow can't be short-circuited — deliverables can only be attached once a designer has actually and officially picked up the work.
- **test_deliverables_upload_allowed_once_in_progress** — After a designer formally accepts a banner request, moving it into "in_progress" status, uploading a finished deliverable file now succeeds and the request's deliverable file count correctly increases to reflect it. This proves the deliverable-upload path opens up exactly when it logically should — the moment real design work has officially started, not before and not after.
- **test_upload_rejected_once_cancelled** — After a reel request is cancelled, a follow-up attempt to upload a raw video file to it is rejected with a 409 conflict error rather than being silently accepted. This proves cancelled requests are fully locked down against file activity, not just against edits, which prevents designers from wasting time uploading footage to a job the client has already called off.
- **test_multiple_files_in_one_upload_all_saved** — Two separate video files are uploaded together in a single batch request, and the test confirms both come back as saved files in the response and the request's raw file count correctly reflects both, landing at two rather than one. This proves batch uploads work correctly end to end, so designers submitting multiple assets at once never silently lose a file.

### tests/integration/test_health.py

This is the basic proof-of-life check that monitoring dashboards, load balancers, and deployment tooling rely on to confirm the service is up and responding before any real traffic is routed to it.

### tests/integration/test_kpi_flow.py

- **test_kpi_summary_reflects_a_completed_request** — A full request lifecycle is run end-to-end (create, accept, upload deliverable, submit for review, approve) for one requester, and then the KPI summary endpoint is queried filtered to that requester. The test confirms the completed count and total count both reflect that finished request. This proves the KPI reporting engine actually aggregates real historical activity, not just static numbers.
- **test_kpi_summary_filters_by_designer** — Querying the KPI summary endpoint for a made-up designer ID ("no-such-designer") that doesn't correspond to anyone in the system returns a clean, valid summary with a total of zero rather than an error or, worse, unrelated data. This proves the KPI filters are precise and won't accidentally leak or blend in stats belonging to other designers when a filter matches nobody.

### tests/integration/test_publishing_flow.py

- **test_publish_completed_request_to_multiple_platforms** — A fully completed request is published to both Instagram and Facebook stand-ins in one call, and the test confirms both report success and the request's published-platforms record shows both as "published". This proves the multi-platform publishing feature correctly fans out to every requested channel and records the outcome for each independently.
- **test_publish_rejected_for_non_completed_request** — Publishing is attempted on a request that is still freshly created (not yet completed through the approval workflow), and the system rejects it with a conflict error. This proves unfinished or unapproved content can never accidentally go live on social channels — publishing is gated strictly behind the completed state.
- **test_publish_to_unknown_platform_returns_400** — This is the regression test for a real bug: publishing to a made-up platform name ("myspace") must return a clean, expected 400 "bad request" error rather than leaking an internal server error or stack trace. This proves the dedicated unknown-platform error handling was fixed so invalid input fails safely and predictably instead of exposing internals.

### tests/integration/test_review_and_approval_flow.py

- **test_submit_for_review_requires_in_progress_or_changes_requested** — A designer who has already accepted a banner request submits it for review, and the test confirms the request's status correctly moves from "in_progress" to "review". This proves the handoff point where active design work is declared finished and handed to the client or requester for sign-off is tracked as its own distinct, visible lifecycle stage rather than being implicit.
- **test_approve_by_creator_completes_the_request** — After a deliverable is uploaded and the request is submitted for review, the original requester who created it approves the work, and the test confirms the request status finally moves to "completed". This proves the standard, most common approval path — the person who asked for the work signs off and the job is officially finished — works correctly end to end.
- **test_approve_by_wrong_actor_is_rejected** — Someone (staff ID "STF-999") who is neither the request's original creator nor its designated approver tries to approve a request sitting in review, and the system blocks the attempt with a 403 "forbidden" error. This proves approval authority is strictly enforced, so uninvolved staff can't rubber-stamp or fast-track work that isn't theirs to sign off on.
- **test_request_changes_then_resubmit_and_approve** — This is the regression test for a real bug: after a reviewer requests changes (status becomes "changes_requested"), the designer must be able to upload a revised deliverable and resubmit for review again, then get approved normally. The test walks through exactly that full loop and confirms each step succeeds, proving revision cycles no longer get stuck after a "changes requested" response.
- **test_video_request_routes_approval_to_client_not_creator** — For a video request with a designated client approver contact, the test confirms the internal staff creator is forbidden from approving it, while the named external client contact can approve and complete it. This proves higher-stakes content (video, which needs client sign-off) correctly routes approval authority to the client rather than defaulting to whoever created the internal request.

## Unit tests

### tests/unit/test_content_request_approval_service.py

- **test_approve_by_the_creator_completes_and_publishes** — Using mocked repositories, the approval service is told the request's creator is approving it, and the test confirms the result status becomes "completed", the history log records the action, and an "approved" event is published with the request ID. This proves the core approval business logic — independent of the API layer — correctly finalizes work and notifies downstream systems like Audit.
- **test_approve_by_someone_else_raises_unauthorized** — The approval service is asked to approve a request on behalf of someone who is not the recognized approver, and it raises an "unauthorized approver" error while explicitly confirming the status update was never even attempted. This proves the authorization check happens before any state change, so a rejected approval attempt can't have side effects.
- **test_request_changes_publishes_a_dedicated_event_with_the_reason** — When a reviewer requests changes with a specific reason ("wrong colors"), the service is checked to confirm it publishes a distinct "changes_requested" event carrying both the request ID and that exact reason text. This proves the reason for rejecting work is preserved and broadcast, not lost, so designers and audit trails know exactly what needs fixing.

### tests/unit/test_content_request_model.py

- **test_pending_can_move_to_in_progress_or_cancelled_only** — A request sitting in "pending" status is checked against every possible next status, confirming it can only legally move to "in_progress" or "cancelled" and is explicitly forbidden from jumping straight to "review" or "completed". This proves the core content lifecycle rules are enforced at the data-model level itself, preventing any request from skipping stages regardless of what the API layer allows.
- **test_changes_requested_can_go_straight_back_to_review** — A request sitting in "changes_requested" status is confirmed to be allowed to move directly back to "review" once the designer revises it, while a move to "in_progress" from that same state is explicitly disallowed. This proves the revision loop has its own dedicated, valid shortcut path that is distinct from the original forward-moving new-request workflow, matching how real revision cycles actually work.
- **test_terminal_statuses_allow_no_further_transitions** — Both "completed" and "cancelled" requests are checked, in a loop over each status, to confirm they each return an empty list of allowed next statuses with no exceptions. This proves finished work is truly final at the data-model level — nothing can be reopened or moved once it reaches an end state, which protects historical records and keeps KPI reporting numbers stable and trustworthy.
- **test_resolve_approver_defaults_to_creator** — For a request with no client approver contact set at all, the model's approver-resolution logic is confirmed to fall back to and return the original creator's own staff ID as the person responsible for approval. This proves the default, most common case — internal-only content with no external client involved — correctly assigns approval responsibility to whoever originally asked for the work.
- **test_resolve_approver_prefers_client_contact_when_set** — For a request that has both a creator and an explicit client approver contact assigned, the resolution logic is confirmed to return that client contact's ID rather than the creator's. This proves the system correctly prioritizes an explicit external client sign-off requirement over the default internal approver whenever a client contact has been specified on the request.

### tests/unit/test_content_type_rules.py

- **test_poster_requires_ai_generation_but_not_client_approval** — The business rule lookup for the "poster" content type is checked to confirm it flags AI text generation as required but client approval as explicitly not required for that type. This proves posters are correctly categorized as an AI-assisted but internally-approved content type, which drives how the request workflow branches automatically the moment a poster request is created.
- **test_video_requires_both_ai_generation_and_client_approval** — The business rule lookup for the "video" content type is checked to confirm both AI generation and client approval are flagged as required together, unlike any other content type in the system. This proves video is treated as the highest-touch content type — needing both automated subtitle generation and external client sign-off — which is exactly why dedicated video-specific approval routing exists elsewhere in the service.
- **test_every_other_type_requires_neither** — Every content type other than poster and video — banners, reels, carousels, stories, and thumbnails — is looped through and checked to confirm none of them require AI generation or client approval. This proves the AI-generation and client-approval features are deliberately scoped to just those two special content types and won't unexpectedly activate or add extra steps for simple, everyday design requests.
- **test_every_content_request_type_has_a_rule** — Every single value defined in the content request type enum (poster, video, reel, carousel, story, thumbnail, banner) is checked to confirm it has a corresponding business rule entry defined in the rules table. This proves there's no content type that could silently fall through the cracks with undefined behavior — every type the API accepts has explicit, known rules governing its workflow.
