# Data-Import Service — Test Catalog

The Data-Import Service accepts bulk data-import jobs (recording source type, submitter, status, and an opaque field-mapping configuration) that bring external data — CSV files, legacy Google Sheet exports, or external-database dumps — into the CRM in bulk, checking every row against existing records for duplicates before writing anything, and it stores all of this through the shared Data Gateway; the suite below has 9 integration tests and 45 unit tests, 54 in total.

## Integration tests

*These also live at `../tests/service_integration/data_import/`, dual-mode (real Data Gateway/real Sheets by default, `--gateway-mode=memory` for the fast in-memory behavior described below) — run via `python run_local_integration_tests.py --service data_import`. Same definitions apply to both, though the real-mode copies of `test_job_completes_synchronously_under_the_test_inline_runner_and_report_is_correct` and `test_a_second_submission_of_the_same_row_is_skipped_as_a_duplicate` assert the real Gateway's own already-anticipated ownership-rejection outcome instead of "completed" (see `../README.md`'s note on this). See `../TESTING_GUIDE.md` section 8.5.*

### tests/integration/test_health.py

- **test_health** — Confirms that the Data-Import microservice itself starts up cleanly and answers requests before any import behavior is exercised. The test calls `GET /health` and checks for an HTTP 200 response with the exact body `{"status": "ok"}`. This is the baseline sanity check to run first in a demo: if the service isn't even reachable, none of the import, mapping, or duplicate-detection behavior shown afterward can be trusted.

### tests/integration/test_import_flow.py

- **test_submit_job_returns_202_with_the_job_queued** — Demonstrates that submitting a new bulk-import job — a small CSV mapping "Name" and "Email" columns onto a Contact record — is accepted immediately rather than making the caller wait for the import to finish. The API responds with HTTP 202 "Accepted," a freshly generated job ID prefixed "IMP-," and a "queued" status, proving imports are handled asynchronously so a large file never blocks the person submitting it.
- **test_job_completes_synchronously_under_the_test_inline_runner_and_report_is_correct** — In the test environment, import work is deliberately made to run immediately instead of on a background thread so results are predictable. This test submits one valid contact row, then immediately fetches the job's status and its results report. It confirms the job shows "completed" and the report accurately counts exactly one record imported, zero duplicates skipped, and zero validation failures — proof the numbers shown to staff are correct.
- **test_submit_job_with_an_unrecognized_source_type_returns_422_and_creates_no_job** — Proves the service enforces a fixed list of supported import sources. Submitting a job that claims its source is "sharepoint" — not one of the supported CSV, Google-sheet, or external-database options — is rejected outright with HTTP 422 "Unprocessable Entity," and critically, no job record is created at all, so the system never pretends to accept work it has no way to actually process.
- **test_submit_job_with_empty_raw_input_returns_422** — Confirms the service refuses to accept an import job that has no actual data attached. Submitting a request with a blank raw-input field is rejected with HTTP 422 rather than silently creating an empty or broken job that would sit around doing nothing. This protects downstream processing from ever running against nothing and gives the person submitting the file immediate, clear feedback that it was empty.
- **test_get_status_for_an_unknown_job_returns_404** — Verifies that asking for the status of an import job ID that was never actually submitted returns a clean HTTP 404 "Not Found" instead of an error or a misleading fake answer. This matters in practice: if a staff member references a stale or mistyped job ID, they get an honest "this doesn't exist" response rather than being shown incorrect status information.
- **test_get_report_for_an_unknown_job_returns_404** — Applies the same protection to the results-report endpoint: requesting the detailed import report for a job ID that doesn't exist returns HTTP 404 instead of an empty or fabricated report. This guarantees that any report shown to a user is always tied to a real, previously submitted job, so nobody can be shown results for an import that never actually happened.
- **test_a_second_submission_of_the_same_row_is_skipped_as_a_duplicate** — Shows the duplicate-protection rule working end-to-end through the real API rather than in isolation: the exact same contact row is submitted twice as two separate import jobs. The first job successfully imports the row, but the second job's report shows zero records imported and one record skipped as a duplicate, proving the system won't create the same contact twice even across two unrelated import jobs run minutes apart.
- **test_unparseable_raw_input_marks_the_job_failed** — Demonstrates graceful failure handling when uploaded data doesn't match its declared format: a job is submitted claiming a "google" (legacy sheet) source but supplying plain text instead of the valid JSON that format requires. Rather than crashing the service or hanging indefinitely, the job's status is cleanly set to "failed," giving a clear, inspectable outcome for a malformed file instead of leaving the job stuck in limbo.

## Unit tests

### tests/unit/test_source_mapper.py

- **test_csv_mapper_parses_and_maps_a_real_csv** — Proves the core CSV-to-record translation works correctly on real input: given a two-column CSV with "Name" and "Email" headers and one data row, the mapper reads it and, using the job's submitted field-mapping configuration, correctly renames those columns onto the target Contact's actual field names ("full_name" and "primary_email") while keeping a reference back to the original source row for traceability.
- **test_csv_mapper_raises_source_parse_error_on_undecodable_bytes** — Confirms the CSV mapper detects genuinely corrupt, non-text file content — bytes that cannot be decoded as text at all — and raises a specific "source parse error" rather than crashing unpredictably or silently producing garbage data. A corrupted or wrong-format upload is reported as a clear, expected failure instead of an unhandled crash that would confuse whoever submitted it.
- **test_csv_mapper_map_to_domain_raises_when_nothing_matches_the_field_map** — Verifies that if an uploaded CSV's column headers don't match anything in the submitted field-mapping configuration — for example a column called "Unrelated" with no corresponding mapping rule — the mapper raises a row-mapping error rather than importing a blank or nonsensical record. Only genuinely mappable data is ever allowed to reach the target Contact entity.
- **test_legacy_sheet_mapper_parses_json_row_array** — Confirms support for the older "Google Sheets export" source format: given a JSON array of row objects, the legacy-sheet mapper correctly parses it and applies the same field-mapping rules used for CSV, translating "Name" and "Email" into the target's "full_name" and "primary_email" fields, proving the system can absorb data from more than just one type of upstream source file.
- **test_legacy_sheet_mapper_raises_source_parse_error_on_invalid_json** — Ensures that if a "legacy sheet" import is submitted with text that isn't valid JSON at all, the mapper fails predictably with the same source parse error used elsewhere in the system, instead of throwing an unrelated, confusing technical exception. This keeps error handling consistent no matter which supported import format actually broke.
- **test_legacy_sheet_mapper_raises_source_parse_error_when_not_a_json_array** — Checks a subtler malformed-input case: the submitted content is technically valid JSON, but it's a single object rather than the expected list of rows the importer needs. The mapper correctly rejects this shape as a source parse error too, proving it validates not just "is this JSON" but "is this JSON shaped the way a real import file must be."
- **test_external_db_mapper_parses_json_row_array** — Confirms the third supported source type, data pulled from an external database, is handled consistently with the other formats: a JSON array of rows is parsed and its fields correctly translated onto the target Contact's real field names, showing the mapping logic behaves the same regardless of which upstream system the incoming data actually came from.
- **test_external_db_mapper_raises_source_parse_error_on_invalid_json** — Confirms the external-database import path also fails cleanly and predictably when given text that isn't valid JSON, raising the same source parse error used by every other format rather than a format-specific or confusing error message, so operators always see one consistent, recognizable failure signal no matter which source type broke.
- **test_mapper_factory_resolves_csv** — Verifies the internal "which parser do I need" lookup correctly hands back a CSV-specific mapper when a job declares its source type as "csv." This proves the service automatically wires up the right file-reading logic for the format the caller says they're sending, rather than requiring any manual per-job configuration of parsing logic.
- **test_mapper_factory_resolves_google** — Verifies that declaring a job's source type as "google" correctly resolves to the legacy-sheet mapper behind the scenes, confirming the mapping between a business-facing source name and the internal parsing logic that actually understands that particular file format is wired up correctly and won't silently pick the wrong parser for a file the caller labeled clearly.
- **test_mapper_factory_resolves_external_db** — Verifies that declaring "external_db" as the source type correctly resolves to the external-database mapper, completing the proof that each of the three currently supported source names routes to its own matching parser, so every import option advertised to users genuinely has working logic behind it rather than being a dead end.
- **test_mapper_factory_rejects_microsoft_not_yet_instantiated_in_v1** — Documents and enforces a known, deliberate product limitation: even though "microsoft" may be recognized as a planned future source type, this version of the service has no parser actually built for it yet. Requesting it raises an "unsupported source type" error, so the system is honest about a known gap instead of quietly pretending support that doesn't exist.
- **test_mapper_factory_rejects_an_unknown_source_type** — Confirms the system safely rejects a completely made-up, never-supported source type value with the same "unsupported source type" error used for known-but-unbuilt sources like Microsoft. This proves unrecognized input is always explicitly refused rather than falling through to a default parser or causing unpredictable, hard-to-debug behavior deep inside the import pipeline where it would be much harder to diagnose.

### tests/unit/test_job_runner.py

- **test_inline_job_runner_runs_synchronously** — Verifies the "inline" execution mode used by the automated test suite runs a submitted job immediately, in the same line of execution, before control is returned to the caller. This proves the test suite's shortcut for avoiding real background threads genuinely produces deterministic, immediate results rather than silently deferring work that a later assertion might check too early.
- **test_thread_pool_job_runner_runs_off_the_calling_thread** — Proves that in real, non-test operation, submitted import jobs are actually handed off to run on a separate background thread rather than the same thread that received the original request. This is exactly what allows the API to respond to the caller instantly while the potentially slow file-processing work keeps running behind the scenes.
- **test_thread_pool_job_runner_does_not_block_the_caller** — Confirms the background job runner truly doesn't make the caller wait: a deliberately slow job is submitted, and the test measures that control returns to the caller in well under half a second even though the job itself is still running in the background. This proves large or slow bulk imports can never freeze the API for the person who submitted them.

### tests/unit/test_duplicate_reconciler.py

- **test_find_duplicates_returns_none_when_nothing_matches** — Confirms that when a new contact record shares no meaningful identifying information with any existing record in the system, the duplicate-detection logic correctly reports "no match" rather than flagging it unnecessarily. This matters in practice because it ensures genuinely new, unique people are never mistakenly held back or blocked from being imported due to an overly aggressive duplicate check.
- **test_find_duplicates_returns_exact_for_an_identical_record** — Verifies that when an incoming row is a perfect match to an already-existing record — identical name and identical email address — the system correctly classifies it as an "exact" duplicate. This exact classification is what later triggers the system to automatically skip the row rather than creating a redundant second copy of the same real person.
- **test_find_duplicates_returns_probable_for_a_natural_key_match_with_other_differences** — Verifies a subtler, very realistic scenario: an incoming row shares the same email address as an existing contact but has a slightly different spelling of the name ("Jane A. Doe" versus "Jane Doe"). The system correctly classifies this as only "probable," not an automatic exact match, reflecting that near-duplicates deserve human judgment rather than being auto-decided in either direction.
- **test_find_duplicates_ignores_records_with_no_natural_key_overlap** — Confirms that records with no shared identifying details whatsoever — a different name, and no matching email or phone number — are correctly treated as two unrelated people rather than potential duplicates of each other. This proves the duplicate check doesn't over-flag unrelated records just because they both happen to exist in the same comparison list.
- **test_apply_policy_maps_verdicts_to_actions** — Verifies the core business rule that translates a duplicate-detection verdict into a concrete real-world action: a "no match" verdict leads to accepting the record, an "exact" match leads to skipping it entirely, and a "probable" match leads to flagging it for human review rather than the machine deciding unilaterally — the single policy governing every possible duplicate outcome in the system.

### tests/unit/test_reconciliation_engine.py

- **test_reconcile_accepts_a_row_with_no_existing_match** — Confirms the end-to-end row-processing logic correctly accepts and counts a brand-new contact that has no match among existing records, proving one clean, genuinely unique row flows all the way through parsing and duplicate-checking to being marked as a single successfully imported record with no errors along the way, exactly as a real first-time contact upload should behave.
- **test_reconcile_skips_an_exact_duplicate_against_existing_records** — Proves that when a submitted row is identical to a record already stored in the system, the reconciliation logic correctly declines to import it a second time, counting it instead as a skipped duplicate. This confirms the system won't create a redundant, wasteful second copy of an already-known contact just because the same file gets uploaded again.
- **test_reconcile_flags_a_probable_match_instead_of_importing_it** — Demonstrates the important "handle with care" middle case: a row that shares an email with an existing contact but has a different name is neither imported nor silently dropped. Instead it's held back, and a "possible duplicate" note is recorded in the job's error list, ensuring genuinely uncertain matches get surfaced for a human to review rather than resolved automatically by the machine alone.
- **test_reconcile_counts_a_row_mapping_failure_without_failing_the_batch** — Confirms that one bad row inside a larger batch — a row whose columns don't match the submitted field-mapping configuration — doesn't sink the entire import job. The good row in the same batch is still imported successfully, while the bad row is separately counted as a validation failure, so a single mistake in a spreadsheet doesn't waste an otherwise valid bulk upload.
- **test_reconcile_fetches_existing_records_once_per_target_entity_type** — Verifies an important efficiency safeguard: even when a job contains multiple rows destined for the same record type, such as several contacts in one file, the system fetches the list of existing records to compare against only a single time per batch, rather than re-querying storage separately for every individual row, which matters directly for keeping large imports fast and affordable.
- **test_reconcile_dedupes_against_records_accepted_earlier_in_the_same_run** — Proves the system also catches duplicates that appear for the first time within the same uploaded file, not only against data already sitting in storage: when the exact same row appears twice inside one CSV, the second occurrence is correctly skipped as a duplicate of the first, even though neither row existed in the system before this upload began.

### tests/unit/test_import_job_repository.py

- **test_save_assigns_an_imp_prefixed_id_on_first_save** — Confirms that when a brand-new import job is saved for the very first time, the system automatically generates a unique, human-recognizable identifier prefixed "IMP-" for it. This guarantees every import job gets a consistent, traceable reference number that staff and other systems can use, without the caller ever having to invent or supply one themselves.
- **test_save_updates_the_same_row_on_a_second_save** — Verifies that saving an already-existing job a second time — for example, after it finishes processing and its final results are recorded — updates that same underlying record in place rather than creating a confusing duplicate entry. The job correctly ends up reflecting its new "completed" status and updated result counts, still under its original job ID.
- **test_find_by_id_returns_what_was_saved_including_report_fields** — Confirms that looking a job back up by its ID returns the complete picture, including the detailed results that were recorded after processing finished: how many records were imported, skipped as duplicates, and failed validation, plus any error notes. This proves nothing gets lost between when a job's outcome is saved and when it's later retrieved for a report.
- **test_find_by_id_raises_for_an_unknown_job** — Verifies that looking up a job ID that was never actually saved produces a clear, explicit "record not found" error rather than quietly returning empty or incorrect data. This ensures the storage layer is always honest about what it does and doesn't actually have on file, which matters for any code or person relying on its answers.
- **test_find_existing_reads_the_target_tab_and_strips_internal_keys** — Confirms the mechanism used to check for duplicates works correctly against real stored data: it reads existing Contact records from storage and correctly strips away the storage system's own internal bookkeeping ID, leaving only the real business fields. This ensures duplicate comparisons are made against actual contact details, not internal, irrelevant storage metadata.
- **test_write_reconciled_batch_writes_every_record_and_returns_the_count** — Verifies that once a batch of rows has been cleared for import by the reconciliation logic, every single one of them is actually written to storage — none are silently dropped — and the system correctly reports back exactly how many records were saved, giving an accurate, trustworthy count for the job's final results report.

### tests/unit/test_import_job_service.py

- **test_submit_job_runs_synchronously_to_completion_under_the_inline_runner** — Proves the whole submission workflow, from accepting a job through it finishing successfully, also emits the correct sequence of business events along the way: a "job submitted" event followed by a "job completed" event. This matters because other systems and audit logs depend on exactly these notifications, in this order, to know reliably what happened and when.
- **test_submit_job_report_reflects_the_completed_import** — Confirms that after a straightforward, valid import job runs all the way to completion, the detailed report attached to it accurately reflects the true outcome: exactly one record imported, none skipped as duplicates, none failed validation, and an empty list of errors. This gives confidence that the specific numbers shown to staff on a completed job are genuinely trustworthy.
- **test_submit_job_rejects_an_unsupported_source_type_before_creating_a_job** — Verifies that submitting a job with a source type the service doesn't support, such as "microsoft," is rejected before any job record is created in storage and before any business event is published to other systems. This proves the system fails fast and cleanly, without leaving orphaned half-created jobs or sending out misleading notifications about work that was never actually accepted.
- **test_submit_job_rejects_empty_raw_input** — Confirms submitting a job with no actual file content attached is rejected with a specific "invalid request" error, and importantly, no job record is created in storage at all. This ensures the system never wastes storage space or processing effort recording a request that was never going to contain any real, usable data in the first place.
- **test_submit_job_with_unparseable_input_marks_the_job_failed** — Demonstrates that when a job's data can't be read at all — in this case, badly corrupted, undecodable bytes — the job isn't silently discarded. It still gets created and is correctly marked "failed" with a descriptive "parse failed" note, and the system publishes a "job failed" event, keeping a complete, honest audit trail of every attempted import, including the broken ones.
- **test_submit_job_write_failure_marks_the_job_failed_instead_of_hanging** — Simulates a real Data Gateway ownership rejection where the service isn't allowed to write to the target entity's storage tab, while its own job-status writes keep working normally. Confirms submitting the job doesn't raise an exception but instead lands the job in a genuine "failed" state with a "reconciliation/write failed" error recorded, and that both a "job submitted" and "job failed" event get published. This closes off a real production risk where a storage-permission problem could otherwise leave a job stuck showing "processing" forever with no explanation.
- **test_submit_job_with_a_flagged_probable_duplicate_completes_with_errors** — Verifies the specific outcome status used when an import technically finishes but not cleanly: submitting a contact whose email matches an existing record but whose name is slightly different results in the job being marked "completed with errors," zero records actually imported, and a "possible duplicate" note recorded. This lets staff see at a glance that a finished job still needs a manual look before being considered fully resolved.
- **test_get_status_on_an_unknown_job_raises_record_not_found** — Confirms that asking for the status of a job ID that doesn't exist raises a clear "record not found" error at the core business-logic layer, not just at the outer web API. This ensures the same honest, no-such-record protection holds true no matter which part of the system is asking, reducing the risk of inconsistent behavior between layers.
- **test_get_report_on_an_unknown_job_raises_record_not_found** — Confirms the equivalent protection applies to the results report as well: requesting a report for a nonexistent job ID raises "record not found" rather than returning a blank or fabricated report. This reinforces that every report the business logic can produce corresponds to a job that genuinely exists somewhere in storage.
- **test_a_second_identical_submission_is_skipped_as_a_duplicate** — Proves the duplicate-prevention rule holds true at the core business-logic level, independent of the web API layer tested elsewhere. Submitting the exact same import twice results in the first import succeeding normally and the second correctly reporting zero records imported and one record skipped as a duplicate, confirming the safeguard is a real business rule and not just an API-layer coincidence.

### tests/unit/test_kafka_event_publisher.py

- **test_publish_wraps_event_into_the_full_audit_envelope_shape** — Verifies that every business event this service announces to the rest of the system, such as "job submitted," is wrapped in a complete, well-formed audit envelope before being sent out. That envelope includes a unique event ID, the name of the service that raised it, what kind of record the event concerns, exactly which record, and a timezone-aware timestamp, ensuring every event is fully traceable after the fact.
- **test_envelope_is_json_serializable** — Confirms that the audit envelope built around every published event can actually be converted into valid JSON text without errors. This matters in practice because if the envelope couldn't be serialized, the event could never actually be transmitted to or stored by any downstream system that consumes these notifications, silently breaking the entire audit trail without any obvious symptom at publish time.
