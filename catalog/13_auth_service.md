# Auth Service — Test Catalog

The Auth Service authenticates staff and client logins by password or SSO identity token, issues and validates signed session tokens used to prove who is calling on every subsequent request, and runs the self-service forgot-password flow (one-time code request, then confirm), and this catalog covers 48 tests in total (10 integration, 38 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — Confirms the service exposes a working health-check endpoint that returns HTTP 200 with a simple `{"status": "ok"}` body. This is the basic signal that the service is alive and reachable, which every monitoring tool, load balancer, and deployment pipeline relies on before routing real traffic to it.

### tests/integration/test_auth_flow.py

- **test_password_login_succeeds_with_the_right_password** — Seeds a staff account ("STF-000001") with a bcrypt-hashed password, then posts the matching identifier and password to `/auth/login` through the real HTTP API. Confirms a 200 response whose body echoes the correct staff ID and "Staff" account type and includes an issued token. This proves the standard username/password login path works end to end and actually hands back a usable session.
- **test_password_login_fails_with_the_wrong_password** — Uses the same seeded account but submits the wrong password to `/auth/login`, confirming the API responds with 401. This is the most basic security guarantee a login system must provide: incorrect credentials never grant access.
- **test_login_with_neither_shape_returns_400** — Posts a completely empty JSON body to `/auth/login`, containing neither an SSO token nor an identifier/password pair, and confirms a 400 response. This ensures malformed or incomplete login requests are rejected cleanly with a clear client error instead of crashing the service or being silently ignored.
- **test_sso_login_with_a_fake_token_for_a_known_staff_identity** — Seeds a staff credentials record for "staff-subject-9", then logs in using an SSO id_token in the dev/test identity-provider's format ("staff-subject-9:staff@example.com:Staff"), confirming a 200 response with the matching staff ID returned. This proves staff can authenticate through single sign-on, not just a password, once their credentials record already exists.
- **test_sso_login_for_a_first_seen_client_is_denied_by_default** — Attempts an SSO login using a token for a client identity the system has never seen before, confirming the API responds with 403. This confirms that, under the service's default configuration, an unrecognized client cannot get in through SSO alone — self-service account creation via SSO is deliberately locked down until that product decision is finalized.
- **test_validate_token_round_trip** — Logs in to obtain a real session token, then posts that exact token to `/auth/validate-token`, confirming the response reports it as valid and returns the same staff ID. This is the mechanism the API Gateway and every other service depend on to confirm "this caller is who they claim to be" on every authenticated request.
- **test_validate_token_rejects_garbage** — Posts a nonsense string as a token to `/auth/validate-token` and confirms the API still responds 200, just with `valid: false`, rather than erroring. Because this endpoint is likely called on nearly every API request across the system, it needs to degrade gracefully for bad input instead of throwing exceptions that could take down request handling elsewhere.
- **test_password_reset_full_flow** — Walks the complete self-service reset journey: requests a reset for a seeded account (202), pulls the generated one-time code out of the test notifier, confirms it along with a new password (200), then logs in again using that new password (200). This proves a staff member who forgot their password can regain access entirely on their own, without needing an administrator to intervene.
- **test_password_reset_confirm_with_wrong_otp_returns_400** — Seeds a second account, requests a reset for it, then attempts to confirm using a deliberately wrong six-digit code ("000000"), confirming a 400 response. This ensures a password can only be changed by someone who actually received the correct one-time code, not by guessing.

## Unit tests

### tests/unit/test_auth_credentials.py

- **test_set_password_stores_the_hash** — Calls `set_password` on a freshly constructed credentials object with a hash string and confirms the `password_hash` field is updated to exactly that value. This is a basic sanity check on the core setter that every password-based login and password-reset flow ultimately writes through.
- **test_set_reset_otp_stores_all_three_fields** — Calls `set_reset_otp` with a hash, an expiry timestamp, and a requested-at timestamp, then confirms all three fields land on the credentials object unchanged. This confirms the model correctly tracks everything later needed to validate a one-time code and to enforce a cooldown between reset requests.
- **test_clear_reset_otp_removes_hash_and_expiry_but_keeps_requested_at** — Sets a reset OTP, then clears it, confirming the hash and expiry are wiped back to `None` while the `requested_at` timestamp is deliberately left in place. This is what makes a used OTP single-use, while still preserving the "when was a reset last requested" timestamp needed to enforce the cooldown on the next attempt.
- **test_is_otp_valid_true_before_expiry** — Sets an OTP that expires ten minutes out, then checks validity as of five minutes later, confirming it reports true. Confirms an OTP that's still within its window is correctly treated as usable.
- **test_is_otp_valid_false_after_expiry** — Same setup, but checks validity eleven minutes later — one minute past the ten-minute window — confirming it reports false. This proves reset codes genuinely expire rather than remaining valid indefinitely, closing the window an attacker who intercepts an old code could exploit.
- **test_is_otp_valid_false_when_no_otp_set** — Checks OTP validity on a brand-new credentials record where no reset was ever requested, confirming it reports false. Guards against a missing OTP ever being mistaken for a valid one.

### tests/unit/test_auth_credentials_repository.py

- **test_save_then_find_round_trips_plain_fields** — Saves a new credentials record (staff ID, account type, and password hash) through the repository layer backed by the Data Gateway, then fetches it back by ID and confirms the account type and password hash match exactly what was saved. This validates the basic read/write reliability of credential storage on its own, independent of the HTTP layer sitting on top of it.
- **test_find_by_id_unknown_raises_record_not_found** — Confirms that looking up an ID that was never saved ("nobody") raises a `RecordNotFoundError` rather than returning something empty or crashing. This is the underlying mechanism that lets login correctly and predictably fail for unknown identifiers.
- **test_update_round_trips_datetime_fields** — Saves a credentials record, then sets its OTP hash and two datetime fields (expiry and requested-at) and calls `update`, re-fetching afterward to confirm all three values persisted correctly. This proves datetime values specifically — a common serialization trap — survive the round trip through the Data Gateway intact, which the reset flow depends on to enforce expiry and cooldown checks correctly.

### tests/unit/test_auth_service.py

- **test_login_resolves_a_strategy_authenticates_and_issues_a_session** — Wires `AuthService` with a mocked strategy that reports it supports the request and returns a fixed principal, plus a mocked token issuer, then calls `login`. Confirms the returned session is exactly what the token issuer produced, and that the issuer was called with the strategy's authenticated principal. This proves the core login orchestration — pick the right strategy, authenticate, then issue a token — is wired together correctly.
- **test_validate_token_delegates_to_the_token_issuer** — Calls `validate_token` on the service with a mocked token issuer and confirms the issuer's `validate` method was invoked with the exact token passed in. Confirms token validation is a clean, direct pass-through rather than duplicated or diverging logic elsewhere in the service.
- **test_password_reset_methods_delegate_to_the_reset_service** — Calls both `initiate_password_reset` and `complete_password_reset` on the service with a mocked `PasswordResetService`, confirming each call is forwarded with the exact arguments given. This proves the top-level service correctly hands off all reset behavior to the dedicated reset service rather than reimplementing or diverging from it.

### tests/unit/test_auth_strategy.py

- **test_password_strategy_supports_only_identifier_and_password_requests** — Checks `PasswordAuthStrategy.supports()` against three request shapes: identifier+password (true), an SSO-only id_token request (false), and a completely empty request (false). This proves the strategy correctly recognizes only requests actually shaped for it, which is what lets the resolver route each login attempt to the right handler.
- **test_password_strategy_authenticates_a_correct_password** — Seeds a staff account with a known password, authenticates against it with the matching identifier and password directly through the strategy, and confirms the returned principal's ID and account type match. Confirms the strategy's success path works correctly on its own, isolated from the HTTP layer.
- **test_password_strategy_rejects_a_wrong_password** — Same seeded account, but authenticates with an incorrect password, confirming an `AuthenticationFailedError` is raised. This is the strategy-level security check underlying every rejected password login.
- **test_password_strategy_rejects_an_unknown_identifier** — Attempts to authenticate an identifier that was never seeded into the system, confirming it also raises `AuthenticationFailedError`. Getting the same error as a wrong password (rather than a distinct "no such user" error) is deliberate, preventing attackers from using login failures to enumerate which accounts exist.
- **test_password_strategy_rejects_an_sso_only_account** — Seeds an account that has no password set at all (an SSO-only account), then attempts a password login against it, confirming it's rejected with `AuthenticationFailedError`. This closes off the password endpoint as a backdoor into accounts that were only ever meant to authenticate via SSO.
- **test_sso_strategy_authenticates_an_existing_staff_identity** — Seeds a staff credentials record, then authenticates through `SSOAuthStrategy` using a fake SSO token identifying that same staff subject, confirming the returned principal's ID and account type match. Confirms staff whose credentials already exist can log in via single sign-on, not just by password.
- **test_sso_strategy_rejects_an_unknown_staff_identity** — Attempts SSO authentication for a staff subject with no seeded credentials record, confirming `AuthenticationFailedError` is raised. This documents that Auth Service never provisions staff accounts itself — creating staff records is the User Service's responsibility — so an SSO-verified staff identity with no local record is simply treated as invalid here, not auto-created.
- **test_sso_strategy_denies_a_first_seen_client_by_default** — Authenticates an SSO token for a never-before-seen client subject while the strategy is wired with the deny-by-default provisioning policy, confirming a `ClientNotProvisionedError` is raised. This is the strategy-level source of the 403 seen at the API for first-time client SSO logins under the system's current conservative default.
- **test_sso_strategy_auto_provisions_a_first_seen_client_when_policy_allows_it** — Same scenario, but wired instead with the alternative auto-provisioning policy, confirming authentication succeeds and returns a new "Client" principal for the previously-unseen subject. This proves the not-yet-finalized self-service-signup alternative genuinely works when an operator chooses to enable it, rather than being dead, unexercised code.
- **test_resolver_picks_the_first_supporting_strategy** — Registers the SSO strategy ahead of the password strategy in the resolver, then confirms an SSO-shaped request resolves to the SSO strategy while a password-shaped request resolves to the password strategy. This proves the resolver matches each login attempt to the strategy that actually fits its shape, rather than always picking whichever strategy happens to be registered first.
- **test_resolver_rejects_a_request_matching_no_strategy** — Asks a resolver configured with no strategies at all to resolve an empty login request, confirming it raises `UnsupportedLoginMethodError`. This is the strategy-level source of the 400 response returned when a login request matches neither the password nor the SSO shape.

### tests/unit/test_clients.py

- **test_bcrypt_hasher_round_trips** — Hashes the password "correct-horse" with `BcryptPasswordHasher`, then confirms `verify` returns true for that exact password and false for "wrong". Confirms the actual hashing implementation used in production correctly distinguishes matching from non-matching passwords, the foundation every password login check relies on.
- **test_bcrypt_hasher_two_hashes_of_the_same_value_differ** — Hashes the identical plaintext ("same-input") twice and confirms the two resulting hash strings differ from each other. This proves bcrypt's built-in per-hash salting is genuinely active, which is what stops identical passwords across different accounts from producing identical, pattern-revealing entries in storage.
- **test_fake_identity_provider_parses_a_well_formed_token** — Verifies a well-formed dev/test token ("sub-1:a@example.com:Staff") through `FakeIdentityProviderClient` and confirms the subject, email, and account type are all extracted correctly. This confirms the stand-in used in place of real Google SSO correctly parses identity fields, something every SSO-related test elsewhere in the suite depends on.
- **test_fake_identity_provider_rejects_a_malformed_token** — Feeds a garbage string with none of the expected structure ("not-a-valid-token") to the fake identity provider, confirming it raises `InvalidSSOTokenError`. Ensures malformed SSO tokens are rejected cleanly instead of crashing or being silently accepted as valid.
- **test_session_token_issuer_issues_and_validates_a_round_trip** — Issues a real signed session token for a principal using `SessionTokenIssuer`, then immediately validates that same token, confirming it comes back valid with the matching staff ID and account type. Confirms the actual production JWT signing and verification logic works correctly end to end — the mechanism underlying every session in the system.
- **test_session_token_issuer_rejects_a_garbage_token** — Validates a nonsense string as if it were a token, confirming the result reports invalid rather than raising an exception. Ensures the real token issuer itself, not just the API layer wrapping it, degrades gracefully for malformed input.
- **test_session_token_issuer_rejects_a_token_signed_with_a_different_key** — Issues a token using one signing key, then attempts to validate it with an issuer configured with a different signing key, confirming the result reports invalid. This proves a session token can't be forged or accepted using the wrong secret, which matters for keeping sessions from crossing environments that use different signing keys.

### tests/unit/test_password_reset_service.py

- **test_initiate_on_unknown_identifier_does_nothing_and_does_not_raise** — Calls `initiate` for an identifier ("nobody") with no credentials record at all, confirming no exception is raised and that no notification was sent. This deliberately mirrors login's behavior of never revealing whether an identifier exists, so the reset-request endpoint can't be used to discover which staff or client IDs are real.
- **test_initiate_stores_an_otp_and_notifies** — Seeds a credentials record, calls `initiate`, and confirms exactly one notification was recorded for that ID and that a real `reset_otp_hash` was actually stored on the record. Confirms the core reset-request path both generates and persists a usable one-time code and actually dispatches it, the two things that must both happen for a reset to be completable later.
- **test_initiate_twice_within_the_cooldown_is_throttled** — Calls `initiate` twice back to back for the same seeded account, confirming the second call raises `ResetRequestThrottledError`. This prevents an attacker — or simply an impatient user hitting the button twice — from spamming reset requests and one-time codes in rapid succession.
- **test_confirm_with_the_correct_otp_sets_a_new_password** — Initiates a reset, retrieves the real generated OTP from the test notifier, confirms it along with a new password ("new-password-123"), then checks that the stored OTP hash is now cleared and that the new password actually verifies via `BcryptPasswordHasher`. This proves confirming a reset genuinely changes the account's password to the value supplied, rather than just returning a success response.
- **test_confirm_with_the_wrong_otp_raises_invalid_otp** — Initiates a reset, then attempts to confirm using an incorrect code ("000000"), confirming `InvalidOtpError` is raised. This is the core check preventing a password from being reset using a guessed or wrong one-time code.
- **test_confirm_is_single_use** — Initiates a reset, successfully confirms once with the real OTP, then attempts to confirm a second time using that same already-used code, confirming the second attempt raises `InvalidOtpError`. This proves a reset code can't be replayed to change a password a second time, for instance if it were intercepted after already being used legitimately.
- **test_confirm_with_an_expired_otp_raises_invalid_otp** — Directly seeds a credentials record with an OTP whose expiry is already one second in the past (originally requested fifteen minutes earlier), then attempts to confirm with the otherwise-correct code, confirming `InvalidOtpError`. This proves the ten-minute OTP validity window is actually enforced, so an old, potentially leaked code can't still be used well after the fact.
- **test_confirm_on_unknown_identifier_raises_invalid_otp_not_a_distinct_error** — Calls `confirm` for an identifier with no credentials record at all, confirming it raises the same `InvalidOtpError` used for a genuinely wrong code, rather than a distinct "unknown user" error. This keeps the reset-confirm endpoint from leaking, through a different error type, whether a given identifier actually exists in the system — consistent with the enumeration-avoidance posture the service takes everywhere else.
