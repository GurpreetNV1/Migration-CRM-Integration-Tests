# Task Service — Test Catalog

The Task Service creates, assigns, and tracks follow-up work items against a Contact or an Application, either from a direct staff request or automatically from an incoming business event, and this catalog covers 51 tests in total (10 integration, 41 unit).

## Integration tests

### tests/integration/test_health.py

- **test_health** — Confirms the service exposes a working health-check endpoint that returns HTTP 200 with a simple `{"status": "ok"}` body. This is the basic signal that the service is alive and reachable, which every monitoring tool, load balancer, and deployment pipeline relies on before routing real traffic to it.

### tests/integration/test_tasks_flow.py

- **test_create_task_against_a_contact** — Seeds a Contact record, then creates a task pointed at that contact with a due date and assigned staff member through the real HTTP API. Confirms the response is a 201, the returned task ID is formatted with a "TK-" prefix, the task's display label shows the contact's actual name, and the new task starts in "open" status, proving the full contact-linked task creation path works end to end.
- **test_create_task_against_an_application** — Seeds an Application record and creates a task against it via the API, verifying a 201 response and that the task's display label combines the application's visa type with its ID (e.g. "Skilled Migration (AP-000001)"). This proves tasks can be linked to Applications just as easily as Contacts, and that each target type gets a meaningful, human-readable label rather than a raw ID.
- **test_create_task_against_a_missing_target_returns_404** — Attempts to create a task against a Contact ID that was never seeded into the system, and confirms the API responds with 404 Not Found. This protects data integrity by making sure staff cannot accidentally create a task tied to a person or record that doesn't actually exist in the CRM.
- **test_create_task_with_an_unsupported_target_type_returns_422** — Sends a task creation request naming an unsupported target type ("Ticket") that the service has no handler for, and checks the API rejects it with a 422 validation error rather than crashing or silently accepting it. This proves the system only allows tasks against target types it explicitly understands.
- **test_get_task_returns_what_was_created** — Creates a task through the API, then immediately fetches it back by its ID, confirming the retrieved task ID matches exactly what was created. This proves that once a task is saved, staff can reliably look it up again later, which is the foundation of any task list or detail view in the CRM.
- **test_get_unknown_task_returns_404** — Requests a task ID that has never been created and confirms the API correctly responds with 404 rather than an error or an empty success. This ensures the UI and any integrating services get a clear, predictable "not found" signal instead of ambiguous behavior when a task doesn't exist.
- **test_list_tasks_filters_by_assigned_staff_id** — Creates a task assigned to a specific staff member, then queries the task list filtered by that staff member's ID, confirming the created task appears in the filtered results. This proves staff can pull up "my tasks" or a specific colleague's workload, a core feature for day-to-day task management.
- **test_update_task_status_to_done** — Creates a task against a seeded contact through the real HTTP API, then sends a follow-up request to that task's status endpoint marking it "done," and confirms the response comes back as HTTP 200 with the status field now reading "done." This verifies that staff can close out completed follow-up work through the same interface a frontend would use, and that the status change is genuinely persisted and reflected back rather than silently accepted and dropped.
- **test_reassign_task** — Creates a task assigned to one staff member, then reassigns it to a different staff member through the reassignment endpoint, confirming the response shows the new assignee. This proves work can be handed off between team members (e.g. when someone is out or workload needs rebalancing) without losing the task's history.

## Unit tests

### tests/unit/test_target_resolver.py

- **test_contact_resolver_validates_and_labels** — Seeds a contact named "Test Person" into storage, then checks that the Contact-specific resolver correctly reports that contact's ID as valid and produces the contact's actual full name, not a raw ID, as its display label. This is the building block that ensures every task shown to staff carries a recognizable, human-readable name rather than a cryptic internal identifier no one can act on.
- **test_contact_resolver_rejects_missing_target** — Confirms that asking the Contact resolver whether a nonexistent contact ID is valid returns false, and that trying to generate a label for it raises a clear "target not found" error instead of silently succeeding. This is what ultimately powers the 404 response when someone tries to create a task against a contact that doesn't exist.
- **test_contact_resolver_falls_back_to_id_when_full_name_blank** — Tests the edge case where a contact record exists but has no name filled in, confirming the resolver falls back to showing the contact's ID as the label rather than displaying a blank or broken label. This prevents confusing, empty-looking task entries in the UI for incomplete contact records.
- **test_application_resolver_validates_and_labels** — Seeds an application with visa type "Skilled Migration," then checks that the Application-specific resolver validates its ID as real and builds a display label combining the visa type with the application ID (e.g. "Skilled Migration (AP-000001)"). This confirms Applications get the same reliable existence-checking and human-readable labeling treatment that Contacts already get, keeping task displays consistent across target types.
- **test_application_resolver_rejects_missing_target** — Confirms the Application resolver flags a nonexistent application ID as invalid, and separately confirms that asking it to generate a display label for that same missing ID raises a clear "target not found" error rather than returning a blank or fabricated label. This is the safeguard preventing tasks from ever being silently attached to applications that were deleted or never existed in the first place.
- **test_factory_returns_registered_resolver** — Registers a Contact resolver with the factory responsible for choosing the right resolver per target type (Contact vs. Application, etc.), then asks the factory for the "Contact" type and confirms it hands back a working resolver that correctly validates a seeded contact. This proves the routing mechanism letting the service support multiple target types is wired correctly, not just declared.
- **test_factory_rejects_unregistered_target_type** — Confirms that asking the resolver factory for a target type it has no handler for (like "Ticket") raises an explicit "unsupported target type" error. This is the root cause of the 422 error seen at the API level, ensuring unknown target types are rejected early and clearly rather than causing confusing downstream failures.
- **test_factory_register_adds_a_new_resolver_without_replacing_existing_ones** — Starts with a factory that already has a Contact resolver registered, then registers an additional Application resolver onto the same factory, and confirms both the original Contact resolver and the newly added Application resolver remain available and retrievable afterward. This proves new target types can be added to the system over time without accidentally breaking or overwriting support for the ones already in place.

### tests/unit/test_gateway_task_repository.py

- **test_save_assigns_an_id** — Saves a brand-new task through the repository layer that talks to the Data Gateway, and confirms the task comes back with a non-empty generated ID (the real Data Gateway Service allocates a "TK-000001"-style ID; this in-memory test double only guarantees an ID is assigned, not that specific format). This proves every task gets a real identifier the moment it's created, which every later lookup, update, or reference to that task depends on.
- **test_find_by_id_returns_what_was_saved** — Saves a new task directly through the repository layer that talks to the Data Gateway, then retrieves it back by its generated ID, confirming both the target contact ID and the "open" status exactly match what was originally saved. This validates the core read/write reliability of task storage on its own, independent of the HTTP layer sitting on top of it.
- **test_find_by_id_raises_for_an_unknown_task** — Confirms that looking up a task ID that was never saved raises a clear "record not found" error rather than returning garbage or crashing unexpectedly. This is the underlying mechanism that produces a clean 404 response when the API is asked for a nonexistent task.
- **test_find_by_filter_matches_on_provided_fields** — Saves two separate tasks assigned to two different staff members, then queries the repository filtered by just one specific staff ID, confirming exactly one task comes back and that it's the one actually assigned to that staff member. This proves the underlying filtering logic correctly narrows results rather than returning everything, which is essential for features like "show me only my tasks."
- **test_update_persists_status_and_assignee_changes** — Saves a task, marks it done and reassigns it to a new staff member, then re-fetches it from storage to confirm both the status and assignee changes were actually persisted. This proves updates to a task are durable and not just held in memory temporarily, so changes survive across requests.

### tests/unit/test_task_creation_rules_evaluator.py

- **test_should_create_task_true_for_a_registered_event_type** — Configures the evaluator with a rule mapping "application.stage_changed" events to automatic task creation, then feeds it a matching event and confirms it correctly reports that a task should be created. This is the trigger point behind automatic follow-up tasks being generated from real business activity without any staff member having to manually create them.
- **test_should_create_task_false_for_an_unregistered_event_type** — Feeds the evaluator an event type ("contact.created") that has no configured auto-task-creation rule attached to it, and confirms it correctly reports that no task should be created for that event. This prevents the system from generating unwanted or irrelevant tasks for every single business event flowing through the platform, keeping task lists focused on what actually matters.
- **test_build_task_dto_maps_fields_per_the_rule** — Feeds a qualifying event into the evaluator and confirms it correctly extracts the target type, target ID, due date, and assigned staff ID from the event's fields according to the configured rule's field mappings. This proves the system correctly translates a generic business event into the specific data needed to create a real task.
- **test_a_redelivered_event_id_is_suppressed_after_being_built_once** — Simulates the same event being processed twice (as can happen with at-least-once message delivery), confirming that after a task has already been built from an event, asking again whether a task should be created for that same event ID now returns false. This prevents duplicate tasks from being created if the same event is accidentally delivered more than once.
- **test_events_without_an_event_id_are_never_deduplicated** — Confirms that an event with no event ID at all is never subject to the duplicate-suppression logic, so a task can still be built from it every time. This documents that the deduplication safety net specifically depends on event IDs being present, which matters for understanding the limits of that protection.

### tests/unit/test_task_event_consumer.py

- **test_on_message_creates_a_task_for_a_qualifying_event** — Feeds a qualifying "application.stage_changed" event to the message consumer and confirms it calls through to create a task with the correct target type and ID extracted from the event. This proves the end-to-end automated pathway from an incoming event to a real task creation request functions correctly.
- **test_on_message_accepts_a_json_string_payload** — Confirms the consumer can handle an event delivered as a raw JSON string (as messages typically arrive from a message queue) rather than requiring a pre-parsed dictionary, and still successfully triggers task creation. This proves compatibility with how events actually arrive in production messaging infrastructure.
- **test_on_message_ignores_a_non_qualifying_event_type** — Sends the message consumer an event type with no matching auto-creation rule ("contact.created" instead of "application.stage_changed") and confirms neither is a task created nor is any warning event published in response. This proves the service quietly and correctly ignores irrelevant traffic instead of generating noise, warnings, or errors for every event type it doesn't actually care about.
- **test_on_message_skips_and_publishes_a_warning_when_the_target_does_not_exist** — Simulates the underlying task creation failing because the referenced target (e.g. an application) doesn't actually exist, and confirms the consumer catches this gracefully, publishing a "task.auto_creation_skipped" warning event that records which event type triggered the failed attempt. This ensures a bad or stale event doesn't crash the service, while still leaving an audit trail explaining why a task wasn't created.
- **test_on_message_skips_and_publishes_a_warning_for_an_unsupported_target_type** — Simulates the target type coming back as unsupported and confirms the consumer again gracefully skips task creation and emits a "task.auto_creation_skipped" warning rather than raising an unhandled error. This is another layer of resilience so malformed or unexpected upstream events can't take the service down.
- **test_on_message_skips_a_malformed_event_missing_a_required_field** — Removes the required follow-up due-date field from an otherwise valid, qualifying event and confirms the consumer does not attempt task creation from it, instead publishing a "task.auto_creation_skipped" warning event so the incident is recorded rather than silently dropped. This protects against partial or corrupted upstream event data ever resulting in an incomplete or broken task record.
- **test_on_message_creates_a_task_from_a_real_kafka_envelope** — Feeds the consumer a fully-wrapped Kafka audit envelope, the same shape the Application Service's real event publisher actually sends (topic under "action," business fields nested inside "detail_json"), rather than the flatter shape used in this file's other test fixtures, and confirms it still correctly triggers task creation with the right target type and ID. This proves the consumer works against the real on-the-wire message format produced by upstream services, not just a simplified stand-in shape.
- **test_on_message_handles_an_undeserializable_payload_without_raising** — Feeds the consumer a plain string that isn't valid JSON at all, confirming it doesn't crash but instead safely publishes a skip warning noting the deserialization failure. This proves the service can survive completely garbled input from the message queue without going down, which matters for overall system uptime.

### tests/unit/test_task_service.py

- **test_create_task_resolves_label_saves_and_publishes_created_event** — Exercises the core task creation logic directly, confirming that creating a task against a valid contact resolves the contact's name as the label, saves the task, and publishes a "task.created" event afterward. This proves the central business logic wiring together validation, storage, and downstream notification all works together correctly.
- **test_create_task_rejects_an_unregistered_target_type** — Confirms that attempting to create a task against an unsupported target type raises an error before anything is saved to storage. This proves the service enforces its target-type rules at the business-logic layer, not just at the API's input validation, so bad data can never slip through.
- **test_create_task_rejects_a_target_that_does_not_exist** — Confirms that creating a task against a target ID that doesn't exist raises a "target not found" error and that nothing gets saved. This is the core rule preventing tasks from ever being attached to a nonexistent Contact or Application, protecting data integrity throughout the system.
- **test_create_task_from_event_follows_the_same_path_as_direct_creation** — Creates a task via the automated event pathway (rather than a direct staff request) and confirms it goes through the same save-and-publish behavior as manual creation, including correctly picking up the assigned staff member from the event. This proves automated and manual task creation are consistent, so downstream systems don't need to treat them differently.
- **test_update_status_to_done_publishes_status_updated_event** — Updates an existing task's status to "done" and confirms both that the returned task reflects the new status and that a "task.status_updated" event is published with the task ID and new status. This proves status changes are properly tracked and broadcast so other services (like reporting or audit trails) stay in sync.
- **test_reassign_updates_assignee_and_publishes_event** — Reassigns an existing task to a new staff member and confirms the returned task shows the new assignee while a "task.reassigned" event is published with the task ID and new staff ID. This ensures handoffs between staff are both applied correctly and visible to the rest of the system for tracking purposes.
- **test_list_tasks_delegates_to_repository_find_by_filter** — Confirms that listing tasks with a filter (like a specific staff ID) correctly passes that same filter through to the underlying storage layer's lookup. This proves the filtering feature used in task lists is wired correctly end to end at the service level, not just at storage.

### tests/unit/test_kafka_event_publisher.py

- **test_publish_wraps_event_into_the_full_audit_envelope_shape** — Publishes a "task.created" event and inspects the message actually sent to the messaging system, confirming it includes a valid unique event ID, correctly identifies the source as "task-service", the acting party as "system," the target type as "Task," the specific task ID, the original event details, and a timestamp with timezone information. This proves every event this service emits carries the complete, well-formed audit trail data that downstream systems like the Audit Service require.
- **test_publish_falls_back_to_event_type_when_task_id_is_absent** — Publishes a "task.auto_creation_skipped" event, which by nature never has a task ID since no task was created, and confirms the envelope instead uses the original event type as the target ID rather than leaving it blank. This is important because the downstream Audit Service silently discards any event with an empty target ID, so this fallback ensures skip/warning events still get properly recorded rather than vanishing.
- **test_publish_falls_back_to_empty_target_id_only_when_nothing_else_is_available** — Publishes an event with no task ID and no event type field to fall back on, confirming the envelope's target ID ends up as an empty string in this last-resort scenario. This documents the outer boundary of the fallback behavior, showing exactly when the safety net described above can still come up empty.
- **test_envelope_is_json_serializable** — Publishes a "task.created" event through the Kafka publisher and confirms the complete envelope it hands off (event ID, source service, actor, target, timestamp, and original details all included) can be successfully converted to JSON without raising any error. This is a basic but critical guarantee, since a non-serializable envelope would silently break message delivery to the Kafka-based event pipeline every downstream service depends on.

### tests/unit/test_kafka_consumer_runner.py

- **test_run_forever_subscribes_only_to_the_configured_topics** — Confirms that when the consumer runner starts up, it subscribes specifically to the exact list of event topics it cares about (like "application.stage_changed"), configured with the correct consumer group and offset settings. This proves the Task Service only listens to relevant business events rather than every event flowing through the messaging system, keeping it efficient and focused.
- **test_run_forever_passes_each_message_value_to_the_consumer_and_commits** — Simulates a single message arriving from the message queue and confirms the runner hands its value off to the event consumer for processing, then commits the offset afterward to mark it as handled. This proves messages are both processed and properly acknowledged, so they aren't silently lost or endlessly reprocessed.
- **test_run_forever_closes_the_client_when_done** — Runs the Kafka consumer loop against a fake client with no messages waiting, then confirms that once the loop exits, the underlying connection to the message broker is explicitly closed rather than left dangling. This ensures the service cleans up its network resources correctly and doesn't leak open broker connections across restarts or redeploys.
- **test_stop_sets_running_false** — Manually flips the consumer runner's internal running flag to true to simulate an active poll loop, then calls stop and confirms the flag flips back to false. This is the basic mechanism that lets the service gracefully wind down its message-listening loop when the application is shutting down, rather than being forcibly killed mid-poll.
