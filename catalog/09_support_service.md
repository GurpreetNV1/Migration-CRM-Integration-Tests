# Support Service — Test Catalog

The Support Service manages support tickets raised against a polymorphic target (like a Contact or Application), handling creation with auto-assignment, status transitions, reopening, reassignment, and querying — this catalog covers 27 tests total (13 integration, 14 unit).

## Integration tests

*These also live at `../tests/service_integration/support/`, dual-mode (real Data Gateway/real Sheets by default, `--gateway-mode=memory` for the fast in-memory behavior described below) — run via `python run_local_integration_tests.py --service support`. Same definitions apply to both; see `../README.md`/`../TESTING_GUIDE.md` section 8.5.*

### tests/integration/test_health.py

- **test_health** — This test hits the service's health-check endpoint with a simple GET request and confirms it returns HTTP 200 along with a plain `{"status": "ok"}` response body. It exists purely as an infrastructure smoke test — proof the Support Service process is up, responding, and wired correctly before any ticket-related functionality is exercised, which is exactly what uptime monitors and load balancers check.

### tests/integration/test_ticket_flow.py

- **test_create_ticket** — This test submits a new support ticket with just a raised-by customer ID, subject, and description — no target attached — and confirms the API responds with 201 Created. It checks the returned ticket ID follows the TCK- prefix convention, the ticket starts in "open" status automatically, and the subject text is stored exactly as submitted, proving basic ticket creation works end to end.
- **test_create_ticket_with_target** — This test creates a ticket that is explicitly linked to a target record — in this case an Application with ID AP-000001 — demonstrating the polymorphic ticket model where a ticket can be raised against different kinds of business entities. It confirms the API echoes back the same target_type and target_id, proving tickets can be correctly tied to the record a customer is complaining about.
- **test_create_ticket_with_target_type_but_no_target_id_returns_400** — This test submits a ticket that specifies a target_type of "Application" but leaves out the target_id, and confirms the API rejects it with a 400 Bad Request. This enforces a data-integrity rule: you cannot say a ticket is about an Application without saying which Application, preventing orphaned or ambiguous ticket-to-record links that would confuse support staff and reporting later on.
- **test_get_ticket_returns_what_was_created** — This test creates a ticket and then immediately fetches it back by its ticket ID via a GET request, confirming the returned ticket ID matches exactly. It proves the read path is consistent with the write path — what a user sees when they open a ticket is genuinely the same record that was just saved, not stale or mismatched data from the storage layer.
- **test_get_unknown_ticket_returns_404** — This test requests a ticket ID that was never created — TCK-999999 — and confirms the API responds with a 404 Not Found rather than an error or an empty success response. This proves the service correctly distinguishes between "this ticket does not exist" and other failure modes, which matters for support agents searching for tickets by ID or handling stale links.
- **test_list_tickets_filters_by_raised_by_id** — This test creates a ticket raised by a specific customer, CT-777777, then queries the ticket list endpoint filtered by that same raised_by_id and confirms the newly created ticket appears in the results. It proves customers or agents can pull up "all tickets raised by this person," a core lookup used whenever someone wants a full history of one customer's support requests.
- **test_list_for_target** — This test creates a ticket linked to a Contact target (CT-TARGET-1) and then queries the dedicated by-target endpoint for that same Contact, confirming the ticket shows up in the results. It proves the polymorphic linking works both ways — you can not only tag a ticket with a record, but also look up every ticket ever raised against that specific record.
- **test_full_lifecycle_open_to_closed** — This test walks one ticket through its entire real-world lifecycle: created as "open," moved to "in_progress" when staff start working it, moved to "resolved" once the issue is fixed, and finally moved to "closed." Each step asserts a 200 response and the correct status value, proving the full happy-path workflow a support ticket follows from intake to closure works correctly.
- **test_illegal_transition_returns_409_with_allowed_states** — This test resolves a ticket and then tries to illegally push it back to "in_progress," confirming the API rejects the move with a 409 Conflict rather than silently allowing it. The error response also reports the ticket's current status ("resolved") and the list of states it can legally move to next, giving the UI enough information to guide staff instead of just failing blindly.
- **test_reopen_from_resolved_is_allowed** — This test resolves a ticket and then calls the dedicated reopen endpoint with a staff actor ID and a reason ("still broken"), confirming the ticket successfully returns to "open" status with a 200 response. This proves the business rule that a resolved-but-not-yet-closed ticket can be reopened if the customer reports the problem persists, without forcing staff to create a brand new ticket.
- **test_reopen_from_closed_is_rejected** — This test closes a ticket completely and then attempts to reopen it, confirming the API rejects the request with a 409 Conflict. This enforces the business rule that "closed" is a truly final state — once a ticket is closed, staff must raise a new ticket rather than resurrecting an old one, keeping historical records clean and closure meaningful.
- **test_reassign_ticket** — This test creates a new ticket and then calls the reassign endpoint to hand it to a different staff member, STF-42, confirming the response reflects the new assigned_staff_id with a 200 status. This proves a supervisor or the system can manually override the automatic assignment at any time, which matters when workload needs rebalancing or a specialist needs to take over a case.

## Unit tests

### tests/unit/test_ticket_assignment_strategy.py

- **test_raises_when_no_staff_has_ever_been_assigned** — This test sets up an empty ticket repository — no ticket has ever been assigned to any staff member — and confirms that asking the round-robin assignment strategy to pick an assignee raises a NoEligibleAssigneeError. It proves the system correctly recognizes when there is no assignment history to work from yet, rather than crashing or silently picking an invalid staff ID.
- **test_picks_the_only_known_staff_member** — This test saves one existing ticket already assigned to a single staff member, STF-SOLO, and then asks the round-robin strategy to assign a brand-new ticket. It confirms that lone staff member is selected, proving the simplest real-world case works correctly: when only one person has ever handled tickets, every new ticket automatically goes to them by default.
- **test_picks_the_staff_member_with_fewer_open_tickets** — This test creates two open tickets assigned to a busy staff member and one closed ticket assigned to a free staff member, then asks the round-robin strategy to assign a new ticket. It confirms the free staff member is chosen, proving the load-balancing logic correctly counts only open workload and routes new tickets toward whoever currently has the lighter caseload.

### tests/unit/test_ticket_creation_service.py

- **test_raise_ticket_assigns_saves_and_publishes_created_event** — This test exercises the core ticket-creation service directly with mocked dependencies, forcing the assignment strategy to return staff member STF-1. It confirms the created ticket carries that assigned staff ID, that the ticket was saved to the repository, and that both a "ticket.created" and a "ticket.assigned" event were published — proving creation, auto-assignment, and downstream event notification all happen together in one atomic flow.
- **test_raise_ticket_rejects_a_target_type_with_no_target_id** — This test calls the ticket-creation service with a target_type of "Application" but no target_id, confirming it raises an InvalidTicketTargetError before anything is saved. It also verifies the repository's save method was never called, proving invalid ticket data is rejected at the service layer itself rather than allowed through to storage and only failing later.
- **test_raise_ticket_still_succeeds_when_no_eligible_assignee** — This test simulates the assignment strategy failing with a NoEligibleAssigneeError — meaning there's genuinely no staff member available to route the ticket to — and confirms ticket creation still succeeds anyway, with assigned_staff_id left as null. It also verifies only a "ticket.created" event fires, not "ticket.assigned," proving a missing assignee never blocks a customer's ticket from being logged.

### tests/unit/test_ticket_resolution_service.py

- **test_transition_updates_status_and_publishes_event** — This test moves a ticket from "open" to "in_progress" through the resolution service with actor STF-1 and a note of "starting work," confirming the returned ticket reflects the new status. It also checks that a "ticket.status_changed" event was published carrying the previous status, new status, actor, and note — proving every status change is both applied and recorded for the Audit Service.
- **test_transition_rejects_an_illegal_move** — This test starts with a ticket already in "resolved" status and attempts to move it directly to "in_progress," confirming the service raises an InvalidTicketTransitionError instead of allowing the change. It also verifies the repository's update_status method was never called, proving illegal status jumps are blocked at the business-logic layer before any data is actually written to storage.
- **test_reopen_delegates_to_transition_with_open_status** — This test starts with a resolved ticket and calls the service's dedicated reopen method with actor STF-1 and reason "client says still broken," confirming the ticket comes back with status "open." It proves reopening is implemented as a thin, consistent wrapper around the same validated transition logic used everywhere else, rather than a separate one-off code path that could drift out of sync.
- **test_reassign_updates_assignee_via_save** — This test reassigns an existing ticket to staff member STF-99 through the resolution service, confirming the returned ticket's assigned_staff_id is updated and that the repository's save method was called to persist the change. It also verifies a "ticket.reassigned" event was published with the ticket ID and new assignee, proving reassignments are both saved and broadcast for downstream consumers like the Audit Service.

### tests/unit/test_ticket_status_transition.py

- **test_open_can_move_to_in_progress_or_closed** — This test checks the status-transition rules for a ticket currently "open," confirming it is allowed to move to "in_progress" or directly to "closed," but is explicitly forbidden from jumping straight to "resolved." This encodes the business rule that a ticket must be actively worked before it can be marked resolved — you can abandon it (close) but you cannot skip the work step.
- **test_in_progress_can_move_to_open_resolved_or_closed** — This test checks the status-transition rules for a ticket "in_progress," confirming it can move back to "open" (if work stalls or gets reassigned), forward to "resolved" (once fixed), or straight to "closed." This proves staff have full flexibility once they've started working a ticket, reflecting how real support workflows often need to pause, finish, or abandon a case mid-stream.
- **test_resolved_can_reopen_or_close_but_not_go_back_to_in_progress** — This test checks the status-transition rules for a "resolved" ticket, confirming it can be reopened back to "open" or finalized to "closed," but cannot move directly back to "in_progress." This enforces the rule that resuming active work on a resolved ticket must go through reopening it first, keeping the history clear about when a ticket was genuinely reopened versus just re-touched.
- **test_closed_is_terminal** — This test checks the status-transition rules for a "closed" ticket and confirms its list of allowed next states is completely empty, meaning no transition — including back to "open" — is permitted. This proves "closed" is a true dead end in the ticket lifecycle, guaranteeing closed tickets stay closed and can never be silently mutated after the fact.
